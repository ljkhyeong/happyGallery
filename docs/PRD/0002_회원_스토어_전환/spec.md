# 회원 중심 스토어 전환 메모

현재 반영 상태:
- U1~U6 구현 완료
- 회원 `/api/v1/me/**`, `/my`, `/my/orders`, `/my/bookings`, `/my/passes`, 휴대폰 변경·기준 이메일 최초 등록·탈퇴, 비회원 이력 가져오기(claim)와 토큰 복구, `/guest/**` 표준 경로까지 반영되어 있다.
- 현재 서비스의 기준 문서는 `docs/PRD/0001_기준_스펙/spec.md`
- 이 문서는 회원 중심 스토어로 정리하던 과정에서 남긴 요구사항과 배경 메모다.

참고 화면:
- 사용자가 제시한 네이버 스마트스토어 상품 상세 페이지
  - `https://smartstore.naver.com/ballon2/products/12510354216?...`

---

## 0. 문서 목적

- 비회원 중심 화면에서 회원 중심 스토어로 옮길 때 필요한 요구사항을 정리한다.
- 인증, 조회, 화면 경로가 어떻게 바뀌는지 한눈에 보이게 정리한다.
- 현재 구현 문서와 분리해 배경과 의사결정 맥락을 남긴다.

---

## 1. 목표 경험

- 사용자는 스토어 홈과 상품 상세를 중심으로 상품을 탐색한다.
- 상품 상세 페이지에서 바로 주문 흐름으로 진입할 수 있다.
- 상품·클래스 상세 콘텐츠와 공방 위치·영업 안내를 실제 운영 정보로 제공한다.
- 회원은 로그인 후 주문/예약/8회권 조회를 추가 인증 없이 처리한다.
- 비회원은 기존처럼 휴대폰 인증 또는 토큰 기반 조회를 유지한다.
- 예약과 비회원 주문은 제출 직전까지 인증을 요구하지 않는다.
- 8회권 구매는 회원 로그인 후 진행한다.

---

## 2. 사용자 유형

### 2.1 회원

- 이메일+비밀번호 또는 Google/Naver/Kakao 소셜 계정으로 로그인하는 사용자
- 로그인 세션으로 `내 주문`, `내 예약`, `내 8회권`에 접근 가능
- 예약/구매 제출 시 휴대폰 인증을 매번 다시 요구하지 않음

### 2.2 비회원

- 계정 없이 비회원 주문 절차를 사용하는 사용자
- 주문/예약 생성 시 휴대폰 인증 또는 주문/예약 토큰이 필요
- 조회는 비회원 전용 경로로만 접근 가능

### 2.3 관리자

- 기존 관리자 인증 모델 유지
- 고객 회원 인증과 완전히 분리
- 주문·예약 검색 결과의 `운영` 액션은 별도 상세 화면이 아니라 기존 주문·예약 운영 패널로 이동해 대상 행을 강조하고 후속 처리를 이어가게 한다.

---

## 3. 인증 정책

### 3.1 고객 회원 인증

- 고객 회원가입 API와 로그인 API를 제공한다.
- 기본 방식은 `HttpOnly` 쿠키 기반 세션이다.
- 고객 세션은 관리자 세션과 분리한다.
- 고객 세션 TTL은 7일이며 Spring Session Redis의 단일 설정을 사용한다. 인증·폐기 기준은
  [ADR-0023](../../ADR/0023_관리자_회원_인증_세션_기준선/adr.md)을 따른다.
- 이메일 회원가입과 처음 보는 소셜 계정의 신규 회원 생성은 현재 이용약관·개인정보처리방침 버전에 동의해야 하며, 서버 수락 시각과 목적을 회원 동의 이력으로 남긴다. 기존 회원 로그인에는 재동의를 요구하지 않는다.
- Google 검증 이메일과 Kakao의 유효·검증 이메일은 가입 시 기준 이메일로 사용한다. Naver 프로필 이메일은 신뢰하거나 기존 회원 자동 병합에 사용하지 않는다. 기준 이메일이 없는 로그인 회원은 최근 본인 확인 뒤 전용 SMTP로 받은 6자리 코드를 검증해 본인이 소유한 이메일을 한 번 등록할 수 있다.

### 3.2 비회원 인증

- 비회원 주문 절차는 유지한다.
- 주문/예약 조회는 현재와 같은 토큰 또는 휴대폰 인증 기반을 유지한다.
- 비회원 생성 플로우에서만 휴대폰 인증을 사용한다.

### 3.3 인증 시점

- 상품/클래스/시간 탐색 단계에서는 인증을 요구하지 않는다.
- 예약/비회원 주문은 확정 직전에만 로그인/회원가입/비회원 진행을 선택하게 한다.
- 8회권은 상품 안내를 볼 수 있지만, 구매 실행은 로그인 세션 기준으로만 허용한다.

## 5. 화면 요구사항

### 5.1 홈

- 홈은 다수 공방을 입점시키는 마켓이 아니라 충주 해피갤러리 공식 서비스의 첫 화면이다.
- 첫 화면에서 실제 공방과 작품을 보여주고 `해피갤러리 → 개인 클래스 → 단체·기관 수업 → 공방 기록 → 작품 → 방문 안내` 순서로 핵심 경험을 소개한다.
- `/classes`는 활성 클래스의 시간·가격·대상·준비물을 보여주고 각 항목을 `/bookings/new?classId={id}`로 연결한다.
- `/group-classes`는 학교·기관·모임의 인원, 장소와 일정을 먼저 조율하도록 네이버톡톡 또는 전화 문의로 연결한다.
- 작품, 8회권, 내 정보 또는 로그인 진입점도 전역 내비게이션에서 명확해야 한다.

### 5.2 상품 상세

- 상품 상세는 주문 메인 진입점이다.
- 필수 표시:
  - 상품명
  - 가격
  - 재고/구매 가능 상태
  - 상품 유형
  - 상품 설명
  - 대표 이미지
  - 수량 선택
  - 총액
  - 구매 버튼
- Product Q&A 일반글 상세는 비밀번호 없이 공개하고, 비밀글 상세에만 작성 시 설정한 비밀번호 검증을 요구한다.
- 모바일에서는 구매 CTA가 쉽게 노출되어야 한다.

### 5.3 예약 생성

- 먼저 클래스/날짜/시간을 고른다.
- 제출 직전에 인증 선택 단계를 연다.
- 회원이면 바로 제출, 비회원이면 휴대폰 인증 후 제출한다.

### 5.4 8회권 구매

- 먼저 상품 안내/가격을 확인한다.
- 비로그인 사용자는 로그인 페이지로 리다이렉트한다.
- 로그인한 회원만 구매를 실행할 수 있다.
- 구매한 8회권의 예약은 운영자가 일괄 배정하지 않고, 회원이 예약 가능 슬롯을 직접 선택해 한 회차씩 생성한다.
- 신규 8회권은 `REGULAR_CRAFT_8` 계획으로 저장하고 `passEligible=true`이며 향수가 아닌 클래스에만 사용할 수 있다.
- `내 8회권`의 사용 가능 항목에서 예약 화면으로 이동하면 해당 8회권을 미리 선택한다. 예약 화면의 8회권 선택 목록에는 본인 소유이면서 잔여 크레딧이 있고, 만료되지 않았으며, 환불 이력이 없는 항목만 노출한다.
- 회원은 내 8회권에서 잔여 횟수 정산 환불을 요청하고 같은 목록·상세에서 PG 환불 진행 상태를 확인한다.

### 5.5 조회 화면

- 회원은 `내 주문`, `내 예약`, `내 8회권`, `내 후기`에서 조회한다.
- 주문·예약·8회권 목록은 `/my/orders`, `/my/bookings`, `/my/passes`에서 나눠 보고 검색, 상태 필터, 빠른 탭, 정렬로 좁힌다. `/my/reviews`는 최신순 커서 목록으로 작성한 후기를 이어 본다.
- 회원 예약 상세 화면에서 변경/취소를 직접 수행한다.
- 회원 주문 상세에서는 승인 대기 주문을 취소하고, 제작 지연 동의 대기 주문의 제안을 수락하거나 거절한다.
- 배송·픽업이 끝난 회원 주문 상세에서 품목별 상품 후기를, 완료된 회원 예약 상세에서 클래스 후기를 작성한다. `/my/reviews`에서 작성 가능한 완료 거래, 작성한 후기, 숨김 사유와 공방 답글을 모아 보고 본문·별점·사진을 수정·삭제한다.
- 배송·픽업이 끝난 회원·비회원 주문 상세에서는 품목·수량별 환불·교환 클레임을 접수하고 처리·PG 환불 상태를 조회한다.
- 비회원은 비회원 전용 조회 화면에서만 조회한다.
- 비회원 전용 조회 화면은 생성 후 확인용 보조 경로로 안내하고, 지속 관리 경로는 회원 `/my`로 유도한다.
- 비회원 주문/예약 성공 화면은 회원가입/로그인 후 `/my`의 비회원 이력 가져오기(claim)로 이어지는 CTA를 제공한다.
- 로그인/회원가입 페이지는 `redirect`, `claim`, 회원가입 시 미리 채우는 값(`name`, `phone`)을 유지한다. 회원 전환 흐름이 중간에 끊기지 않게 하기 위함이다.

## 6. 비즈니스 규칙 변경

### 6.1 주문

- 회원 주문은 로그인 세션 기준으로 생성한다.
- 비회원 주문은 비회원 주문 절차와 휴대폰 인증을 거쳐 생성한다.
- 상품 상세에서 비회원 주문 보조 경로로 이동할 때는 선택한 상품과 수량을 미리 채운다.
- 회원 주문 조회는 추가 토큰 없이 가능하다.
- 비회원 주문 조회는 토큰 또는 비회원 인증이 필요하다.
- 회원·비회원 모두 `PAID_APPROVAL_PENDING` 주문만 직접 취소할 수 있다. 비회원은 `X-Access-Token`을 사용한다.
- 관리자는 기성품의 승인 전 재고 부족과 주문제작의 제작 중 일정 변경에 대해 주문 처리 지연을 제안할 수 있다. 고객 수락은 `DELAY_ACCEPTED`, 거절은 `DELAY_REJECTED_CANCELED`로 처리한다.
- 수락 뒤 `/api/v1/admin/orders/{id}/resume-after-delay`로 재개하면 기성품은 `APPROVED_FULFILLMENT_PENDING`, 주문제작은 `IN_PRODUCTION`으로 돌아간다.
- 완료된 주문의 클레임은 주문 전체가 아니라 주문 항목 ID와 수량으로 접수한다. 관리자는 환불·교환 승인 또는 거절, 반품 재고 복구 여부와 환불액을 결정하며 교환품 출고 재고는 다시 차감한다.

### 6.2 예약

- 회원 예약은 로그인 상태에서 생성/조회/변경/취소한다.
- 비회원 예약은 기존 비회원 인증 경로를 유지한다.
- 예약 시간 탐색에는 인증이 필요 없다.
- 운영자 취소로 자동 처리할 수 없는 현장 잔금·만료 이용권 보상은 DB 후속 작업으로 남겨 관리자 오늘 할 일과 예약 탭에서 완료 처리한다.

### 6.3 8회권

- 8회권 구매는 회원 전용이다. 비로그인 시 로그인 리다이렉트.
- 비회원 소유 8회권 상태는 더 이상 지원하지 않는다.

## 7. 데이터 모델 목표 상태

### 7.1 users

- 기존 `users` 테이블을 실제 고객 회원 모델로 사용한다.
- 검증된 기준 이메일은 nullable이며, 이메일·이름·전화번호는 평문 컬럼 없이 AES-GCM 암호문과 정확 일치 검색용 HMAC으로 저장한다.
- 이메일은 앞뒤 공백을 제거하고 소문자로, 전화번호는 공백·하이픈을 제거한 숫자 형식으로 통일한다.
- `phone_verified`, `last_login_at`을 회원 인증 상태로 유지한다.
- `withdrawn_at`으로 탈퇴 회원을 일반 조회·로그인에서 제외하고, `phone_hmac`은 회원 전체에서 유일하게 유지한다.
- 소셜 제공자 식별자는 `user_social_accounts.provider_id_hmac`에 저장한다.

### 7.2 sessions

- 고객 세션은 `HG_SESSION` 쿠키 + Spring Session + Redis를 기준으로 한다.
- 세션 사용자 식별자는 Spring Session에 저장한 `customerUserId`를 사용한다.
- 세션 TTL은 7일이다.
- 브라우저는 로그인·로그아웃·회원 ID 변경과 활성 회원 세션 만료 때 회원 cache와 개인정보 입력 상태를 새 계정 세대로 교체한다. 새 epoch와 관찰한 회원 ID를 같은 브라우저 탭끼리 공유하고, 다른 탭의 변경을 감지하면 개인정보 상태를 먼저 제거한 뒤 `/me`로 실제 세션 주체를 다시 확인한다. 다시 표시된 탭은 epoch가 같아도 `/me`를 확인하며, timeout이나 서버 장애를 로그아웃으로 전파하지 않는다. 최초 비회원 상태를 확인하는 `/me` 401만으로 공개 화면 입력을 초기화하지 않으며, 저장된 회원 ID와 `/me`의 회원 ID가 같은 새로고침·PG 리다이렉트는 계정 전환으로 처리하지 않는다.
- 이전 계정에서 시작한 회원 변경 응답이 계정 전환 뒤 도착하면 토스트, 화면 이동과 cache 갱신을 현재 계정에 적용하지 않는다. 회원·비회원 구분 없이 결제를 시작한 계정 세대나 공유 epoch가 바뀌면 지연된 결제 응답의 임시 저장값과 PG 호출을 이어가지 않으며, 결제 결과 화면도 이전 계정의 confirm·상태 조회 결과를 표시하지 않는다. 결제 임시값과 비회원 주문·예약/결제 복구 결과는 저장 당시 epoch와 회원 ID가 현재 경계와 같을 때만 읽는다. 이전 흐름의 정리는 저장 당시 소유자와 값이 모두 같은 항목에만 적용해 새 계정이 같은 주문번호나 값을 저장해도 삭제하지 않는다. 복구 결과에서 상세 화면으로 넘긴 token도 시작 계정 snapshot이 현재와 같을 때만 사용하며, 계정 세대가 바뀌면 비회원 조회 폼·상세·mutation 상태를 버린다. 진행 중 `/me` 요청은 같은 계정 세대와 공유 epoch에서만 재사용하고, stale 요청은 비회원 결과가 아니라 계정 변경으로 종료한다.
- 소셜 재인증과 계정 연결의 callback continuation은 시작 회원 ID에 귀속하며, callback의 현재 회원과 다르면 후속 작업을 중단한다.

### 7.3 주문/예약/8회권 식별

- `orders`, `bookings` 는 `user_id` 또는 `guest_id` 중 하나만 가진다.
- 둘 다 비어 있거나 둘 다 채워진 상태는 금지한다.
- 이 규칙은 도메인 생성·claim 경로와 DB `CHECK` 제약에서 모두 강제한다.
- `pass_purchases` 는 회원 전용이므로 `user_id`만 가진다.

### 7.4 비회원 이력 가져오기(claim)

- 자동 병합 금지
- 현재 선택:
  - 로그인한 회원이 휴대폰 인증을 통과한 뒤 기존 비회원 이력을 직접 가져온다.

### 7.5 스토어 콘텐츠와 운영 정보

- 상품은 설명·대표 이미지·판매 상태를, 클래스는 설명·대표 이미지·준비물·대상·8회권 사용 가능 여부·운영 상태를 가진다.
- 공개 상품 목록과 클래스 목록은 활성 항목만 노출한다. 판매 중지 상품의 기존 상세 링크는 구매 불가 상태로 유지한다.
- 공방 이름·연락처·주소·영업시간·지도·주차 안내는 단일 공방 프로필에서 공개·관리한다.
- 블로그의 수업·작품 기록은 런타임에 스크래핑하지 않는다. 홈페이지는 선별한 공식 게시물과 저장소에 보관한 실제 공방 사진을 사용하고, 자세한 기록은 원문 블로그로 연결한다.
- 업로드 이미지는 DB 바이너리가 아니라 자가 호스팅 미디어 볼륨에 append-only로 저장하고 DB 백업과 같은 복구 묶음으로 관리한다.
- 주문 항목의 상품명·단가, 배송비와 배송 출발 뒤 택배사·운송장 번호는 과거 주문을 재현할 수 있게 스냅샷으로 유지한다.

### 7.6 정책 동의 이력

- `policy_consents`는 회원 또는 결제 시도 중 정확히 한 주체를 가진다.
- 이용약관·개인정보처리방침을 유형별 행으로 추가 저장하고, 가입·소셜 가입·비회원 주문·비회원 예약 목적과 서버 수락 시각을 보존한다.
- 현재 문서 경로와 버전은 공개 정책 API로 조회하며, 문구 본문은 기존 `/terms`, `/privacy` 화면을 기준으로 한다.

## 8. API 목표 상태

### 8.1 고객 인증 (U1 구현 완료)

- `GET /api/v1/policies/current` — 현재 이용약관·개인정보처리방침 버전과 문서 경로
- `POST /api/v1/auth/signup` — 이메일/비밀번호/이름/전화번호/SMS 인증 코드와 현재 정책 동의, 소유권 확인 성공 시 `phoneVerified=true`, 201 + HttpOnly 쿠키
- `POST /api/v1/auth/login` — 이메일/비밀번호, 200 + HttpOnly 쿠키
- `POST /api/v1/auth/logout` — 204 + 쿠키 삭제
- `GET /api/v1/me` — 로그인 필수, 200 `{id, email, name, phone, phoneVerified, localPasswordEnabled}` (`email`, `phone` nullable)
- `POST /api/v1/me/email-verifications` — 최근 본인 확인 필수, 기준 이메일 소유 확인 코드 발송, 204
- `PATCH /api/v1/me/email` — 최근 본인 확인과 6자리 코드로 기준 이메일 최초 등록, 204 + 기존 회원 세션 폐기
- 세션: Spring Session + Redis, 7일 동안 유지
- 쿠키: `HG_SESSION`, HttpOnly, SameSite=Lax, Path=/

### 8.2 회원 전용 조회 / 변경

- `GET /api/v1/me/orders`

### 8.3 비회원 조회 유지

- 기존 주문/예약 토큰 조회 API를 유지한다.
- 휴대폰 SMS 소유 확인을 다시 통과하면 `POST /api/v1/guest-records/recovery`가 같은 비회원의 주문·예약에 새 단기 토큰을 발급하고 이전 토큰을 회수한다.
- 브라우저에 임시 저장한 복구 결과와 상세 이동 token은 복구를 수행한 회원 세대 또는 비회원 세대에만 귀속한다. 로그인·로그아웃이나 다른 탭의 계정 전환 뒤에는 이전 세대의 token을 자동 입력하거나 요청에 사용하지 않는다.
- 화면 표준 경로는 `/guest/orders`, `/guest/bookings`를 사용한다.

### 8.4 결제 기반 생성 API

- 주문과 예약, 8회권 구매는 `POST /api/v1/payments/prepare` → `POST /api/v1/payments/confirm`으로 생성한다.
- 로그인 사용자는 `HG_SESSION` 쿠키와 payload의 `userId`가 일치해야 한다.
- 비회원 주문/예약은 prepare 단계에서 payload의 `phone`, `verificationCode`, `name`을 검증하고 인증 코드를 소비한다. 암호화한 내부 payload에는 결제 주문 ID·전화번호·결제 문맥에 귀속된 서버 증명만 저장하고, confirm은 이 증명을 검증한다.
- 비회원 주문/예약은 prepare 단계에서 현재 정책 버전의 동의를 함께 검증하고 해당 결제 시도에 동의 이력을 저장한다.
- 8회권 구매는 회원 전용이며 `context=PASS` payload로 결제한다.

## 9. 운영 전환 기준

### 9.1 비회원 이력 가져오기(claim)

- 자동 비회원 -> 회원 병합 금지
- 로그인 후 휴대폰 인증을 통과한 회원만 직접 가져오기 가능
- 회원·비회원·인증 전화번호는 저장 전에 같은 숫자 형식으로 통일하므로 하이픈 유무와 관계없이 같은 번호로 취급한다.
- 가져오기 전에는 미리보기로 주문/예약 후보를 확인하고 일부만 선택할 수 있다.
- 가져오기 전에는 기존 비회원 토큰 조회를 유지한다.

### 9.2 기존 경로 유지

- 공개 비회원 진입점은 `/guest` 시작 화면을 사용한다.
- 비회원 조회 화면은 `/guest/orders`, `/guest/bookings` 표준 경로만 사용한다.
- `/orders/new` 직접 진입은 상품 상세에서 상품/수량을 미리 채워 들어오는 경로와 분리된 보조 경로로 유지한다. 사용자는 안내 문구를 본 뒤 명시적으로 계속해야 한다.
- 운영 모니터링은 `/api/v1/monitoring/client-events` 와 `[client-monitoring]` 로그를 기준으로 본다. 현재 지표는 `/guest` 시작 화면 유입, `/orders/new` 직접 계속, 비회원 -> 회원 전환 CTA, 이력 가져오기 모달 오픈, 이력 가져오기 완료다.
- 회원 경로를 안정화한 뒤 2~4주 동안 위 지표를 보고 비회원 보조 경로를 줄일지 다시 판단한다.
- 비회원 표준 경로 변경은 별도 배포 단위로 분리한다.

### 9.3 E2E 기준

- 비회원과 관리자 관련 기존 핵심 브라우저 시나리오 1~5를 유지하고 회원·이력 가져오기·8회권 시나리오 6~10을 운영한다.
- `P8-7`은 회원 8회권 구매, 회원 예약 생성, `/my/bookings/:id` 예약 상세, 변경/취소까지 포함한다
- `P8-8`은 비회원 주문·예약 생성 후 같은 번호의 회원이 `/my`에서 재인증과 선택 claim을 수행하는 흐름을 포함한다
- `P8-9`는 비회원 주문 성공 화면에서 회원가입 후 `/my` 비회원 이력 가져오기(claim) 모달 자동 진입을 포함한다
- `P8-10`은 8회권 예약의 취소 마감이 지난 경우 취소 확인창과 완료 알림에 크레딧 미복구 경고가 한국어로 표시되는지 검증한다.

## 10. 당시 범위 밖과 현재 반영 상태

- 장바구니: 현재 구현됨. 결제는 `POST /api/v1/payments/prepare`의 `ORDER`, `cartCheckout=true`로 시작하고 표준 confirm 경로에서 주문 생성과 결제 수량 차감을 함께 완료한다.
- 리뷰/별점: 현재 구현 범위다. 회원은 작성 가능한 완료 거래를 모아 보고 별점·본문·사진 후기를 관리한다. 공개 화면은 평균·별점 분포·필터·정렬, 검증된 거래·수정 표식, 공방 답글·도움돼요를 표시하며, 회원은 타인의 공개 후기를 신고할 수 있다. 관리자는 신고, 공방 답글, 숨김·재공개 감사 이력을 운영한다.
- Q&A: Product Q&A와 1:1 문의는 현재 구현됨. 공개 Product Q&A의 일반글 상세는 비밀번호 없이 조회하고 비밀글 상세만 비밀번호를 검증한다.
- 소셜 로그인: Google, Naver, Kakao 로그인을 지원하며, Spring Security OAuth2 Client가 만든 authorization request와 `state`를 백엔드 callback까지 Redis HTTP 세션에 임시 보관하고 1회 검증·소비한다. Naver 전용 회원은 별도 이메일 소유 확인 후 기준 이메일을 등록할 수 있다.
- 네이버페이와 카카오페이는 토스 경유 전용 결제창으로 제공하며 별도 PG 직접 연동은 사용하지 않는다. 스마트스토어는 관리자가 상품·옵션 ID를 매핑하고, 네이버 판매 수량을 내부 재고에 반영한 뒤 내부 최신 절대 재고를 네이버에 다시 맞추는 양방향 재고 동기화를 지원한다. 관리자는 스마트스토어 주문·클레임, 상품·고객 문의, 정산 대사와 회계 자료도 해피갤러리 운영 화면에서 처리한다.
- 쿠폰/적립금: 회원 상품 주문 범위로 현재 구현됨. 쿠폰은 한 장을 배송비 제외 상품액에 적용하고, 적립금은 배송·픽업 완료 순결제 상품액의 1%를 1년간 제공한다.
- 찜: 미구현.

상품·클래스 설명과 대표 이미지 관리, 공방 프로필, 로컬 미디어 업로드·공개·백업은 현재 구현 범위에 포함한다.
