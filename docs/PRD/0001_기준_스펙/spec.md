# 공방 온라인 주문·예약 서비스 기준 스펙

## 0. 문서 목적
- 제품이 반드시 지켜야 하는 요구사항을 한 곳에 정리한다.
- API 형식, 설계 배경, 운영 설정은 연결된 `ADR`과 보조 `PRD`로 분리해 관리한다.
- 테스트는 핵심 비즈니스 규칙과 운영 리스크를 검증하는 데 집중한다.

## 1. 프로젝트 개요
### 1.1 도메인
- 오프라인 공방(실매장)과 **온라인 쇼핑몰 재고를 공유**한다.
- 판매 대상:
    - 공예품(목공예, pop글씨, 뜨개질 등): 주로 **단일 작품(수량 1)**, 일부는 **예약 제작**
- 체험 대상:
    - 조향: **원데이 클래스만**
    - 기타 공예: **원데이 클래스 + 정규과정(월 8회권)**
- 체험 후 완성품은 가져갈 수 있으나 **향수/공예 완성품을 온라인에서 별도 판매하지는 않음**(체험 결과물).

### 1.2 핵심 목표
- 온라인/오프라인 충돌을 운영 정책(승인/거절/환불)로 흡수하면서도,
- 고객 경험(예약, 알림, 환불 규칙)을 일관되게 제공한다.
- 회원 인증은 이메일/비밀번호와 Google, Naver, Kakao 소셜 로그인을 함께 지원한다. 소셜로 처음 가입한 사용자를 포함해 회원은 마이페이지에서 SMS 소유 확인을 거쳐 휴대폰 번호를 등록하거나 변경하고, 기준 이메일이 없으면 메일함 소유 확인을 거쳐 이메일을 한 번 등록한다.
- 회원은 최근 10분 안에 현재 비밀번호 또는 이미 연결된 동일 소셜 계정으로 본인을 다시 확인한 세션에서만 Google·Naver·Kakao 계정을 연결하거나 해제하고 휴대폰을 최초 등록·변경하거나 기준 이메일을 최초 등록한다. 이메일 일치만으로 계정을 합치지 않고, 마지막 로그인 수단은 해제할 수 없다.
- 이메일 회원가입은 가입 전에 SMS 인증 코드를 발급받아 같은 전화번호와 코드로 소유권을 확인해야 하며, 성공한 회원은 `phoneVerified=true`로 저장한다.
- 회원은 현재 비밀번호로 로컬 비밀번호를 변경한다. 검증된 기준 이메일이 저장된 회원은 해당 이메일·검증된 휴대폰·SMS 코드로 분실 비밀번호를 재설정하며, Google·Kakao 소셜 전용 회원과 직접 이메일을 등록한 Naver 소셜 전용 회원도 이 경로에서 최초 로컬 비밀번호를 설정할 수 있다. 회원·관리자 비밀번호 입력은 BCrypt가 구분하는 UTF-8 72바이트 이하로 제한한다.
- 비밀번호 변경·재설정 성공 시 모든 회원 세션을 무효화하고 다시 로그인하게 한다.
- 회원 로그아웃은 서버가 세션 폐기를 완료한 뒤에 클라이언트 인증 상태를 제거한다. 요청 실패나 응답 유실 때는 현재 회원 상태를 유지하고 로그아웃 완료를 확인하지 못했음을 표시한다. 관리자는 공유 단말의 Bearer 토큰 잔존을 막기 위해 로그아웃 요청 결과와 무관하게 브라우저 토큰과 관리자 캐시를 즉시 제거하며, 서버 폐기 실패만 별도로 알린다.
- 전화번호가 없거나 인증되지 않은 회원은 연락처가 필요한 주문·예약·8회권 결제를 시작할 수 없다. 변경하려는 번호의 SMS 소유 확인을 다시 요구하고, 같은 번호를 두 회원이 공유하지 못하게 한다.
- 회원은 최근 본인 확인을 다시 거친 뒤 미종결 결제 시도·주문·주문 클레임·예약 취소 후속 작업·환불, 사용 가능한 8회권, 예약 적립금 또는 적립금 부채가 없을 때 탈퇴할 수 있다. 회원 행을 잠근 상태에서 세션 증명의 자격 버전을 다시 확인하고 결제 prepare와 탈퇴를 직렬화한다. 탈퇴 즉시 개인정보·비밀번호·소셜 연결을 제거한 뒤 모든 기존 세션을 무효화한다. 사용 가능한 미예약 적립금과 발급 쿠폰은 탈퇴 뒤 사용할 수 없지만 감사 이력은 회원 FK와 함께 보존한다.

## 2. 용어 정의
- POS: 오프라인 결제/재고 관리 시스템(본 프로젝트는 오프라인 시스템과 직접 연동 여부 미정, 매장 우선권 정책으로 흡수)
- SKU: 재고를 구분하는 단위 코드. 기성품은 상품 1건을 SKU 1개로 취급하고, 주문제작 상품은 선택형 옵션 조합마다 별도 SKU를 둔다.
- 슬롯(Slot): 체험 예약 시간 단위(시간 슬롯 방식)
- 예약금(Deposit): 체험 예약 시 결제하는 금액(`클래스 1인 가격 × 예약 인원 × 10%`)
- 잔금(Balance): 체험 당일 현장 결제 금액(시작 전 결제가 원칙이나 시스템 강제 없음)
- D-1: 체험 전날(리마인드 등 날짜 표현 기준)
- 취소 보상 마감: 체험일 **00:00, Asia/Seoul 기준**
- 이벤트(Event): 공지와 분리해 게시 기간, 홈 추천 여부, 대표 이미지와 관련 상품을 관리하는 프로모션 콘텐츠
- 쿠폰(Coupon): 회원에게 발급되어 상품 주문의 배송비를 제외한 상품 금액에 한 장 적용되는 할인 권리
- 적립금(Reward Point): `1P = 1원`으로 회원 상품 주문에 사용하는 만료 가능한 내부 결제 수단
- 후기(Review): 회원이 완료된 주문 품목 또는 완료된 클래스 예약을 근거로 남기는 1~5점 별점과 본문

## 3. 비즈니스 규칙(확정)
### 3.1 공예품 주문(온라인/오프라인 재고 공유)
- 주문 주체: **회원** 또는 **비회원(휴대폰 인증)**
  - 표준 생성 경로는 회원·비회원 모두 `/api/v1/payments/prepare` (`context=ORDER`) → `/api/v1/payments/confirm`이다. 회원/비회원 구분은 `HG_SESSION` 세션 유무로 결정한다.
  - 회원 결제 준비는 SMS로 확인한 전화번호가 등록된 회원만 허용한다.
  - 회원 주문은 추가 토큰 없이 세션 기반으로 조회한다.
  - 비회원 주문은 confirm 응답으로 받은 접근 토큰(`X-Access-Token` 헤더)으로 조회한다.
  - `orders` 레코드는 `user_id`, `guest_id` 중 정확히 하나만 가지며 DB `CHECK` 제약으로 강제한다.
- 회원은 장바구니에 여러 상품을 담아 `/api/v1/payments/prepare`의 `ORDER` payload에 `cartCheckout=true`를 지정해 한 번에 결제한다. 비회원은 이 기기의 로컬 장바구니에서 최신 공개 상품 정보로 상품명·옵션·단가·소계를 확인하고 항목별 수량을 수정하거나 삭제한다. 결제는 로그인 후 회원 장바구니로 병합한 뒤 진행한다. 추가·병합·수량 증가 시 같은 SKU의 전체 장바구니 수량이 현재 재고를 넘으면 `409 INVENTORY_NOT_ENOUGH`로 거절하되 감소·유지는 허용한다. 직접입력 문구가 달라 장바구니 행이 나뉘어도 같은 선택 조합은 하나의 SKU로 합산한다. 로그인 직전의 비회원 장바구니는 요청 UUID를 포함한 단일 병합 API로 옮기며, 응답 유실 후 같은 요청을 다시 보내도 한 번만 반영한다. 현재 웹 클라이언트는 장바구니 조회가 반환한 `cartVersion`을 `expectedCartVersion`으로 보내며, 서버는 같은 회원의 변경과 직렬화한 뒤 버전이 다르면 결제 준비를 `409 CART_SNAPSHOT_CHANGED`로 거절한다. 서버는 클라이언트가 보낸 항목 대신 일치한 장바구니의 구매 가능한 행 ID·수량·단가를 확정하고, confirm 성공 시 그 행의 결제 수량만 잠금 차감한다. 장바구니 검증은 재고 예약이 아니므로 prepare와 confirm은 각각 현재 재고를 다시 확인한다. prepare 뒤 삭제하고 다시 담은 새 행은 과거 결제로 제거하지 않는다.
- 회원 바로 주문·장바구니와 비회원 주문은 결제 prepare 전에 `SHIPPING` 또는 `PICKUP`을 반드시 선택한다. 배송이면 받는 사람·연락처·우편번호·기본/상세 주소를 함께 확정하고, 픽업이면 현재 단일 매장을 사용하므로 매장명을 자유 문자열로 받지 않는다. 배송 주문은 `app.order.shipping-fee`의 고정 배송비를 더하고 픽업은 0원이며, 공개 가격 정책 API로 결제 전에 같은 금액을 표시한다.
- 직접 주문과 장바구니 결제는 모두 `ACTIVE` 상품만 결제 대상으로 확정한다. 판매 중지 상품은 재고가 남아 있어도 prepare에서 거절하고, 현재 재고보다 큰 요청도 결제창을 열기 전에 거절한다. 동시 주문의 최종 재고 보장은 confirm의 잠금 차감에서 다시 확인한다.
- 상품은 이름·유형·카테고리·가격과 설명·대표 이미지·고정 사양·관리 방법·판매 상태를 가진다. 주문제작 상품은 1~180일의 예상 제작 기간과 고정 사양이 필수이고, 기성품에는 제작 기간을 설정하지 않는다. 주문제작 상품에는 관리자가 선택형 옵션 그룹과 직접입력형 옵션 그룹을 만들 수 있다. 선택형은 최대 3개, 직접입력형은 최대 5개이며 그룹명·옵션값은 25자 이하로 관리한다. 각 그룹은 필수 또는 선택으로 설정하고, 직접입력형은 안내 문구·최대 입력 길이·추가 금액을 가진다. 관리자는 표시 정보를 수정하고 판매 상태를 별도 전환하며, 동시에 먼저 읽은 상품을 수정한 요청은 낙관적 락으로 앞선 변경을 덮지 않고 409 충돌을 반환한다. 공개 목록과 상세는 `ACTIVE` 상품만 노출하며, 없거나 판매 중지된 상품 상세는 동일하게 404를 반환한다.
- 관리자가 올린 상품·클래스·이벤트 대표 이미지는 JPEG/PNG/WebP, 최대 5MiB만 허용한다. 서버는 MIME과 파일 시그니처를 확인해 UUID 파일명으로 영속 볼륨에 저장한다. 인증 없는 이미지 조회는 현재 공개 상품·클래스, 게시 상태이고 종료 전인 이벤트, 공개 후기에서 참조하는 파일만 `no-store`로 반환하고, 업로드 직후와 비활성·미게시 자산의 미리보기는 계정 기반 Bearer 관리자 경로로만 제공한다.
- 공방 프로필은 이름, 연락처, 주소, 영업시간, 지도 URL, 주차 안내와 사업자등록번호, 대표자명, 전자우편주소, 통신판매업 신고번호, 공방 소개, 카카오톡 ID, 네이버톡톡·네이버 블로그·인스타그램·스마트스토어 URL을 단일 운영 정보로 관리하고 공개 조회한다. 공지 제목은 200자, 본문은 16,000자 이하로 제한한다. 관리자 공지 편집은 본문과 최신 버전을 포함한 관리자 상세를 먼저 불러오며, 공지 수정·삭제와 공방 프로필 수정은 조회한 버전을 함께 제출해 다른 관리자가 먼저 바꾼 내용을 덮거나 지우지 않고 409 충돌을 반환한다. 충돌한 화면은 최신 서버 값과 버전을 다시 불러오되 작성 중인 초안은 보존한다. 관리자 공지 생성·수정·삭제 성공 뒤 공개 목록과 상세 캐시도 함께 무효화해 같은 탭에서 이전 공지를 재사용하지 않는다.

- 주문 항목에는 prepare 당시 상품명·유형·기본가·선택 조합 추가금·직접입력 옵션 추가금·최종 단가, 선택한 옵션명·값과 직접입력 문구, SKU, 고정 사양·관리 방법·예상 제작 기간과 품목별 쿠폰·적립금 배분을 저장한다. 주문에는 상품액·배송비·쿠폰 할인·적립금 사용·PG 결제액을 스냅샷으로 저장한다. 배송 출발 시 관리자가 지원 택배사를 선택하고 택배사 코드·표시명·운송장 번호를 함께 저장해 상품·옵션·혜택·배송 정책 변경 뒤에도 과거 주문 상세와 환불 원천을 재현한다. 연동이 켜져 있으면 출고 트랜잭션과 분리된 배치가 외부 배송조회 등록을 재시도하고, HMAC 서명이 확인된 웹훅이 현재 배송 상태와 진행 이력을 갱신한다. 택배사의 배송 완료는 주문 완료·적립·후기 요청을 자동 실행하지 않으며 관리자가 주문 배송 완료를 확정한다. 스냅샷 도입 전 기존 주문 항목은 `productType=null`인 구매조건 미기록 이력으로 유지하고 현재 상품 값으로 임의 보정하지 않는다.
- 주문 전액 환불은 prepare 당시 저장한 PG 결제액과 적립금 사용액을 각각 환불·복원한다. 사용 쿠폰은 전액 취소 시점에도 유효한 경우에만 다시 사용할 수 있게 복원한다. PG 결제액이 0원이면 외부 PG를 호출하지 않고 내부 환불 이력을 성공 처리한다.
- 매장 수령 마감이 지나면 기성품과 주문제작 주문 모두 자동 환불하지 않고 `PICKUP_FORFEITED`로 미수령 종료한다. 기성품은 매장에 남은 상품을 다시 판매할 수 있도록 재고만 복구하고, 주문제작 상품이 하나라도 포함된 주문은 재고도 복구하지 않는다. 관리자는 고객 응대 결과 예외 환불이 필요할 때만 미수령 종료 주문의 전액 환불을 요청할 수 있으며, 이때 재고는 다시 조정하지 않고 `PICKUP_EXPIRED`로 전이한다. 기존 `PICKUP_EXPIRED`는 이미 환불된 과거 이력으로 유지한다.
- 배송·픽업이 끝난 `DELIVERED`, `PICKED_UP`, `COMPLETED` 주문은 회원 세션 또는 비회원 접근 토큰으로 한 요청당 최대 100개 품목의 수량별 클레임을 접수한다. 하자·오배송·단순 변심·기타 사유와 환불·교환 요청을 저장하며, 거절되지 않은 기존 접수 수량을 제외해 주문 수량을 초과하지 못하게 한다.
- 관리자는 클레임을 거절하거나 환불·교환을 승인한다. 환불액은 접수 품목에 저장된 쿠폰 할인 뒤 고객 결제액 이내이며 주문 전체 수량을 한 번에 접수한 경우에만 배송비를 포함할 수 있다. 승인 고객 반환액은 품목별 결제액 비율로 원 단위 배분하고 PG 환불액과 적립금 복원액을 분리해 고정하며, 이미 지급한 1% 적립금은 환불된 적립 기준액에 맞춰 회수하고 부족분은 적립금 부채로 남긴다. 환불 요청은 클레임별 환불 이력으로 남겨 기존 비동기 PG 재시도·대사 경계를 사용하고 성공 시 클레임을 완료한다.
- 반품품이 다시 판매 가능할 때만 관리자가 재고 복구를 선택한다. 교환 승인은 복구 여부와 별개로 같은 품목·수량의 교환품 재고를 다시 차감하고, 교환 배송을 마친 관리자가 택배사·운송장과 처리자를 남겨 완료한다.
- 관리자 화면은 고객명 또는 정확한 휴대폰 번호로 주문·예약·8회권 이용 내역을 한 번에 확인하는 고객 통합 검색과 주문 커서 목록, 상태/기간/키워드 검색, 매출 요약 대시보드를 제공한다. 주문 검색 결과의 `운영` 액션은 주문 탭의 기존 운영 패널로 이동해 해당 주문을 강조하고 승인·거절·배송·픽업 등 현재 상태에 맞는 후속 처리를 이어가게 한다. 기본 `오늘 할 일` 화면에는 결제 대사·PG/스마트스토어 정산 불일치·환불·알림 실패, 승인 대기 주문, 주문 클레임, 확인이 필요한 스마트스토어 주문, 판매 중이지만 재고가 0인 기성품과 활성 주문제작 옵션 조합, 예약 취소 후속 작업, 당일 예약을 모은다. 주문 탭은 최신 스마트스토어 채널 주문의 상세·처리 기능과 확인 사유 필터를 제공하고, 품절 항목은 해당 상품·옵션 조합이 선택된 재고 조정 화면으로 바로 연결한다. Q&A 작업 영역은 상품을 먼저 고르지 않아도 전체 미답변 질문을 최신순 커서로 조회하고 스마트스토어 상품 문의도 별도 작업 목록에서 답변하며, 나머지 기능은 작업 영역별 탭에서 필요한 시점에만 조회한다.
- 고객·관리자 화면 문구는 `Slot`, `buffer`, `reconciliation`, `idempotency key`, `batch`, `revision` 같은 내부 모델·처리 방식의 이름을 그대로 노출하지 않는다. 고객 화면은 현재 상태와 다음 행동을, 관리자 화면의 버튼·상태는 실제 처리 효과와 행동 주체를 먼저 설명한다. 같은 상태라도 고객과 관리자의 다음 행동이 다르면 역할별 라벨을 사용하고, 미매핑 enum이나 외부 시스템 오류 원문 대신 안전한 한글 안내와 별도 기술 상세를 제공한다.
- 관리자 순매출은 주문의 쿠폰 적용 뒤 고객 결제액(PG+적립금), 예약금, 예약 잔금, 8회권 구매를 결제 시점에 더하고 도메인 환불의 고객 반환 총액이 `SUCCEEDED`가 된 시점에 차감한다. `REQUESTED`·`PROCESSING`·`RETRYABLE`·`RECONCILIATION_REQUIRED`·`FAILED` 환불과 도메인 생성 실패를 되돌리는 보상환불은 고객 매출 통계에서 차감하지 않는다.
- 상품별·기간별 주문 매출 요약은 주문 상품 분석 지표로 유지하고, 전체 현금흐름은 네 결제 원천을 합산하는 개요·매출 구성·일별 순매출 지표로 본다. 관리자 대시보드는 상품 주문 순위, 현재 주문 상태 분포, 기간별 클래스 슬롯 이용률도 같은 조회 기간 화면에서 제공한다.
- 결제·환불·슬롯처럼 사용자에게 보이는 업무 시각 `DATETIME`은 서울 현지시각으로 기록하고 KST 날짜 경계로 집계한다. DB 기본값으로 생성되는 `created_at`만 UTC 경계를 사용한다. 클라이언트는 offset 없는 업무 시각을 `Asia/Seoul`로 해석하고, `Z` 또는 offset이 포함된 시각은 해당 절대 시각을 그대로 사용한다.

### 3.1.1 이벤트·쿠폰·적립금
- 이벤트는 공지와 분리된 aggregate로 관리한다. 공개 목록·상세는 게시 상태이고 종료 시각에 도달하지 않은 이벤트를 반환하므로 예정 이벤트도 포함하며, 홈은 그중 현재 진행 중인 추천 이벤트를 우선 노출한다. 열린 상세는 종료 경계 직후 404 화면으로 전환하고 반복 조회를 멈춘다. 관리자는 제목, 요약, 본문, 대표 이미지, 시작·종료 시각, 게시·추천 여부, 관련 상품과 선택적인 쿠폰 한 개를 CRUD하고 버전 충돌을 409로 처리한다. 이벤트 상세의 비회원은 로그인 후 같은 이벤트로 돌아오며, 회원은 연결된 쿠폰이 현재 공개 발급 가능하면 기존 회원당 한 번 발급 흐름으로 바로 받는다.
- 쿠폰은 정의와 회원 발급분을 분리한다. 관리자는 정액 또는 정률 할인, 최소 상품 주문액, 정률 최대 할인액, 발급·사용 기간, 활성·공개 발급 여부를 관리하고 삭제는 발급 이력을 보존하는 비활성화로 처리한다. 한 장이라도 발급된 정의의 이름·할인 조건·유효기간은 소급 변경하지 못하고 활성·공개 발급 플래그만 바꾼다. 회원은 현재 공개 발급 가능한 쿠폰을 최근 정의 기준 최대 100개까지 조회해 정의별 한 번 발급받고 자기 쿠폰 상태를 조회하며, 비활성화 뒤 미사용 발급분은 조회 시 취소 상태로 정리한다.
- 쿠폰은 회원 `ORDER`에 한 장만 적용하며 배송비에는 적용하지 않는다. 결제 prepare는 발급 쿠폰 행을 배타 잠그고 쿠폰 정의 행을 공유 잠금 조회한 뒤 회원·활성·유효기간·최소 상품액을 최신 상태로 검증해 할인액을 고정하고 결제 시도에 예약한다. 관리자 비활성화와 결제 prepare는 같은 정의 행 잠금으로 직렬화하되, 서로 다른 회원의 같은 정의 결제 견적은 병렬로 허용한다. 정률 할인은 원 미만을 버리며 계산 결과가 1원 미만이면 해당 주문에 적용할 수 없다. confirm의 주문 생성과 같은 트랜잭션에서 사용 확정하고, 만료·미승인 등 안전한 결제 종결에서는 예약을 해제한다.
- 적립금은 회원 `ORDER`에만 사용하며 쿠폰 할인 뒤 상품 금액을 넘을 수 없다. 만료가 가까운 적립 단위부터 사용하고 결제 prepare에서 결제 시도에 예약한 뒤 confirm 주문 생성 시 사용 확정한다. 예약 해제 시 이미 만료된 단위는 반환하지 않는다.
- 회원은 상품 상세 바로구매·장바구니·주문서에서 같은 쿠폰·적립금 입력을 사용한다. 옵션별 단가와 수량의 상품 합계, 쿠폰 할인, 적립금 사용, 배송비, 최종 결제 예정 금액을 구분한다. 수량·옵션 변경으로 사용 한도를 넘은 적립금은 새 한도에 맞추고, 적용 조건을 충족하지 못하는 쿠폰은 선택을 해제한다. 혜택은 배송비를 차감하지 않으며 전액 할인된 매장 수령 주문은 공통 0원 결제 확정 화면으로 연결한다.
- 배송 완료 또는 픽업 완료 시 `상품 금액 - 쿠폰 할인 - 사용 적립금`의 1%를 원 단위 내림해 적립한다. 적립 단위는 지급 시각부터 1년간 유효하다. 만료 뒤 환불로 복원되는 사용 적립금은 복원 시점부터 최소 30일을 보장한다.
- 적립금 계정은 사용 가능·예약·부채 잔액을, 원장은 적립·예약·해제·사용·복원·회수·만료 후 잔액을 보존한다. 환불로 사용 적립금을 복원할 때는 원래 적립 lot의 주문 출처와 만료 시각을 보존하고, 이미 만료된 경우에만 복원 시점부터 최소 30일을 부여한다. 환불 뒤 회수해야 할 지급 적립금이 이미 사용됐거나 다른 결제에 예약됐다면 음수 잔액 대신 부채로 기록하고 이후 적립·복원·예약 해제 반환액으로 먼저 상환한다. 예약 해제 반환은 원래 만료가 가까운 배분부터 부채에 상계해 장기 유효 단위를 우선 보존하고, 일부 배분이 만료됐으면 해제와 만료가 서로 다른 잔액 스냅샷을 남긴다. 복원·회수의 같은 멱등 키 동시 요청은 한 번만 반영하고 모두 성공으로 수렴한다.
- 환불 화면은 고객 반환액을 PG 환불·사용 적립금 복원·지급 적립금 회수와 쿠폰 사용 상태 정리로 구분한다. 쿠폰 후처리는 완료 시점의 유효기간에 따라 재사용 가능 또는 만료로 끝날 수 있으므로 상태 응답 없이 재사용 가능 복원을 단정하지 않는다.
- 비회원 주문, 예약, 8회권에는 이번 쿠폰·적립금 정책을 적용하지 않는다.

### 3.2 예약 제작 주문(공예품)
- 회원 장바구니도 재고가 줄거나 판매 옵션이 바뀌어도 수량 감소·삭제는 허용한다. 추가·증가의 재고·판매 옵션 검증과 결제 시 최종 확인은 유지한다.
- 관리자 옵션 표시 순서가 바뀌어도 같은 각인은 같은 장바구니 항목으로 식별한다. 기존에 나뉜 중복 항목은 진행 중 결제의 ID 참조와 수량을 보존하며 이후 추가분은 가장 오래된 항목에 합산한다.
- 상품 상세의 선택 행 가격·옵션명·합계는 현재 상품 응답에서 계산하며 비회원 장바구니·주문서도 같은 계산을 사용한다. 재조회 뒤 가격·옵션 표시가 달라지면 고객에게 안내하고 선택 조건이 유효하지 않으면 삭제 후 재선택하도록 한다. 이미 선택한 모든 옵션이 삭제돼도 기본 조합으로 자동 주문하지 않는다.
- 직접입력 문구에 구분문자가 있어도 서로 다른 입력 구성을 같은 장바구니 항목으로 합치지 않는다. 비회원 장바구니의 추가·수량 증가도 같은 상품·SKU의 기존 수량까지 합산해 현재 재고와 99개 한도를 적용한다. 재고 감소로 초과된 항목은 수량 조정을 안내하고 감소·삭제를 허용한다.
- 여러 옵션의 장바구니 담기는 전부 반영되거나 전부 실패한다. 회원은 기존 다건 병합 API의 멱등키를 재시도에 유지하고, 비회원은 단일 잠금 안에서 최신 로컬 수량과 공개 재고를 확인한 뒤 한 번만 저장한다.
- 비회원 주문서는 상품 상세에서 넘겨받은 옵션 조합 ID와 직접입력 값으로 옵션명·선택값·각인 문구·직접입력 추가금을 품목별로 표시한다. 입력하지 않은 선택 옵션은 생략하고 텍스트는 HTML로 해석하지 않는다. 고객 장바구니·주문 상세도 같은 표시 형식을 사용하며, 완료 주문은 현재 상품 정보가 아니라 저장된 구매 당시 옵션을 표시한다.
- 상품 상세의 선택 수량은 직접입력 문구가 달라도 동일 `productVariantId`별로 합산한다. 옵션 추가·수량 변경·구매 가능 여부는 현재 상품 응답의 조합 재고와 조합별 99개 한도를 적용한다. 문구별 행을 삭제하면 해당 조합의 추가 가능 수량을 복원하고, 다른 조합의 선택 수량에는 영향을 주지 않는다. 선택 행에는 재고 사본을 저장하지 않으며 서버의 기존 prepare 재검증은 유지한다.
- 주문제작 상품 상세·장바구니·결제 화면은 고정 사양, 관리 방법, 예상 제작 기간, 필수·선택 옵션과 조합별 최종 가격·재고를 결제 전에 표시한다. 한 상품에서 서로 다른 옵션 조합이나 직접입력 문구를 여러 품목으로 함께 주문할 수 있다. prepare는 현재 `ACTIVE` 상품의 옵션 구성과 SKU를 다시 확인해 가격·재고·구매조건을 서버 확정 payload에 저장하고 confirm은 이 스냅샷으로 주문 항목을 만든다. V97 이전 구형 prepare는 상품 유형과 주문제작 동의가 모두 없을 때만 기성품으로 호환하고, 주문제작 동의가 남아 있으나 구매조건 스냅샷이 없으면 확정하지 않고 새로 준비하도록 안내한다.
- 구매조건 도입 시 기존 주문제작 상품은 설명을 임시 사양으로 옮기고 기본 제작 기간을 설정하되 판매를 중지한다. 운영자가 실제 사양과 기간을 확인한 뒤에만 다시 활성화한다.
- 주문제작 상품이 하나라도 포함되면 결제 전에 청약철회 제한 가능성과 법령상 권리 예외를 별도 문구로 표시하고 필수 체크 동의를 받는다. 클라이언트는 조회한 문구 버전과 동의 여부를 보내며 서버는 현재 버전과 일치할 때만 문구 버전·전문·동의 시각을 prepare payload와 최종 주문에 스냅샷으로 저장한다.
- 동의 기록이 없는 주문은 관리자가 승인해도 `IN_PRODUCTION`으로 전이할 수 없다. 하자·오배송 등 법령상 권리와 실제 청약철회 가능 여부는 저장한 동의만으로 일률 제한하지 않는다.
- 결제 후 승인 즉시 **제작 시작**
- 제작 시작 이후에는 고객 일반 취소와 관리자 거절 환불을 허용하지 않는다.
- 예상 출고일(배송 예정일)은 관리자 화면에서 설정하고 고객에게 표시
- 예상 출고일 설정·갱신과 제작 중 주문 처리 지연 제안은 주문 처리 이력으로 남긴다. 행위자는 Bearer 세션이면 관리자 ID, 로컬 API key면 `null`이며, 예상 출고일 이력에는 변경 전·후 날짜를 기록한다.
- 관리자가 제작 중 주문의 처리 지연을 제안하면 `DELAY_CONSENT_PENDING`으로 전이하고 회원·비회원 주문 상세에서 고객 응답을 받는다.
- 고객이 수락하면 `DELAY_ACCEPTED`, 거절하면 `DELAY_REJECTED_CANCELED`로 전이하고 전액 환불 + 재고 복구를 수행한다.
- 수락 후 관리자가 `/api/v1/admin/orders/{id}/resume-after-delay`로 처리를 재개하면 주문제작 주문은 `IN_PRODUCTION`으로 돌아간다.
- `DELAY_ACCEPTED` 전이 후에는 동의가 확정된 상태로 보아 지연 거절 취소를 허용하지 않는다.

### 3.3 픽업(기존 재고)
- 택배/픽업 모두 제공
- 픽업 규칙(기존 재고):
    - 승인 후 픽업 준비
    - 픽업 준비 시 마감 시각은 서버 `Clock` 기준 현재보다 이후여야 한다.
    - 매장 **마감 2시간 전 알림**
    - 마감까지 미수령 시 **자동 결제 취소(환불) + 재고 복구**
- 픽업 규칙(예약 제작):
    - 제작 시작 이후 일반 취소/미수령 자동환불 대상 아님
    - 마감까지 미수령하면 `PICKUP_FORFEITED`로 종료하고 이력을 남기되, 환불 요청과 재고 복구는 수행하지 않음

### 3.4 상품 Q&A / 1:1 문의
- Q&A와 1:1 문의의 제목은 200자, 본문과 관리자 답변은 각각 16,000자 이하로 제한한다. API 입력 검증과 도메인 저장 경계가 같은 상한을 적용해 DB 저장 단계의 길이 오류를 사용자 입력 오류로 바꾼다.
- 상품 상세에는 **작성은 회원 전용인 Product Q&A** 를 제공한다.
  - 작성 주체: 회원
  - 공개 목록은 작성자 이름을 마스킹해 노출한다.
  - 일반글(`secret=false`) 상세는 비밀번호 없이 공개 조회한다.
  - 비밀글(`secret=true`)은 공개 목록에서 제목을 숨기고 공개 상세 조회를 거절한다.
  - 로그인한 작성자 본인과 관리자는 비밀번호 공유 없이 회원·관리자 소유권 경계에서 비밀글 상세를 조회한다.
    회원 상세는 URL의 상품, Q&A와 현재 회원 ID가 모두 일치해야 한다.
  - 관리자 답변은 1회만 등록한다. 이미 답변된 글의 재답변은 `409 CONFLICT`로 거절하고 기존 답변과 알림 outbox를 변경하지 않는다.
  - 관리자 답변 성공 뒤 같은 상품의 공개·회원 Q&A 목록과 상세 캐시를 함께 무효화해, 같은 SPA 세션에서도 답변 상태와 내용이 즉시 다시 조회되게 한다.
  - 관리자 Q&A 화면은 전체 미답변 질문을 `(createdAt, id)` 최신순 커서로 먼저 보여주고, 필요하면 상품별 전체 목록으로 전환한다.
- 상단 메뉴에는 로그인 여부와 관계없이 **1:1 문의** 진입점을 표시한다. 비회원이 선택하면 로그인 후 `/my/inquiries`로 돌아오며, 문의 작성·조회는 회원에게만 제공한다.
  - 작성/조회 주체: 회원
  - 본인 문의만 조회 가능하다.
  - 관리자는 전체 문의 목록/상세를 조회하고 답변할 수 있다.
  - 이미 답변된 문의의 재답변은 `409 CONFLICT`로 거절하고 기존 답변과 알림 outbox를 변경하지 않는다.
  - 관리자 답변과 회원 알림 outbox 요청은 같은 트랜잭션으로 저장한다. 커밋 뒤 `INQUIRY_ANSWERED` 또는 `PRODUCT_QNA_ANSWERED` 알림을 보내며 같은 게시글에는 한 번만 발송 요청한다.

### 3.5 상품·클래스 후기
- 후기 작성은 회원 전용이다. 요청의 회원 ID를 신뢰하지 않고 `HG_SESSION`의 현재 회원을 사용한다.
- 상품 후기는 현재 회원이 소유한 주문 품목의 주문이 `DELIVERED`, `PICKED_UP`, `COMPLETED` 중 하나일 때만 작성한다.
- 클래스 후기는 현재 회원이 소유한 예약이 `COMPLETED`일 때만 작성한다. `BOOKED`, `CANCELED`, `NO_SHOW` 예약은 작성할 수 없다.
- 주문 품목 또는 예약 원천당 활성 후기 한 건만 저장한다. 사전 조회와 별개로 DB `UNIQUE` 제약이 동시 중복 작성을 `409 REVIEW_ALREADY_EXISTS`로 막는다.
- 별점은 1~5의 정수이고 본문은 공백이 아닌 16,000자 이하로 제한한다. API Bean Validation과 도메인 저장 경계가 같은 규칙을 적용한다.
- 작성자는 본인 후기를 수정하거나 삭제할 수 있다. 수정은 화면이 읽은 `expectedContentRevision`을 비교하고 값이 바뀌었으면 `409 REVIEW_CONTENT_CHANGED`로 거절해 다른 탭의 최신 본문을 덮어쓰지 않는다. 삭제는 사용자 화면에서 즉시 사라지되 본문·별점·답글·현재 숨김 메타데이터를 지운 tombstone으로 남긴다. 숨김 이력이 없는 후기는 삭제 후 재작성할 수 있고 신고·운영 조치·판단 증거가 없으면 30일 뒤 개인정보 보존 배치가 tombstone도 파기한다. 한 번이라도 숨겨진 후기는 재공개 후에 삭제해도 같은 원천으로 재작성할 수 없으며, 재작성 차단용 최소 회원·원천 식별자는 조치 우회 방지 목적 동안 유지한다.
- 완료 거래 중 현재 작성 가능한 항목을 내 후기 작성 기회에서 보여 준다. 표시 시각은 주문 생성일이 아니라 실제 배송·픽업·수강 완료 시각을 사용한다. 주문 배송·픽업 완료, 클래스 수강 완료와 완료된 비회원 이력 가져오기 시 후기 요청 알림을 거래 aggregate당 한 번 저장한다.
- 공개 목록은 `PUBLISHED`이고 삭제되지 않은 후기만 반환한다. 최신순·별점 높은순·낮은순과 1~5점 필터를 제공하고, 각 정렬 키를 포함한 opaque cursor를 사용한다. 전체 공개 후기의 수·평균·별점별 분포와 현재 필터 결과 수를 구분한다.
- 공개 후기는 실제 거래 표식, 본문 수정 표식, 공방 공식 답글, 최대 5장의 사진과 도움돼요 수를 보여 준다. 회원 후기 사진은 JPEG/PNG와 5MiB 이하만 받고, 실제 디코딩 형식과 픽셀 크기를 검증하고 EXIF 방향을 적용한 뒤 메타데이터 없는 파일로 재인코딩한다. 동시 디코딩 상한을 넘으면 `429`로 빠르게 거절한다. 로그인 회원의 도움돼요·신고 여부와 본인 후기 여부는 공개 응답에 섞지 않고 회원 API로 분리한다.
- 후기 작성·수정·공식 답글 폼을 열면 첫 입력으로 키보드 포커스를 옮긴다. 취소하거나 저장해 폼이 닫힌 뒤 같은 트리거가 다시 표시되면 그 버튼으로 포커스를 복구한다. 불러오지 못한 공개 사진은 깨진 링크 대신 대체 상태를 보여 주고, 기존 사진 삭제는 44px 이상 터치 영역과 확인 절차를 거친다. 관리자 신고·운영 이력의 긴 식별자와 URL은 모바일 폭 안에서 줄바꿈한다.
- 본문·평점·사진 묶음은 생성 시 1부터 시작하는 `contentRevision`을 가진다. 본문·평점 수정과 사진 추가·삭제 때만 증가하고 상태·답글·도움돼요·신고에는 증가하지 않는다.
- 관리자는 계정 기반 Bearer 세션으로 후기를 `HIDDEN` 또는 `PUBLISHED`로 전환한다. 숨김은 사유가 필수이며, 관리자가 확인한 `expectedContentRevision`과 현재 값이 다르면 `409 REVIEW_CONTENT_CHANGED`로 최신 내용을 다시 검토하게 한다. 조회한 JPA `version`을 `expectedVersion`으로 함께 비교해 다른 관리자의 상태 왕복 전환과 답글 덮어쓰기·삭제를 막는다. `contentRevision`은 콘텐츠 의미 변경, JPA `version`은 후기 행의 모든 쓰기 충돌을 담당한다. 실제 상태 전환마다 이전·신규 상태·사유·관리자·시각과 당시 별점·본문·사진의 불변 증거를 추가한다.
- 숨김 후기는 작성자와 관리자에게는 상태와 사유를 포함해 남지만 공개 목록·평균·분포·후기 수에서는 제외한다. 숨김·재공개 실제 전환과 최초 공식 답글은 작성자에게 알림한다.
- 회원은 공개되고 삭제되지 않은 타인 후기를 원천당 한 번 신고하거나 도움돼요로 표시할 수 있다. 회원 반응 조회는 `ownedByMe`, `canInteract`를 함께 반환해 자기 후기 버튼을 사전에 비활성화한다. 신고 수만으로 자동 숨김하지 않고 관리자가 `ACCEPTED` 또는 `REJECTED`로 판단하며, 신고 목록은 최소 요약만 반환하고 신고자·상세·전체 증거는 Bearer 관리자 단건 조회에서만 제공한다. 신고 화면에서 현재 후기 단건을 확인하고 별도 숨김 조치를 수행할 수 있다.
- 미결 신고의 증거는 결정 전까지 보존한다. 종결 신고, 운영 조치와 해당 별점·본문·사진 증거는 소비자 불만·분쟁처리 기록 기준에 맞춰 3년 보존한 뒤 개인정보 보존 배치에서 삭제한다. DB는 신고·운영 조치·증거가 남은 후기 부모 삭제를 `RESTRICT`로 거절한다. 증거 전용 또는 숨김·삭제 후기에서만 쓰는 사진은 공개 URL에서 차단하고 `no-store` Bearer 관리자 경로로만 제공하며, 보존 만료 커밋 후 다른 참조가 없는 물리 파일도 즉시 재검증·파기한다.

## 4. 체험(예약) 규칙(확정)
### 4.1 슬롯/정원
- 예약 주체: **회원** 또는 **비회원(휴대폰 인증)**
  - 회원 결제 준비와 8회권 사용 예약은 SMS로 확인한 전화번호가 등록된 회원만 허용한다.
  - 회원·비회원 모두 `/api/v1/payments/prepare` (`context=BOOKING`) → `/api/v1/payments/confirm`으로 결제·생성한다. 회원/비회원 구분은 `HG_SESSION` 세션 유무로 결정한다.
  - 회원 8회권 사용 예약은 `payload.passId`를 채워 prepare 단계에서 `amount=0`을 받고, PG 호출 없이 confirm을 직접 호출한다.
  - 회원 예약은 추가 토큰 없이 세션 기반으로 조회/변경/취소한다.
  - 비회원 예약은 confirm 응답으로 받은 접근 토큰(`X-Access-Token` 헤더)으로 조회/변경/취소한다.
  - `bookings` 레코드는 `user_id`, `guest_id` 중 정확히 하나만 가지며 DB `CHECK` 제약으로 강제한다.
  - 비회원이 회원가입 후 기존 이력 가져오기(claim)로 예약을 이전하면 `bookings.user_id`를 설정하고 `guest_id`를 비운다.
- 관리자 운영(예약 목록, 리마인더 배치)은 비회원, 회원, 이전 완료 예약을 모두 포함한다.
- 일반 예약은 한 건에 1명부터 선택한 슬롯의 남은 정원까지 `participantCount`를 받으며 슬롯 `booked_count`, 예약금과 잔금을 같은 인원수만큼 반영한다. 8회권은 한 예약에 크레딧 1회를 쓰는 정책이므로 `participantCount=1`만 허용한다.
- 운영자는 고객 결제 흐름을 거치지 않고 전화·네이버톡톡·카카오톡·방문 접수 예약을 등록할 수 있다. 이름·표준화 휴대폰·슬롯·인원·접수 경로·예약금 입금 여부만 받고 금액은 현재 클래스 1인 가격과 인원으로 서버가 계산한다. 입금 전이면 예약금은 0원이고 전체 금액을 현장 잔금으로 남긴다.
- 관리자는 날짜별 예약 목록 외에 상태/기간/키워드 검색으로 운영 대상을 찾을 수 있다. 검색 결과의 `운영` 액션은 예약 탭의 기존 날짜별 운영 패널로 이동해 대상 예약을 강조하고 현재 상태에 맞는 후속 처리를 이어가게 한다.
- 고객 예약 화면은 선택한 클래스의 향후 14일 예약 가능 슬롯을 한 번에 조회해 예약 가능한 날짜부터 탐색할 수 있다. 조회 범위는 1~30일로 제한한다.
- 예약은 **시간 슬롯 방식**
- 관리자는 운영 화면에서 회차당 정원·설명·대표 이미지·준비물·대상 안내·8회권 사용 가능 여부를 포함한 클래스를 등록한다. 비활성 클래스는 공개 목록과 신규 예약 대상에서 제외하며, 공개 상세는 없는 클래스와 동일하게 404를 반환한다.
- 예약 캘린더는 모든 날짜를 기본 운영시간(초기값 10:00~19:00)에 열고 예약 시작 간격(초기값 30분)마다 클래스별 회차를 계산한다. 관리자는 기본 운영시간·간격·법정 공휴일 기본 차단 여부를 바꾸고, 날짜를 예외적으로 열거나 종일 닫거나 특정 시간만 닫는다.
- 관리자 예약 목록·예약 운영 캘린더·예약이 있거나 중지한 회차 관리는 공통 30분 시간축으로 표시한다. 30분은 화면 눈금이며 예약 시작 간격 설정과는 독립적이므로, 10분·15분 등 다른 간격으로 생성된 회차도 실제 시작·종료 위치에 표시한다. 표는 예약 취소·잔금·정원 같은 상세 작업을 위해 시간표 아래에 유지한다.
- 법정·대체공휴일은 공공데이터포털의 한국천문연구원 특일 정보를 연도별 스냅샷으로 저장해 우선 사용한다. 매월 현재 연도와 다음 연도를 정상 응답일 때만 교체하고, 조회 실패 때는 마지막 정상 스냅샷을 유지한다. 해당 연도 스냅샷이 없을 때만 한국천문연구원 기준 음양력 변환과 현행 `공휴일에 관한 법률`·`관공서의 공휴일에 관한 규정` 계산으로 대체한다. 정기 일요일은 공휴일 토글로 닫지 않으며, 공방 개별 휴무는 날짜 차단으로 등록한다. 기본 차단된 공휴일도 날짜를 `OPEN`으로 지정하면 운영할 수 있다.
- 공개 슬롯 조회는 캘린더 규칙에 맞는 실제 `slots` 행을 클래스 잠금 안에서 필요한 범위만 자동 생성한다. `Slot`은 결제·변경·취소의 영속 식별자와 정원 잠금 단위로 유지하며, 별도 단건·일괄 생성 API는 제공하지 않는다.
- 회차 정원은 클래스 등록 시 1명 이상으로 설정한다. 기존 클래스는 8명으로 이관하고, 자동 생성 슬롯은 해당 클래스의 정원을 복사한다.
- `slots.booked_count`는 예약 건수가 아니라 현재 `BOOKED` 예약의 총 인원 점유다. 예약 생성·변경·취소는 해당 예약의 `participantCount`만큼 한 번에 점유·반납한다.
- 클래스별 소요 시간은 다를 수 있음
- 자동 회차의 종료 시각은 서버가 `start_at + classes.duration_min`으로 계산한다.
- 버퍼(정리/준비):
    - 각 회차는 수업 시작부터 종료 후 `buffer_min`까지 점유하며, 두 회차의 점유 구간이 겹치면 함께 예약할 수 없다.
    - 단위는 **30분** (`classes.buffer_min = 30`)
    - 슬롯의 첫 예약이 잡히면 앞뒤 어느 방향이든 수업·정리 구간이 겹치는 슬롯을 자동 차단한다.
    - 원인 슬롯의 마지막 예약이 취소·변경되어 `booked_count=0`이 되면 해당 버퍼 차단을 자동 해제한다.
    - 여러 원인 슬롯의 버퍼가 겹치면 모든 원인 슬롯의 예약이 사라진 뒤에만 다시 활성화한다.
    - 관리자가 비활성화한 슬롯은 버퍼 차단이 해제되어도 비활성 상태를 유지한다.
    - 예약이 잡힌 뒤 버퍼 범위에 새 슬롯을 생성해도 생성 시점부터 차단한다.
    - 규칙 적용 전에 이미 버퍼가 충돌한 예약은 자동 취소하지 않는다. 다만 이후 앞 슬롯을 포함해 충돌을 새로 만들거나 늘리는 예약은 잠금 후 거절한다.
    - **충돌 범위**: 각 슬롯의 `[start_at, end_at + buffer_min)` 구간이 서로 겹치면 충돌한다. 종료+버퍼 시각과 다른 슬롯 시작 시각이 같으면 충돌하지 않는다.
- **동시성**: 같은 클래스의 자동 회차 구체화·예약·반납은 `classes` 행을 먼저 잠그고, 예약 확정은 원인 및 충돌 `slots` 행을 현재 읽기로 잠근 뒤 `booked_count`를 증가한다 (ADR-0003).
- 공개 예약 가능 슬롯은 현재 시각보다 뒤에 시작하는 슬롯만 노출한다. 예약 확정의 사전 확인과 클래스 ID 수집은 슬롯 scheduling projection을 사용하고, 클래스 행을 잠근 뒤 원인·충돌 슬롯 ID를 현재 읽기로 잠가 관리 중인 Slot만 분리한 다음 최신 상태를 한 번에 다시 적재한다. 슬롯 시작 시각부터는 예약할 수 없고, 잠금 전에 관리자가 비활성화한 클래스나 슬롯의 오래된 상태로 예약을 확정하지 않는다.
- 동일 예약자는 한 슬롯에 `BOOKED` 예약을 한 건만 가질 수 있다. 취소·완료·결석 이력은 중복 판단에서 제외하며, 취소 후에는 같은 슬롯을 다시 예약할 수 있다.
- 고객 예약 화면은 활성·미래 회차의 만석 여부도 함께 보여 준다. 만석 회차에는 휴대폰 소유권을 확인한 회원·비회원이 1회성 빈자리 알림을 신청·취소할 수 있다. 회원 신청 상태는 서버에서 다시 조회하며 클래스명과 일시를 마이페이지에 표시해, 운영·캘린더·버퍼 사유로 회차가 예약 화면에서 사라져도 신청을 취소할 수 있게 한다. 비회원 취소 토큰은 현재 고객 세션 소유권과 함께 탭 세션에 보관해 새로고침 뒤에도 취소할 수 있게 한다. 로그인·로그아웃·계정 전환 뒤에는 이전 고객 세션의 비회원 토큰을 사용하지 않는다. 전체취소·부분취소·예약 변경으로 만석이던 회차에 실제 예약 가능한 자리가 생기면 대기 신청을 모두 종결하고 알림 outbox를 한 번씩 저장한다. 알림은 좌석 선점·자동 예약·자동 결제를 하지 않으며, 고객이 알림을 받은 뒤 선착순으로 예약한다. 운영·캘린더·버퍼 사유로 닫힌 동안에는 알리지 않고 다시 열린 시점에 자리가 있으면 알린다. 시작한 회차의 미발송 신청은 정리하고 발송·취소 신청은 30일만 보존한다.
- 슬롯의 실제 활성 상태는 관리자 활성 상태, 캘린더 활성 상태와 버퍼 차단 수를 함께 반영한다.
- 운영자는 잘못 비활성화한 슬롯을 다시 활성화할 수 있다. 이때 관리자 활성 상태만 복구하며 다른 예약으로 생긴 버퍼 차단은 유지한다.
- 운영자 사정으로 한 회차를 폐강할 때는 먼저 해당 슬롯을 관리자 비활성화해 신규 예약을 막은 뒤, 그 슬롯의 `BOOKED` 예약을 일괄 취소한다. 활성 슬롯은 일괄 취소할 수 없다.

### 4.2 예약금/환불/변경
- 예약금: `클래스 1인 가격 × 예약 인원` 합계의 **10%**
- 클래스 가격은 최소 10원이며, 고객이 PG로 결제하는 일반 예약금은 항상 1원 이상이다. 0원 결제는 유효한 8회권 예약의 내부 승인에만 사용한다.
- 예약 확정: 슬롯이 비어있으면 **자동 확정**
- 환불 규칙(예약금):
    - 체험일 **00:00 이후 환불 불가**. 잔금 미결제 `BOOKED` 예약은 당일에도 취소할 수 있지만 예약금은 환불하지 않고, 8회권 예약은 사용한 1회를 복구하지 않는다.
    - 회원·비회원 예약 상세의 취소 확인창은 서버가 계산한 환불·크레딧 복구 마감 시각과 예상 반환 내용을 먼저 보여준다. 환불 가능 예약은 예약금 환불 요청 금액 또는 8회권 복구를, 마감 후 예약은 환불·복구 없이 예약만 취소된다는 사실을 최종 버튼에도 구분해 표시한다.
- 여러 명이 함께 예약한 일반 PG 예약금 예약은 체험일 00:00 전까지 회원·비회원 고객이 1명 이상을 남기는 인원 부분취소를 할 수 있다. 현재 예약금과 잔금은 변경 전 인원 대비 남은 인원 비율로 정수 내림해 다시 계산하고, 줄어든 예약금만 PG 부분환불로 요청하며 줄인 인원만큼 슬롯 정원을 반납한다. 예약은 `BOOKED`를 유지하고 변경마다 별도 환불·`PARTICIPANTS_REDUCED` 이력을 남긴다. 전원 취소는 전체 예약 취소를 사용하고, 잔금 결제 완료·8회권·오프라인 예약금 예약의 고객 부분취소는 허용하지 않는다.
- 운영자 사정 취소는 고객 취소 마감과 무관하게 예약금 전액 환불 또는 유효한 8회권 크레딧 복구를 시작한다. PG로 결제한 예약금만 자동 환불하며, 전화·메신저·방문 접수에서 받은 오프라인 예약금은 금액이 포함된 `MANUAL_COMPENSATION` 후속 작업으로 남긴다. 이미 받은 현장 잔금은 `BALANCE_SETTLEMENT`, 만료되어 복구할 수 없는 8회권은 금액 0원의 `MANUAL_COMPENSATION` 작업으로 남겨 운영자가 수동 정산한다.
- 개별·회차 일괄 운영자 취소는 예약 상태, 슬롯 정원·버퍼, 취소 이력, 보상 요청, 취소 알림과 필요한 후속 작업을 함께 처리한다. 후속 작업은 예약·유형별 한 건만 만들고 `PENDING` 목록에서 처리 관리자와 완료 시각을 기록하며, 완료 요청 재호출은 이미 완료된 결과를 그대로 반환한다. 예약 이력에는 Bearer 세션이면 관리자 ID, 로컬 API key면 `null`인 행위자와 입력 사유를 기록한다.
- 변경 규칙:
    - 기본: D-1까지 고객 변경 가능
    - 당일: 시작 **1시간 전까지 변경 가능**, 이후는 1회 소모 처리
    - 변경 횟수 제한 없음(단, 시스템 보호를 위한 처리율 제한은 기술적으로 적용 가능)
    - 기존 결제 금액과 잔금 스냅샷을 유지하기 위해 **현재 예약과 같은 클래스의 활성·미래·예약 가능 슬롯**으로만 변경할 수 있다. 다른 클래스 이용은 기존 예약을 취소하고 새로 예약한다.

### 4.3 잔금(현장 결제)
- 잔금은 수업 시작 전 결제가 원칙
- 다만 시스템이 강제하지 않음
    - 운영자가 **미수금**으로 유지 가능
- 예약금 결제 예약은 PG confirm으로 예약이 생성된 시각을 `depositPaidAt`으로 기록한다.
- 8회권 예약은 별도 잔금이 없으므로 생성 시점부터 `balanceStatus=PAID`다.
- 잔금이 있는 예약에서 잔금 결제를 완료한 뒤에는 고객 취소를 허용하지 않는다. 예약금만 자동 환불되고 현장 수납 잔금이 남는 불일치를 막기 위해 관리자 정산으로 처리한다.
- 운영자는 현장 잔금 결제를 `balanceStatus=PAID`, `balancePaidAt`으로 기록하며, 결제 완료 시 미수 표시는 자동 해제된다.
- 잔금 결제와 미수 설정·해제는 실제 상태 변경만 관리자 예약 이력에 남긴다.
- 미결제 잔금이 있는 예약은 운영자가 `arrearsFlag=true`로 명시해야 수업 완료 처리할 수 있다.
- 수업 완료는 슬롯 종료 이후 `BOOKED -> COMPLETED`로 전이하고 `COMPLETED` 이력을 남긴다. 이미 진행된 수업의 정원 기록이므로 슬롯 `bookedCount`와 버퍼 차단 수는 변경하지 않는다.
- 노쇼도 슬롯 종료 이후에만 `BOOKED -> NO_SHOW`로 전이할 수 있다. 크레딧과 슬롯 정원 기록은 이미 확정된 이용 이력으로 유지한다.

## 5. 정규과정(월 8회권) 규칙(확정)
### 5.1 결제/유효기간/이월
- 월 8회권은 **월 전체 선결제**
- 8회권은 회원 전용이며 모든 구매 행은 정확한 `userId`를 가진다. 도메인 생성과 `pass_purchases.user_id NOT NULL`을 함께 적용해 소유자 없는 이용권을 허용하지 않는다.
- 크레딧 모델로 관리(총 8회)
- 신규 구매는 `REGULAR_CRAFT_8` 계획으로 확정해 구매 건의 `planCode`에 저장한다. 판매 뒤 정책이 바뀌어도 기존 구매 계약은 바꾸지 않는다.
- 유효기간: **결제일 포함 90일**. 서버는 마지막 사용 가능일 다음날 00:00 KST를 `expiresAt`으로 저장하며, 이 시각부터는 사용 불가로 본다.
- 만료 7일 전 알림은 구매한 8회권별로 1회 발송한다. 같은 회원의 여러 8회권은 각각 안내하고, 동일 구매 건의 수동·정기 배치 중복 실행은 `passId` 기준 outbox 멱등키로 합친다.
- 만료 시 남은 크레딧은 **즉시 소멸(환불 없음)**
- 만료 배치 실행 여부와 관계없이 크레딧 사용은 `expiresAt`부터 거절한다. 예약 취소의 크레딧 복구와 8회권 전체 환불은 이용권 행 잠금 후 만료 경계를 다시 확인하고, 아직 잔액이 남은 만료 이용권이면 `EXPIRE` 원장과 `remainingCredits=0`을 같은 트랜잭션에서 한 번만 반영한다.

### 5.2 예약 운영
- 고객이 유효한 8회권의 크레딧을 사용해 예약 가능 슬롯을 직접 선택하고 예약한다.
- `REGULAR_CRAFT_8`은 `passEligible=true`이고 카테고리가 `PERFUME`가 아닌 정규 공예 클래스에만 사용할 수 있다.
- 예약 한 건을 만들 때 크레딧 1회를 차감하며, 8회 일정을 한 번에 배정하지 않는다.
- 고객은 “예약 가능 시간” 범위에서 변경 가능
- 보강 없음:
    - 결석 또는 변경 불가(시작 1시간 전 이후)는 **1회 소모**
- 8회권 예약 생성 시 `pass_ledger`의 `USE` 원장은 해당 `booking_id`를 `related_booking_id`에 남긴다.
- 예약 취소로 1회권을 복구하는 `REFUND` 원장도 원인 예약의 `booking_id`를 남긴다. 8회권 전체 환불처럼 단일 예약이 원인이 아닌 원장은 `related_booking_id`를 비운다.
- 하나의 예약에는 `USE` 원장과 예약 취소 `REFUND` 원장을 타입별로 한 건만 기록한다.
- 크레딧을 변경하는 예약·취소·전체 환불·만료는 `pass_purchases` 행을 먼저 잠근다. 슬롯까지 바꾸는 흐름은 `pass_purchases → classes → slots(PK 오름차순)` 순서로 잠근다.
- 예약 상세 응답은 `cancelPolicy`를 포함해 취소 가능 여부, 환불/크레딧 복구 마감 시각, 8회권 크레딧 복구 여부를 서버 기준으로 제공한다.
- 8회권 예약의 취소 마감이 지난 경우 `cancelPolicy.warningCode=PASS_CREDIT_NOT_RESTORABLE_AFTER_DEADLINE`을 내린다. 프론트는 취소 확인창에 “취소 마감이 지나 8회권 크레딧은 복구되지 않습니다”라는 한국어 경고를 표시한다.

### 5.3 환불
- 이용권 소유 회원과 관리자는 남은 횟수 정산 환불을 요청할 수 있다(잔여 크레딧 기반). 회원 경로는 `/api/v1/me/passes/{id}/refund`다.
- `expiresAt`에 도달한 이용권은 잔여 횟수 정산 환불 대상이 아니다. 전체 환불 요청은 거절하고, 배치가 지연되어 남아 있던 크레딧만 환불 없이 만료 소멸시킨다.
- 환불 시 고객의 **미래 예약은 자동 취소**하고, 자동 취소한 미래 예약의 크레딧도 아직 쓰지 않은 크레딧으로 보아 환불 크레딧에 포함한다.
- PG 결제된 8회권은 저장된 `payment_key`로 환불 요청 이력을 먼저 남기고, 부모 트랜잭션 커밋 이후 PG 환불을 실행한다. 명시적 거절은 `FAILED`, 실행 전 일시 실패는 `RETRYABLE`, 반영 여부가 불명인 타임아웃·통신 단절은 `RECONCILIATION_REQUIRED`로 남긴다. 미완료 건은 최초 멱등키를 유지해 자동 복구하고 운영자가 재처리할 수 있다.
- 고객은 본인 8회권 목록·상세에서 환불 금액과 상태를 확인한다. 프론트는 미완료 상태를 제한된 간격으로 다시 조회하고, 성공 시 `PASS_REFUNDED` 알림을 발송한다. 내부 환불 ID와 실패 사유는 노출하지 않는다.

- 상품 주문과 체험 예약금은 각각 별도의 `ORDER`, `BOOKING` 결제로 처리한다.

## 7. 알림 정책(확정)
- 채널 우선순위:
    1) NHN Cloud Alimtalk v2.2(카카오 알림톡)
    2) 실패 시 SMS
    3) 이메일(영수증/보조)
    4) 앱 푸시(리마인드)
- 수신자 조회 실패처럼 실제 발송 채널을 시도하기 전 실패한 알림은 `notification_log`에 `SYSTEM` 채널의 `FAILED` 이력으로 남기고, 발송 재시도 배치 대상에는 포함하지 않는다.
- 일반 알림 요청은 도메인 트랜잭션 안에서 `notification_outbox`에 먼저 저장하고, 커밋 이후 별도 dispatcher가 발송한다. 같은 멱등키의 동시 요청은 사전 조회가 아니라 DB UNIQUE 제약을 이용한 원자적 insert로 한 건만 저장하며, 발송 결과는 기존처럼 `notification_log`에 남긴다.
- outbox는 자동 재시도를 모두 소진하면 `FAILED`로 종결하고 운영 메트릭을 올린다. 운영자는 관리자 화면에서 실패 목록과 사유를 확인하고, 같은 outbox 행과 멱등키를 `PENDING`으로 다시 열어 재처리한다.
- 시간 의존 리마인드는 발송 준비 트랜잭션에서 현재 예약·8회권·주문 상태, 시간 구간, 현재 회원/비회원 소유자를 한 DB snapshot으로 확인한다. 취소·완료·변경된 예약,
  만료·소진·환불된 8회권, 픽업 완료·만료 주문처럼 안내 의미가 사라졌으면 외부 채널과 채널 감사 로그를 호출하지 않고
  outbox를 재시도 불가 `OBSOLETE`로 종결한다. 적격이면 outbox 수신자를 현재 소유자로 갱신해 채널 감사 로그와 `SENT` 알림함도
  같은 현재 소유자에게 귀속하고, 준비 트랜잭션 커밋 뒤 외부 채널을 호출한다. 운영자 재처리는 `FAILED`만 허용한다.
- 예약 재변경이나 픽업 마감 연장으로 같은 대상이 미래 유효 구간에 다시 들어오면 정기 배치가 `OBSOLETE`인 같은 outbox와
  멱등키를 `PENDING`으로 다시 열고 현재 수신자로 갱신한다. 새 outbox를 만들거나 운영자가 임의로 재발송하지 않는다.
- Alimtalk·일반 SMS·휴대폰 인증 SMS 외부 호출은 서로 분리된 서킷 브레이커와 제한 큐 timeout executor로 보호한다. 명시적 영구 거절은 다음 채널 fallback으로 넘기되 서킷 장애율에는 넣지 않는다. 408·425·429·5xx, NHN SMS `-9999` 시스템 오류와 `-2021` 발송 큐 저장 실패, 호출 전 차단·대기열 포화와 DNS·라우팅·TCP 연결·TLS handshake/peer 검증·연결 풀 대기 실패는 재시도 가능한 실패로 처리한다. 요청 전달 뒤 응답 대기 timeout처럼 제공자 수락 여부를 알 수 없는 통신 예외는 전달 결과 불명으로 분류해 즉시 SMS fallback과 자동 재시도를 멈추고 `FAILED + DELIVERY_RESULT_UNKNOWN`으로 운영 확인 대상에 남긴다. NHN transport 단계 합은 바깥 TimeLimiter보다 짧아야 하며 역전된 운영 설정은 기동 시 거부한다.
- Alimtalk은 NHN 공식 v2.2 경로와 `X-Secret-Key`, outbox 멱등키를 담은 `X-NC-API-IDEMPOTENCY-KEY`를 사용한다. HTTP 상태뿐 아니라 응답 헤더 결과와 단일 수신자 결과 코드가 모두 성공일 때만 발송 성공으로 판단한다. 공식 중복 차단 시간은 10분이며, 실패는 애플리케이션의 SMS fallback으로 넘기고 NHN 자체 대체발송은 사용하지 않는다.
- Alimtalk·일반 SMS 발송 요청이 정상 접수되면 제공자 `requestId`와 `recipientSeq`를 outbox와 `notification_log`에 저장하고 `DELIVERY_PENDING`으로 둔다. 30초 간격 결과 조회가 `COMPLETED` 또는 SMS 성공 코드 `1000`을 확인한 뒤에만 `SENT`와 채널 성공 이력을 확정한다. 알림톡 최종 실패를 확인한 경우에만 같은 outbox 실행권으로 SMS를 요청하며, SMS도 최종 성공 확인 전에는 알림함에 노출하지 않는다. 결과 조회 중단은 `DELIVERY_CHECKING` lease를 1분 뒤 다시 선점한다.
- NHN SMS v3에는 클라이언트 멱등키 계약이 없으므로 일반 SMS 요청의 `userId`에는 outbox 멱등키로 만든 불투명 상관관계 ID만 전달한다. 이 값은 운영 대사용이며 중복 차단을 보장하지 않는다.
- outbox는 실행당 최대 50건을 처리하되 한 건씩 선점하고 결과를 확정한 뒤 다음 건을 선점한다. 선점마다 처리 토큰을 새로 발급하고 결과 반영 시 토큰과 행 버전을 확인한다. 오래된 실행의 성공·실패는 최신 재선점 상태를 덮지 않는다.
- `PROCESSING`이 1분 넘게 유지되면 NHN의 10분 멱등키 중복 차단 창 안에서 재선점을 시작한다. 알림 전달은 at-least-once이며 외부 성공 뒤 로컬 완료 저장 유실, 10분을 넘긴 중단, 멱등 계약이 없는 SMS fallback에서는 중복 발송될 수 있다.
- 외부 채널 성공 뒤 `notification_log` 저장만 실패하면 outbox를 경고가 있는 `SENT`로 끝내 중복 발송을 막고 운영 메트릭으로 알린다. 전달 결과 불명과 감사 로그 저장 실패가 겹치면 두 사유를 함께 남긴 최종 `FAILED`로 끝내며 자동 재발송하지 않는다. 외부 성공 전의 감사 이력 실패는 outbox 재시도 대상에 포함한다.
- 휴대폰 인증 SMS는 사용자 요청의 즉시 성공·실패를 알려야 하므로 outbox를 사용하지 않고, 인증 코드 저장을 먼저 커밋한 뒤 같은 SMS 장애 격리 경계로 발송한다.
- 회원 이메일 소유 확인도 일반 알림 outbox와 이메일 fallback 채널을 사용하지 않는다. 5분짜리 코드를 먼저 커밋하고 DB 트랜잭션 밖에서 별도 서킷 브레이커·제한 큐와 SMTP transport 제한보다 큰 전용 TimeLimiter로 보호한 전용 SMTP로 발송한 뒤 성공한 행만 사용 가능하게 표시한다. 운영 SMTP는 STARTTLS와 직접 SSL 중 정확히 하나를 필수로 하고 인증서 호스트명을 검증한다. 발송에 실패한 요청은 `503`으로 끝나며 자동 재발송하지 않고 사용자가 다시 요청한다.
- `notification_outbox`와 `notification_log`는 회원 또는 비회원 수신자 중 정확히 하나만 가진다.
- `notification_outbox`의 `SENT` 한 건을 회원 알림함의 논리 알림 한 건으로 사용하고, `notification_log`는 카카오톡·SMS 등 채널별 발송 감사 이력으로만 사용한다. fallback으로 채널 로그가 여러 건 생겨도 알림함에는 한 건만 표시한다.
- 발송 완료(`SENT`), 현재 의미가 사라져 발송하지 않은 리마인드(`OBSOLETE`), 자동 재시도를 모두 소진해 최종 실패(`FAILED`)로 종결된 outbox와 채널 감사 로그는 `processed_at`부터 180일 보존한 뒤 매일 03:30 배치에서 100건씩 삭제한다. 이 기간이 알림함 조회, 운영자 최종 실패 재처리와 동일 이벤트 멱등 보장 기간이다. 아직 재시도 가능한 `PENDING`, 발송 중인 `PROCESSING`, 제공자 최종 결과를 기다리거나 조회 중인 `DELIVERY_PENDING`·`DELIVERY_CHECKING`은 생성 시각이 오래돼도 자동 삭제하지 않는다.
- 발송 이벤트:
    - 예약 완료, 예약 변경
    - D-1 리마인드, 당일 아침 리마인드
    - 8회권 만료 7일 전 알림, 픽업 마감 2시간 전 알림
    - 결제 영수증/결제·환불 완료(예약금/주문/8회권 결제·환불)
    - 관리자 1:1 문의 답변, 상품 Q&A 답변
- 예약 D-1·당일 리마인드와 픽업 마감 알림은 회원 귀속 전후에도 같은 예약·주문당 한 번만 발송하도록 수신자와 무관한 `eventType + aggregateType + aggregateId` outbox 멱등키를 사용한다. 같은 수신자의 여러 예약·주문은 각각 안내한다.
- 예약·8회권·픽업 리마인드 후보는 `eventType + aggregateType + aggregateId`가 같은 outbox가 있으면 제외한다. 멱등키 문자열 형식이 달라도 같은 도메인 알림을 다시 접수하지 않으며, 예약·픽업은 과거 수신자 기반 키와 현재 aggregate 기반 키를 모두 인식한다.
- 예약 D-1은 발송일 기준 내일의 시작 경계를 포함한 `BOOKED` 예약, 당일 리마인드는 07:00 이후 `start_at > now`인 아직 시작하지 않은 오늘의 `BOOKED` 예약에만 유효하다.
  8회권 만료 임박 알림은 만료가 `(now, now+7d]`이고 잔여 횟수가 있을 때, 픽업 마감 알림은 주문이 `PICKUP_READY`이고
  마감이 `(now, now+2h]`일 때만 발송한다. 예약 D-1 배치가 자정 뒤 오늘 예약을 `내일` 안내로 보충하지 않는다.
- 회원은 상단 알림함에서 최근 180일의 논리 알림, 읽지 않음 개수, 개별/전체 읽음 상태를 확인할 수 있다.

## 8. 개인정보와 비회원 예약/주문 보안
- 휴대폰 번호는 입력의 공백과 하이픈을 제거한 국내 휴대폰 숫자 형식(`^01[0-9]{8,9}$`)으로 통일해 저장·검색·외부 발송에 사용한다.
- 회원의 검증된 기준 이메일·이름·전화번호와 비회원 이름·전화번호는 평문 컬럼을 두지 않는다. 표시가 필요한 값은 AES-GCM 암호문, 정확 일치 검색은 HMAC 인덱스를 사용한다.
- Google은 검증된 이메일을, Kakao는 `is_email_valid=true`이면서 `is_email_verified=true`인 이메일을 가입 시 기준 이메일로 사용한다. Naver 프로필 이메일은 검증된 값으로 간주하지 않아 신규 Naver 회원의 기준 이메일 암호문·HMAC과 회원 응답의 이메일은 `null`로 시작한다. 이메일이 없는 로그인 회원은 최근 본인 확인 뒤 메일함의 6자리 코드를 검증해 직접 소유한 이메일을 한 번 등록하며, 외부 제공자 이메일이나 기존 회원과의 이메일 일치만으로 계정을 합치지 않는다.
- 소셜 제공자 식별자는 원문 대신 제공자별 HMAC으로 저장하고 정확 일치 로그인에만 사용한다.
- 같은 소셜 계정의 최초 로그인 callback이 동시에 들어오면 DB 유일 제약을 먼저 확보한 요청만 회원 연결을 완료한다. 경합한 요청은 409로 종료하며 사용자가 소셜 로그인을 새로 시작하면 이미 연결된 회원으로 로그인한다.
- 소셜 로그인 callback URI는 provider별 운영 설정에 고정한다. Spring Security OAuth2 Client가 만든 authorization request와 `state`는 callback 전까지만 Redis HTTP 세션에 보관하고 검증·소비하며, 로그인 후에는 OAuth 토큰이나 `SecurityContext` 대신 `customerUserId`와 `customerCredentialVersion`만 세션 인증 상태로 유지한다.
- 소셜 신규 가입 동의는 공개 OAuth GET query로 직접 받지 않는다. 회원가입 화면이 CSRF 보호 POST로
  5분짜리 일회성 가입 의도를 만들고, 반환된 불투명 시도 ID로 시작한 OAuth `state`와 provider를 결합한다.
  callback은 시도 ID·provider·state·만료가 모두 유효한 동의를 한 번 소비하며 기존 회원의 일반 로그인은
  가입 의도 없이 계속 허용한다.
- 소셜 계정 추가 연결은 최근 10분 안에 현재 비밀번호 또는 이미 연결된 동일 소셜 계정으로 본인을 다시 확인하고, CSRF 보호 요청으로 만든 5분짜리 일회성 연결 시도와 그 시도로 생성한 OAuth `state`가 모두 유효할 때만 허용한다. callback에서는 연결 의도의 회원 ID·자격 버전·provider와 현재 HTTP 세션의 회원 ID·자격 버전을 함께 다시 확인한다. 연결에는 provider가 인증한 ID만 사용하고 provider 이메일·이름은 기존 회원 소유권 증명이나 연결 조건으로 사용하지 않는다.
- 연결된 외부 계정이 다른 회원 소유이거나 같은 provider의 다른 계정이 이미 연결되어 있으면 자동 이전하지 않는다. 소셜 연결 해제도 같은 최근 본인 확인을 요구한다. 해제 후에는 로컬 비밀번호 또는 다른 소셜 계정 하나를 반드시 유지하며, 새 연결 또는 실제 해제로 로그인 수단 집합이 바뀌면 자격 버전을 증가시키고 모든 회원 세션을 폐기해 남은 로그인 수단으로 다시 로그인하게 한다. 이미 같은 외부 계정이 연결된 멱등 요청은 버전과 세션을 바꾸지 않는다.
- 로컬 비밀번호는 BCrypt로 저장하고 모든 회원·관리자 비밀번호 요청을 UTF-8 72바이트 이하로 제한한다. 롤백 호환 기간에는 식별자 없는 형식으로 쓰고 식별자 없는 형식과 `{bcrypt}` 형식을 모두 읽는다. 고객 로그인은 존재하지 않는 계정과 로컬 비밀번호가 없는 소셜 전용 계정에도 고정 dummy BCrypt 해시를 한 번 비교하고 같은 자격 오류를 반환하며, 정규화 이메일 HMAC 기준으로 10분에 10회 제한한다. 사용자가 비밀번호를 변경·재설정할 때 `users.credential_version`을 증가시킨다. 로그인 성공 중 BCrypt 작업 강도만 투명하게 승격하는 경우에는 비밀번호 자체가 바뀌지 않으므로 자격 버전과 기존 세션을 유지한다. 회원 요청마다 세션 버전과 DB 버전을 비교해 Redis 삭제 실패나 동시 요청으로 남은 이전 세션도 인증에 사용하지 못하게 한다. Redis 정리는 변경 전 자격 증명 버전의 세션만 대상으로 하며 변경 후 새 로그인 세션은 보존한다. Redis 세션 폐기 실패는 전용 카운터와 critical 운영 경보로 즉시 알린다.
- 휴대폰 확인과 비밀번호 변경처럼 `users` 한 행을 갱신하는 경로는 행 잠금으로 직렬화하고 `users.version` 낙관적 락으로 stale update를 최종 차단한다. 휴대폰 인증 코드 소비 제한을 위한 Redis 확인은 회원 전화번호 변경·비밀번호 재설정·비회원 이력 귀속의 사용자 행 잠금 트랜잭션과 비회원 결제 prepare의 DB 트랜잭션보다 먼저 실행한다. 인증 코드 소비는 실제 회원 변경 또는 `PaymentAttempt` 저장과 같은 DB 트랜잭션으로 묶는다. 고객 이메일 로그인은 비관리 해시 스냅샷 조회와 최초 BCrypt를 DB 트랜잭션 밖에서 수행하고, 성공 후보만 별도 트랜잭션에서 행을 잠근 뒤 활성 상태와 최신 해시를 재검증한다. 해시 승격과 최근 로그인 시각은 같은 잠금 트랜잭션에 저장해 잘못된 비밀번호와 일반 BCrypt 요청이 잠금을 점유하지 않게 한다.
- 휴대폰 인증 번호와 인증 코드는 사용 목적까지 포함한 HMAC으로 검증하며, 로컬 조회가 필요한 인증 코드만 암호문으로 저장한다. 회원가입·비밀번호 재설정·회원 전화번호 등록/변경·비회원 예약/주문·이력/결제 복구 목적은 서로 교차 사용할 수 없다. 인증정보 원문은 로그에 남기지 않는다.
- 인증 코드는 DB에 먼저 확정한 뒤 트랜잭션 밖에서 NHN Cloud 인증용 SMS API로 발송 요청한다. NHN이 요청을 정상 접수했다고 기록된 코드만 사용할 수 있고, 더 나중에 발급한 같은 전화번호·같은 목적 코드의 접수 완료가 이전 미소모 코드만 무효화한다. 늦게 끝난 이전 요청의 접수 완료는 최신 코드 상태를 덮지 않는다. 발송 요청 실패는 `503`으로 알리며, 모든 소비 경로는 전화번호별 실패 제한을 먼저 적용하고 가입·복구·직접 비회원 예약 또는 결제 prepare의 소유 트랜잭션 안에서 잠금 후 한 번만 허용한다.
- 이메일 소유 확인 행은 회원 ID·자격 버전·정규화 이메일·6자리 코드를 결합한다. 이메일과 코드는 HMAC으로 조회하고, local/dev 검증 지원에 필요한 코드만 AES-GCM 암호문으로 저장한다. SMTP 발송 성공이 기록된 같은 회원의 가장 최근 코드만 5분 동안 한 번 사용할 수 있고, 새 요청의 발송 실패가 기존 정상 코드를 무효화하지 않는다. 등록 시 회원 행을 잠그고 이메일 HMAC 유일 제약을 최종 확인한 뒤 `credential_version`을 증가시키며 기존 회원 세션을 폐기한다.
- 필드 AES/HMAC 키 회전에서는 원문 이메일이 없는 `email_verifications`와 원문 전화번호가 없는 `phone_verifications`의 HMAC을 재생성할 수 없으므로 두 테이블의 진행 중 행을 모두 삭제하고 사용자가 새 코드를 요청하게 한다.
- 유료 비회원 주문·예약은 결제 prepare에서 인증 코드를 소비한다. 서버는 `context + orderId + 정규화 전화번호 + nonce`를 HMAC 서명한 결제 귀속 증거를 만들고, confirm fulfillment는 원 인증 코드의 만료 여부와 무관하게 이 증거를 재검증한다. 증거는 다른 결제 시도·컨텍스트·전화번호에 재사용할 수 없다.
- 비회원 이름·전화번호와 결제 귀속 증거가 포함된 서버 확정 payload는 `payment_attempt.payload_enc`에 암호문으로 저장한다. 공개 요청의 인증 코드 원문은 서버 확정 payload에 옮기지 않는다.
- 배송 주문은 confirm 트랜잭션에서 고객이 선택한 `Fulfillment`와 배송지 스냅샷을 함께 저장한다. 배송지는 `fulfillments.shipping_address_enc`에 AES-GCM 암호문으로만 보존하고, 소유권이 확인된 고객 주문 상세와 관리자 단건 이행 조회에서만 복호화한다. 두 상세 응답은 `Cache-Control: no-store`로 반환하고 목록·검색 응답에는 배송지를 포함하지 않는다.
- 주문 배송지와 관리자 공방 주소 입력은 `GET /api/v1/addresses/search`의 공식 도로명주소 검색 결과를 우편번호·기본 주소에 적용할 수 있다. 검색 연동 비활성·장애 때도 직접 입력을 유지하며, 승인키는 서버에만 둔다.
- 관리자 주문·예약 키워드 검색은 `ORD-{숫자}`·`BK-{숫자}` 형식의 표시 번호는 ID 정확 일치, 일반 이름과 국내 휴대폰 형식은 각각 이름·전화 HMAC 정확 일치를 지원한다. 선행 와일드카드로 PK 인덱스를 무력화하는 ID 부분 검색과 암호화된 개인정보의 부분 검색은 제공하지 않는다. 검색 결과는 별도 처리 화면을 만들지 않고 기존 주문·예약 운영 패널로 연결한다.
- Redis 처리율 제한 키에는 IP, 이메일이나 관리자 토큰 원문을 쓰지 않는다. 관리자 세션은 토큰 HMAC을 Redis 키로, 세션 JSON 암호문을 값으로 저장한다. 세션·관리자 자격 버전 인덱스·TTL은 Redis Lua 한 번으로 생성해 부분 저장을 남기지 않는다.
- 관리자 비밀번호 변경은 현재 비밀번호를 다시 확인한 뒤 BCrypt 해시와 `credential_version`을 함께 갱신한다. 성공하면 현재 세션을 포함한 해당 관리자의 기존 Bearer 세션을 모두 무효화하고 관리자 화면은 새 비밀번호 로그인을 요구한다. 로그인 성공 중 BCrypt 작업 강도만 투명하게 승격하는 경우에는 자격 버전과 기존 Bearer 세션을 유지한다.
- 관리자 로그인은 존재하지 않는 계정·잘못된 비밀번호·잘못된 MFA에 같은 오류를 반환한다. 인증되지 않은 요청이 공유 계정을 원격으로 막을 수 있는 계정 전역 hard lock은 사용하지 않고, IP당 5회/분 fail-closed 제한과 MFA로 방어한다. 비밀번호는 비관리 해시 스냅샷으로 먼저 확인하고 성공 후보만 ID로 행을 잠근 뒤 최신 해시를 재검증한다. 결과 이력은 입력 원문 대신 HMAC으로 180일 보존한다.
- 관리자는 Bearer 세션에서 TOTP MFA를 등록·확인·해제할 수 있다. MFA 활성 계정은 5분짜리 일회성 challenge의 6자리 TOTP 또는 미사용 복구 코드 확인 전에는 세션을 발급하지 않는다. TOTP 비밀키는 AES-GCM 암호문, 복구 코드는 무작위 salt가 있는 단방향 해시로만 저장한다. 등록 확인과 로그인에서 수락한 30초 시간 구간을 관리자 행에 기록해 같은 구간의 TOTP를 다시 사용할 수 없게 한다. MFA 설정 변경은 자격 버전을 증가시켜 기존 관리자 세션을 모두 무효화한다. 인증 앱을 잃은 관리자는 복구 코드로 로그인한 세션에서 현재 비밀번호를 다시 확인한 뒤 MFA를 초기화할 수 있고, 성공하면 비밀키·모든 복구 코드·기존 세션을 폐기한 뒤 새로 등록한다. 초기화 시도는 `RECOVERY_CODE` 인증 수단 확인 뒤 관리자 ID별 5회/10분 fail-closed 제한을 먼저 소비하고, 그 다음 관리자 행 잠금과 BCrypt 비밀번호 확인을 수행한다. 다른 인증 수단의 세션은 이 버킷을 소비하지 않는다.
- 운영 환경의 MFA 미등록 관리자는 비밀번호 로그인 후 MFA 상태 조회·등록 시작·등록 확인만 가능한 제한 세션을 받는다. 등록 확인 뒤 해당 세션은 무효화되며, 복구 코드 보관 후 MFA로 다시 로그인해야 일반 관리자 기능을 사용할 수 있다.
- 인증 앱과 복구 코드를 모두 잃은 관리자 계정의 자동 복구는 지원하지 않는다. 최초 계정용 `ADMIN_SETUP_TOKEN` 재사용이나 DB 직접 MFA 해제는 허용하지 않으며, 복구 코드는 등록 직후 별도 오프라인 장소에 보관한다.
- 회원 휴대폰 최초 등록·변경은 현재 자격 버전에 결합된 최근 본인 확인과 새 번호의 목적별 SMS 소유 확인 뒤 저장하며 `phone_hmac` 유일 제약으로 회원 간 번호 중복을 차단한다.
- 회원 탈퇴는 미완료 주문, 활성 예약, 사용 가능한 미만료 8회권, 미완료 환불이 없을 때만 허용한다. 성공하면 개인정보와 자격 증명·소셜 연결을 익명화/삭제하고 `withdrawnAt`을 기록한 뒤 기존 세션을 폐기한다.
- 탈퇴 후에도 종결 주문·예약의 회원 ID와 운영 이력은 유지하며, 관리자 조회는 익명화된 회원 이름과 제거된 전화번호를 사용한다.
- 회원 탈퇴는 회원 소유 `PENDING`·`PROCESSING` 등 미종결 결제 시도, 활성 주문 클레임과 미완료 예약 취소 후속 작업도 차단한다. 결제 prepare와 탈퇴는 같은 회원 행을 잠가 직렬화하고, prepare 뒤 탈퇴가 먼저 반영된 비정상 경합에서 PG 승인이 도착하면 도메인을 만들지 않고 보상 환불로 종결한다.
- 이메일 회원가입과 처음 보는 Google·Naver·Kakao 계정의 신규 회원 생성, 비회원 주문·예약 결제 prepare는 현재 이용약관·개인정보처리방침 버전과 명시적 동의를 요구한다. 서버는 클라이언트 시각을 받지 않고 회원 또는 결제 시도에 동의 유형·목적·버전·서버 수락 시각을 append-only 이력으로 저장한다. 프론트는 정책 종류별 버전 registry에서 불변 문서를 선택하고 기존 entry를 수정하지 않아, 공방 프로필이나 현재 정책이 바뀌어도 동의 당시 본문을 재현한다. 기존 회원 로그인과 회원 거래에는 매번 재동의를 요구하지 않는다.
- 프론트는 로그인·회원가입·세션 복구·로그아웃·탈퇴로 인증 주체가 바뀔 때 `me` 고객 전용 React Query 요청을 취소하고 캐시를 폐기해 이전 회원의 주문·예약·8회권·문의·알림·장바구니가 다음 회원 화면에 재사용되지 않게 한다. 비밀 문의 상세, 주문 수령인·배송지와 작성 단계처럼 컴포넌트 로컬에 둔 회원 결합 상태도 세션 버전이 바뀌면 초기화한다. 단, 예약 화면의 인라인 로그인 직전 선택한 공개 클래스·슬롯·결제 방식은 상위의 일회성 draft로 넘겨 로그인 결과의 회원 ID에 결합한 뒤 같은 회원의 새 세대 화면에서만 복원한다. 다른 회원으로 바뀌면 draft를 폐기하고, 같은 회원이면 최신 클래스·슬롯 조회로 유효성을 다시 확인한 뒤 사용자가 결제를 다시 명시적으로 눌러야 시작한다. 로그인 전 컴포넌트의 결제 mutation callback은 실행하지 않는다. 회원 전용 요청은 시작 시점의 세션 버전을 함께 기억하고, 로그인 등으로 버전이 바뀐 뒤 도착한 이전 `/me` 요청의 401·응답은 새 인증 상태를 덮지 않는다.
- 프론트의 최초 회원 상태 확인은 `/me`의 401만 비로그인으로 확정한다. 네트워크·서버 오류는 로그아웃이나 빈 회원 데이터로 바꾸지 않고 전역 오류와 재시도를 표시하며, 확인이 끝날 때까지 회원 장바구니를 비회원 장바구니로 대신 표시하지 않는다. 회원 장바구니 조회 실패도 빈 장바구니와 구분하고, 추가·수량 변경·삭제·비회원 병합과 그 뒤 최신 조회가 끝날 때까지 중복 조작과 결제를 막으며 실패 사유를 표시한다. 결제 준비에는 화면이 가진 `cartVersion`을 보내 서버에서도 오래된 화면 결제를 거절한다. 상품·클래스·슬롯·정책처럼 서버에서 불러오는 선택 기준도 조회 실패와 실제 빈 결과를 구분해 재시도를 제공한다.
- 관리자·인증·회원·결제·비회원 복구 응답과 `X-Access-Token`으로 소유권을 확인한 응답은 중앙 보안 정책으로 `Cache-Control: no-store`를 적용한다. 프런트 Sentry로 보내는 요청·탐색·Referer·API 태그 URL은 경로만 남기고 query와 fragment를 제거하며, 요청 본문·쿠키·query string과 인증·CSRF·비회원 토큰 헤더는 전송하지 않는다. 운영 프런트 Nginx access log도 query string과 Referer를 기록하지 않고 `$uri`만 남기며, Toss 예외는 결제 키가 포함될 수 있는 throwable 원문 없이 내부 ID와 예외 타입만 기록한다.
- 비회원 예약/주문은 휴대폰 인증(문자 코드) 필수
- 비회원 예약/주문의 접근 토큰은 HMAC-SHA256 서명과 만료 시각을 포함한다. 주문·예약에는 서명 토큰 전체의 SHA-256 해시만 저장하며 서명 없는 토큰은 허용하지 않는다. 따라서 토큰에서 nonce만 추출해 제출해도 서명·만료 검사를 우회할 수 없다. 동일 confirm 재호출에 같은 토큰을 반환하기 위한 원문은 `payment_attempt`에 AES-GCM 암호문으로 저장한다 ([ADR-0024](../../ADR/0024_비회원_토큰_강화/adr.md), [ADR-0033](../../ADR/0033_결제_confirm_트랜잭션과_보상_경계/adr.md)).
- 동일 `phone_hmac`은 하나의 비회원 이력 소유자만 식별하며, 동시 요청에서도 기존 Guest를 원자적으로 재사용한다.
- 조회/변경/취소는 `X-Access-Token` 헤더로 토큰 전달 (URL 노출 방지)
- 비회원이 주문·예약 ID 또는 토큰을 잃었거나 토큰이 만료되면 휴대폰 SMS 소유 확인 후 `/api/v1/guest-records/recovery`로 복구한다. 새 단기 토큰 하나를 발급해 같은 비회원의 주문·예약 토큰 해시를 원자적으로 교체하며, 이전 토큰은 즉시 무효가 된다. 복구 POST 응답은 주문·예약별 최신 100건을 제공하고, 같은 복구 토큰으로 주문·예약 커서 API를 조회해 전체 이력을 이어서 확인한다.
- 활성 예약은 회원·비회원 소유자의 현재 정규화 전화번호 HMAC을 예약자 식별자로 저장한다.
  `(slot_id, owner_phone_hmac)` DB 유일 제약으로 회원·비회원 경계를 가로질러 동일 전화번호의 동일 슬롯 중복을 방지한다.
  회원 전화번호 변경과 HMAC 키 회전은 활성 예약 식별자도 같은 트랜잭션에서 갱신하고,
  취소·완료·노쇼 예약은 더 이상 필요 없는 전화번호 HMAC을 제거한다.
- 자가 호스팅 운영 백업은 원래 app replica를 보존하면서 쓰기를 잠시 중단하고 MySQL 스냅샷과 미디어 볼륨을 같은 구간에 보관해 하나의 복구 묶음으로 암호화한다. DB와 상품·클래스 이미지 중 하나만 복구하지 않는다. 복원 성공마다 백업 생성시각과 복구 환경 파일 해시로 대사 토큰을 만든다. 운영자가 PG·알림·개인정보 대사를 완료한 뒤 세 확인값에 같은 토큰을 직접 제출한 경우에만 토큰을 한 번 소비하고 서비스를 활성화한다.
- 백업은 약 6시간마다 실행하고 성공 heartbeat를 남긴다. 독립 systemd watchdog은 15분마다 heartbeat가 7시간 넘게 정체되거나 사라졌는지 확인해 외부 webhook으로 알린다. 같은 노트북 전체 중단은 외부 uptime 감시가 별도로 확인한다.

## 8.1 결제 진입점 (prepare/confirm)
- 표준 결제 생성 경로는 모든 도메인(`ORDER`, `BOOKING`, `PASS`)과 회원 장바구니에서 `/api/v1/payments/prepare` → `/api/v1/payments/confirm` 단일 진입점을 사용한다.
- prepare 단계에서 서버가 `orderId(UUID)`와 `amount`를 확정해 `payment_attempt`(`PENDING`)로 저장한다. 클라이언트가 보낸 amount는 신뢰하지 않는다.
- 회원 결제 시도에는 세션 소유자 ID를 저장한다. 비회원 결제 시도에는 prepare 응답에서 한 번 전달하는 서명 조회 토큰 전체의 해시와 정규화 휴대폰의 active HMAC을 저장한다. 고객은 조회 토큰으로 결제 확정과 보상환불 진행 상태를 조회하며 `orderId`만으로는 조회할 수 없다.
- 비회원이 브라우저 저장소와 `orderId`를 함께 잃으면 새 SMS 코드로 휴대폰 소유를 확인한다. 서버는 active·previous HMAC 후보와 소유 HMAC을 상수 시간 비교하고, 생성 30일 이내 최종 결제와 아직 대사·보상이 끝나지 않은 결제 시도를 ID 순서로 잠근다. 해당 결제들의 상태 조회 토큰 해시를 공통 새 토큰으로 한 번에 교체하고 `orderId`, 결제 종류, 금액, 고객 상태 목록을 반환하므로 이전 토큰은 즉시 무효가 된다.
- 모든 prepare 최종 금액과 상품·클래스·8회권 설정 가격은 웹 클라이언트가 원 단위 정수를 정확히 표현할 수 있는 `9,007,199,254,740,991원` 이하여야 한다. 클래스 가격은 10원 이상이어야 한다.
- prepare 후 30분 동안 confirm이 시작되지 않은 `PENDING`은 `CANCELED`로 만료시키고 개인정보 payload를 제거한다. confirm 진입 시 행 잠금 아래 유효시간을 다시 확인해 배치가 지연돼도 `410 PAYMENT_ATTEMPT_EXPIRED`로 거절하고, 배치는 미사용 결제를 일괄 정리한다.
- 산출 규칙:
    - 주문: 한 요청에서 최대 100개 상품 항목을 받아 `ACTIVE` 상품과 옵션 구성을 일괄 조회한다. 기성품은 상품 가격, 주문제작은 서버가 확인한 `기본가 + 조합 추가금 + 직접입력 추가금`에 수량을 곱하고 배송 주문이면 `app.order.shipping-fee`를 더한다. 서버가 확정한 상품명·기본가·추가금·최종 단가·SKU·선택 옵션·직접입력 문구·고정 사양·관리 방법·예상 제작 기간·배송비·수령 방식·배송지 스냅샷을 결제 시도 payload에 함께 저장한다. 동일한 `productId + variantId + 직접입력값` 요청은 먼저 합산하며 SKU별 수량은 1~99개다. 상품 가격과 총 결제 금액은 브라우저가 원 단위 정수를 정확히 표현할 수 있는 `9,007,199,254,740,991원` 이하여야 하고, 범위 초과와 산술 overflow는 `INVALID_INPUT`으로 거절한다.
    - 예약금: `slot.bookingClass.price × participantCount × 10%`; 예약금과 잔금, 인원을 결제 시도 payload에 함께 저장한다. 일반 예약 인원은 1명부터 선택한 슬롯의 남은 정원까지, 예약금은 1원 이상이며 8회권 예약은 1명·0원 내부 승인이다. prepare에서 슬롯 상태·정원·양방향 수업·정리 구간 충돌을 확인한다. 8회권은 소유권·만료·잔여 횟수·클래스 적용 가능 여부도 읽기 전용으로 확인한다. confirm fulfillment에서는 이용권과 슬롯 범위를 잠근 뒤 최신 상태를 다시 확인한다.
    - 8회권: `app.pass.total-price` 환경 변수 (`PASS_TOTAL_PRICE`, 기본 240,000원); 확정 가격을 결제 시도 payload에 저장한다.
- confirm 단계에서 PG `paymentKey`와 `amount`가 prepare 시점 amount와 다르면 거절한다.
- 주문·예약·8회권 confirm은 현재 가격을 다시 계산하지 않고 prepare 시점에 저장한 가격 스냅샷으로 도메인을 생성한다. 저장된 결제 금액이 `payment_attempt.amount`와 다르면 PG 호출 전에 거절한다.
- confirm은 결제 시도를 새 processing token과 함께 `PROCESSING`으로 선점한 뒤 DB 트랜잭션 밖에서 PG를 호출한다. 동시 요청은 한 건만 PG 호출을 수행한다. stale 재선점 뒤 이전 token의 실패 결과는 저장하지 않지만, 늦게 도착한 PG 성공은 같은 요청임을 재검증한 뒤 `APPROVED`로 화해해 실제 승인을 유실하지 않는다. 이전 요청은 같은 요청 안에서 PG를 재호출하지 않는다.
- `CONFIRMED` 결제는 최종 도메인 ID와 비회원 접근 토큰 암호문을 보존한다. 같은 사용자·금액·paymentKey로 confirm을 재호출하면 PG나 도메인 생성을 반복하지 않고 같은 결과를 반환한다.
- 프런트엔드는 결제 완료가 확인되면 확정 요청을 삭제하고 `/payments/success?completedOrderId=...`로 URL을 정리한다. 이 번호는 조회 키일 뿐 인증 자격이 아니다. 완료 화면 새로고침·재진입은 기존 상태 API를 현재 회원 세션 또는 같은 고객의 비회원 상태 조회 토큰으로 호출해 결과·내역·영수증 링크를 복원한다. 조회에 실패하면 다시 조회할 수 있게 안내하며 confirm이나 새 prepare를 호출하지 않는다. 완료된 0원 결제는 이후 새 구매를 막지 않는다.
- 결제 성공 화면은 confirm 오류 뒤 소유권이 확인된 결제 상태를 조회한다. `PAYMENT_CONFIRM_IN_PROGRESS`, `PAYMENT_CONFIRM_RETRYABLE` 또는 네트워크·필수 인프라 일시 장애일 때만 같은 confirm을 다시 확인하고, PG 승인 후 도메인 생성 실패는 `REFUNDING → REFUNDED` 진행을 표시한다. 대사·환불 확인 상태에는 새 결제를 시작하지 않도록 안내한다.
- 결제창 인증 취소·실패 화면은 같은 고객 세션에 보관한 결제 ID로 승인 전 결제를 종료한 뒤 구매 화면으로 돌아간다. 종료와 쿠폰·적립금 예약 해제는 한 트랜잭션이며 승인 진행·대사·보상 중인 결제는 변경하지 않고 현재 상태를 표시한다. SDK 오류에도 같은 종료를 시도하고 브라우저 자체 종료·요청 실패 시 기존 30분 만료 배치가 미시작 결제를 정리한다. 상품 상세·주문서·장바구니·8회권 구매 경로와 주문서 query를 유지하고 예약은 선택한 `classId`로 돌아가 최신 가능 시간을 다시 고른다. 고객 세션을 다시 확인하고 해당 복귀 정보만 소비하며 prepare·confirm·환불은 자동 호출하지 않는다. 복귀 정보 없음·계정 변경·외부 주소는 홈·상품 목록으로 안내한다. 인증 코드·배송지·결제 약관 동의는 복귀용으로 추가 저장하지 않는다.
- 최종 상태(`CONFIRMED`, `FAILED`, `COMPENSATED`, `CANCELED`)가 된 결제 시도는 생성 30일 뒤 개인정보 payload, 비회원 접근 토큰 암호문, 결제 소유 휴대폰 HMAC과 상태 조회 토큰 해시를 제거한다. 금액·상태·PG 키·최종 도메인 ID는 감사용으로 유지하며, 복구·대사·보상 진행 상태는 자동 정리하지 않는다. 정리 뒤 confirm 재조회는 `410 PAYMENT_RESULT_RETENTION_EXPIRED`로 종료한다.
- 휴대폰·이메일 인증 행은 만료 후 1일 동안 장애 분석과 경합 확인을 위해 유지한 뒤 매일 03:30 배치에서 각각 `(expires_at, id)` 순서로 100건씩 삭제한다.
- 로그인 장바구니 병합은 한 요청당 최대 100개 상품을 받으며 멱등 기록은 재시도 보장을 위해 생성 후 7일간 유지한다. 같은 회원의 장바구니 추가·병합·수정·삭제·결제 차감은 소유자 잠금을 먼저 획득해, 아직 항목이 없는 상품을 동시에 추가해도 한 행에 수량을 합산한다. 클라이언트는 요청에 시작 시점의 회원 ID를 보내고 요청 전·후 세션 스냅샷과 로컬 항목 계보를 함께 보존한다. 서버는 요청의 회원 ID가 현재 인증 주체와 다르면 병합을 거절하고, 클라이언트는 계정 전환 뒤 늦은 성공이 삭제 후 새로 담은 같은 상품을 차감하지 않게 한다. 이후 매일 03:30 보존 배치가 `created_at` 인덱스로 100건씩 짧게 삭제한다.
- 어떤 aggregate도 참조하지 않는 업로드 이미지는 첫 보존 배치에서 최초 고아 관찰 시각을 파일 시스템 마커로 기록한다. 전체 참조와 저장 디렉터리 스캔은 트랜잭션 밖에서 수행한다. 7일 뒤 삭제 후보마다 짧은 트랜잭션으로 DB 단일 행을 잠그고 해당 파일의 최신 참조만 다시 확인해, 여전히 참조되지 않았으면 삭제하고 참조가 생겼으면 마커를 제거한다. query·fragment가 붙은 서비스 상대 로컬 URL도 URI path가 같으면 참조로 인정하되, 같은 path를 가진 외부 절대 URL은 로컬 파일로 해석하지 않는다. 로컬 이미지 URL 저장도 같은 잠금 획득 뒤 파일 존재를 확인해 참조와 파일 삭제가 엇갈리지 않게 한다.
- 상품 상세·주문서·장바구니·예약금·8회권 구매 화면은 `카드·간편결제`, `네이버페이`, `카카오페이`를 제공한다. 기본 선택은 Toss `CARD` 통합창이다. 네이버페이·카카오페이는 `card.flowMode=DIRECT`, 선택한 `card.easyPay` 코드(`NAVERPAY` 또는 `KAKAOPAY`), `windowTarget=self`로 현재 창에서 연다. 두 간편결제 선택 시 전자금융거래 이용약관·개인(신용)정보 수집·이용·제3자 제공 동의를 prepare 전에 확인해 미동의 요청이 비회원 인증 코드를 소비하거나 할인 혜택을 예약하지 않게 한다. 결제수단을 바꾸면 약관 동의를 초기화한다. 서버 금액이 0원인 주문과 이용권 사용 예약은 기존 내부 확정 경로를 유지한다. 서버는 화면 선택값이 아니라 Toss 승인·조회 응답의 실제 `method`를 결제 시도에 저장하고 예약 결제수단에 반영한다.
- Toss confirm은 prepare의 `orderId`를 멱등키로 사용한다. 일시 실패는 `RETRYABLE`, 최종 거절은 `FAILED`로 별도 트랜잭션에 저장한다.
- 비회원 화면은 prepare 성공이 확인되면 소비된 휴대폰 인증코드를 초기화하고, 결제창 취소 후 다시 준비하려면 새 인증을 안내한다. `PHONE_VERIFICATION_FAILED`도 인증 입력으로 돌아가되 상품·예약 시간·이름은 보존한다. 재고 부족 등 prepare 단계의 업무 오류에는 코드를 유지하며, 재발송 시 부모 화면의 이전 코드와 진행 가능 상태도 함께 해제한다. 예약 모달에는 인증을 직접 다시 시작하는 버튼을 제공한다.
- Toss 승인 응답의 `paymentKey`, `orderId`가 요청값과 다르면 해당 결제에 귀속할 수 없는 정합성 이상으로 보고 즉시 `RECONCILIATION_REQUIRED`로 전이한다. 고객은 새 결제를 시작하지 않고 운영 대사를 기다린다.
- 쿠폰·적립금 전액 결제와 8회권 사용 예약은 prepare에서 `amount=0`을 받고, 현재 고객 세션에 `{paymentKey:null, orderId, amount:0}`을 저장한 뒤 공통 `/payments/success` 화면에서 PG 없이 confirm한다. 응답 유실·새로고침·구매 화면 재진입은 기존 번호로 조회·재확인하며 미확인 0원 결제가 있는 동안 새 prepare를 만들지 않는다. 계정 전환 시 다른 계정의 저장 요청을 사용하지 않고 완료·실패·만료·보존기간 종료가 확인되면 해당 요청만 제거한다. 브라우저 저장소에 기록하지 못하면 confirm 전에 준비된 결제를 종료한다. 도메인 생성 실패는 `FAILED`로 기록하며 외부 결제가 없으므로 보상 환불을 만들지 않는다.
- confirm 요청 `paymentKey`는 `payment_attempt.payment_key`, PG 승인 응답의 `paymentKey`는 `payment_attempt.confirmed_payment_key`와 생성된 주문/예약/8회권의 `payment_key`에 저장한다. 환불 이력은 원결제 식별자인 Toss `paymentKey`를 `refunds.payment_key`, 환불 거래 식별자인 Toss cancel `transactionKey`를 `refunds.refund_transaction_key`에 분리해 저장한다. `refunds.amount`는 PG 취소액, `customer_refund_amount`는 PG 취소액과 적립금 복원액을 합친 고객 반환 총액이며, 적립금 회수액과 쿠폰 복원 여부도 별도 스냅샷으로 보존한다. PG 취소액이 양수인 성공 결과와 `SUCCEEDED` 전이는 공백이 아닌 `transactionKey`를 요구하고, PG 취소액이 0원인 주문 환불은 외부 호출 없이 로컬 성공 처리한 뒤 동일한 적립금·쿠폰 후처리를 수행한다. 같은 결제의 부분 환불은 `paymentKey`를 공유할 수 있지만 환불 멱등키와 취소 `transactionKey`는 환불 전체에서 각각 유일하게 유지한다. Toss 취소 사유에는 환불 멱등키를 포함해 같은 결제에서 금액이 같은 취소가 여러 건 생겨도 해당 환불 요청의 결과만 식별한다. 8회권 환불은 `refunds.pass_purchase_id`로 추적한다. PG 환불 호출은 환불 요청을 만든 부모 트랜잭션이 커밋된 뒤 별도 executor에서 실행한다. 실행되지 못한 `REQUESTED`, 재시도 시각이 지난 `RETRYABLE`·`RECONCILIATION_REQUIRED`, 1분 이상 멈춘 `PROCESSING`은 매분 최대 10건씩 자동 복구한다.
- PG 승인 후 도메인 생성이 실패하면 `refunds.payment_attempt_id`로 보상 환불을 남긴다. 보상 환불의 일시 실패와 결과 불명 상태에서는 결제 시도를 `COMPENSATION_REQUESTED`로 유지하고, 명시적 최종 실패만 `COMPENSATION_FAILED`로 전이한다. 모든 환불 재처리는 최초 `refunds.idempotency_key`를 재사용한다.
- PG 승인 상태 또는 보상 환불 요청을 저장하는 트랜잭션까지 실패해 결제 시도가 `PROCESSING`·`RETRYABLE`·`APPROVED`에 남으면, 1분 경과 후 매분 45초에 최대 10건씩 자동 복구한다. `PROCESSING/RETRYABLE`은 기존 `orderId` 멱등키로 confirm을 재확인하고, `APPROVED`는 PG 재호출 없이 도메인 생성을 재개한다. 마지막 복구 시각을 저장해 1분 backoff와 후보 순환을 보장하므로 사용자 confirm 재호출은 자동 복구의 필수 조건이 아니다. 단, 생성 후 14일이 지난 유료 미확정 PG 호출은 다시 승인 요청하지 않고 `RECONCILIATION_REQUIRED`로 격리하며, PG를 호출하지 않는 0원 결제는 기간과 무관하게 내부 처리를 재개한다.
- Toss의 `PAYMENT_STATUS_CHANGED` 웹훅은 `tosspayments-webhook-transmission-id`를 유일키로 한 번만 저장한다. 알려진 결제의 상태 변경은 매분 기존 PG 대사를 실행하며 웹훅 본문만으로 승인·실패를 확정하지 않는다.
- 운영자는 `RECONCILIATION_REQUIRED` 결제를 관리자 화면에서 조회하고 저장된 `orderId`로 Toss 상태 조회를 실행한다. `DONE`이면 저장된 paymentKey·orderId·금액 일치 확인 후 기존 fulfillment를 재개하고, Toss가 `NOT_FOUND_PAYMENT`로 결제 미존재를 명시한 경우에만 `FAILED`로 확정한다. 다른 404나 조회 결과가 불명확하면 상태를 그대로 유지한다. 대사 조회 중에는 DB 트랜잭션을 열지 않는다.
- Toss 승인 응답의 `receipt.url`은 결제 시도에 보존하고 결제 완료·상태 조회, 주문 상세·회원 예약 상세·8회권 목록/상세에서 소유권 확인 후 제공한다. 회원에게 가져온 비회원 거래도 현재 소유권으로 조회한다. 마이페이지에서 영수증을 새 창으로 다시 열 수 있으며 0원·과거 미기록·영수증이 없는 결제는 `null`로 반환하고 버튼을 표시하지 않는다. 8회권 영수증은 목록 단위로 일괄 조회한다.
- 매시간 최근 7일의 Toss 정산을 `soldDate` 기준, 페이지당 최대 5,000건으로 조회한다. 승인 정산은 `paymentKey`·`orderId`·금액을 로컬 결제 시도와, 취소 정산은 취소 `transactionKey`·금액을 로컬 환불 완료 이력과 비교한다. 정산 전용 HTTP 풀은 공식 최대 처리 시간에 맞춰 60초 응답 상한과 최대 연결 2개를 사용한다. 거래키별 최신 대사 결과를 `payment_settlements`에 upsert하고 `MATCHED`가 아닌 건은 관리자 `GET /api/v1/admin/payment-settlements/issues`와 오늘 할 일 화면에 표시한다.
- 예약·8회권·결제 시도 보상과 주문의 전액 취소 원인은 각각 환불 요청 한 건만 가진다. 배송·픽업 뒤 부분 환불은 주문 클레임별 한 건을 가지며 누적 품목 상한을 넘지 않는다. 모든 재시도는 새 이력을 만들지 않고 기존 환불 행과 멱등키를 사용한다.
- 환불이 `RECONCILIATION_REQUIRED`이면 cancel을 바로 재호출하지 않고 PG 결제의 취소 내역을 조회한다. 취소 사유의 멱등키, 금액, 완료 상태, 거래 식별자가 모두 해당 요청과 일치하면 성공으로 화해하고, 해당 멱등키의 취소가 없으며 미취소가 명확할 때만 `RETRYABLE`로 돌려 다음 실행에서 같은 멱등키로 cancel한다. 모순되거나 조회할 수 없는 결과는 대사 필요 상태로 유지한다.
- 주문 거절·예약 취소·8회권 정산 완료와 PG 환불 완료는 구분한다. 시작 응답은 로컬 상태 변경과 `REQUESTED` 이력 접수를 뜻하며, 고객은 소유권이 검증된 예약·주문 상세 또는 8회권 목록·상세의 환불 금액과 상태로, 운영자는 `refundId` 단건 조회로 실제 결과를 확인한다.
- 상태 변경형 대량 배치는 ID 키셋으로 끝까지 순회해 앞 페이지의 반복 실패가 뒤 후보를 막지 않게 한다. 개인정보 보존 배치는 삭제 소스별로 실패를 격리하고 고정된 소스 key로 결과를 합산해 한 소스 장애 때문에 나머지 보존 작업을 건너뛰지 않는다. 환불 복구는 마지막 복구 선점 시각이 없거나 가장 오래된 요청부터 순환시켜 반복 실패하는 앞 10건이 뒤 요청을 계속 막지 않게 한다. 실행 결과·항목 결과·소요 시간·마지막 정상 완료 시각을 메트릭으로 남기고 부분 실패, 결제·환불 복구 배치, 시간 단위 주문·픽업·예약/8회권 리마인드 배치와 일 단위 만료·보존 배치의 정체를 알림으로 감시한다. 예약 D-1·당일 및 8회권 만료 임박 알림은 이미 같은 이벤트·aggregate 종류·aggregate ID의 outbox가 있는 대상을 후보에서 제외하고 ID 키셋으로 보충해, 예정 시각에 서버가 중단됐어도 각 메시지 의미가 유지되는 남은 유효 구간에 한 번만 접수한다. 예약 리마인드 키는 비회원 기록이 회원에게 귀속돼도 바뀌지 않는다.
- 이미지 저장소 사용량은 5분마다 바이트 단위 gauge로 갱신한다. 5Gi PVC의 80%를 10분간 넘거나 갱신이 실패하거나 마지막 정상 갱신 후 15분이 지나면 운영 경보를 보낸다.
- 결제 수동 대사, 환불과 알림 outbox는 DB backlog 건수와 가장 오래 지연된 처리 기준 시각을 15초마다 집계한다. 결제 대사는 `RECONCILIATION_REQUIRED`의 마지막 confirm 실행 시각, 환불은 `REQUESTED=created_at`, `PROCESSING=processing_at`, 재시도·대사 필요 상태는 `next_attempt_at`, 알림은 `PENDING=next_attempt_at`, `PROCESSING=locked_at`을 사용한다. 미래 재시도 예정 시각의 age는 0으로 두므로 정상 백오프는 정체로 보지 않는다. 스냅샷 조회가 실패하면 기존 값을 0으로 덮지 않고 마지막 정상 값과 갱신 지연을 유지하며, 결제 대사·환불 조치 필요 상태·복구 정체·알림 pending/processing 정체·스냅샷 갱신 중단을 별도 경보로 감시한다.
- 업무 알림은 메모리 event counter가 아니라 승인 대기 주문과 예약 취소 후속 작업의 DB backlog를 기준으로 유지한다. 예약 확정과 후속 작업 없는 취소는 관리자 예약 일정에서 확인하고, 승인 대기 주문은 24시간 승인 마감 6시간 전부터 별도 critical 경보를 보낸다.
- 운영 readiness는 애플리케이션 상태뿐 아니라 MySQL과 Redis health를 포함한다. 필수 저장소가 준비되지 않으면 k3s가 app과 관리 포트를 ready endpoint에서 제외하고 Prometheus의 app down 경보가 이를 감지한다.
- Prometheus, Alertmanager, Grafana는 각각 Retain PVC를 사용하며 Grafana는 외부 Ingress 없이 cluster 내부 Viewer로만 제공한다. HTTP 5xx는 충분한 요청량에서는 전체 요청 대비 비율, 저트래픽에서는 일정 시간의 오류 건수로 나눠 경보를 판단한다.
