## 1. 내 주문·예약·8회권 전체 이력 검색·정렬

- **검토 당시:** [회원 조회 API 호출](../../../frontend/src/features/my/api.ts)은 커서와 크기만 전달해 20건씩 가져온다. [내 주문](../../../frontend/src/pages/MyOrdersPage.tsx), [내 예약](../../../frontend/src/pages/MyBookingsPage.tsx), [내 8회권](../../../frontend/src/pages/MyPassesPage.tsx)은 가져온 배열에만 검색·필터·정렬을 적용한다. 주문·예약의 상태 선택지도 가져온 데이터로 만든다. 화면에 이 범위를 안내하지만 전체 이력을 찾는 기능은 아니다.
- **영향:** 21번째 이후에 있는 주문 번호를 검색하면 더 보기를 누르기 전에는 결과가 없다. 오래된 주문순·예약일 빠른순·만료 임박순도 아직 가져오지 않은 거래와 비교하지 않는다.
- **구현 결과:** 세 목록에 검색어·상태·정렬 조건을 서버까지 전달하고, 조건을 적용한 전체 결과를 페이지로 나눈다. 조건을 바꾸면 기존 커서를 초기화하고 상태 선택지는 현재 페이지 데이터에 의존하지 않게 한다. 구매 당시 상품명 검색과 목록의 상품명·옵션 표시도 구현했다. 기본 API 정렬·기존 커서·배열 응답은 유지한다.
- **검증 범위:** 첫 페이지 밖의 거래 검색, 페이지 경계를 넘는 정렬, 조건 변경 후 첫 페이지 조회, 본인 거래만 조회되는지 확인한다. 조회를 바꾸더라도 주문·예약·환불 처리 정책은 그대로 유지한다.

## 2. 상품 검색·필터 상태 복원

- **검토 당시:** [상품 목록](../../../frontend/src/pages/ProductListPage.tsx)은 검색어·유형·카테고리·정렬을 컴포넌트 상태로만 관리한다. [공개 상품 경로의 서버 조회](../../../frontend/src/routes/public/products.tsx)도 URL 검색 조건을 읽지 않는다.
- **영향:** 상세를 보고 목록에 다시 진입하거나 새로고침하면 검색 조건이 초기화된다. 특정 카테고리·검색 결과를 링크로 공유할 수도 없다.
- **구현 결과:** 기존 검색 조건을 URL에 기록하고 첫 화면의 서버 조회와 브라우저 조회가 같은 조건을 사용하게 한다. 필터 복원 방식은 [회원 목록 필터](../../../frontend/src/features/my/useMyListFilters.ts)의 기존 사용 방식을 참고한다.
- **검증 범위:** 검색 결과에서 상세 이동 후 뒤로 가기, 새로고침, 검색 링크 직접 진입에서 같은 조건·결과가 보이는지 확인한다. 검색 노출 기준은 [공개 페이지 SSR ADR](../../ADR/0045_공개_페이지_SSR과_SEO_전달_경계/adr.md)에 맞춘다.

## 3. 주문 후 배송지 수정

- **검토 당시:** [주문서 수령 정보](../../../frontend/src/features/order/FulfillmentForm.tsx)에서 주소를 입력하고 [배송 정보](../../../domain/src/main/java/com/personal/happygallery/domain/order/Fulfillment.java)에 암호화해 저장한다. 저장 후 배송지를 수정하는 API와 화면은 확인되지 않았다. [관리자 배송 API](../../../adapter-in-web/src/main/java/com/personal/happygallery/adapter/in/web/admin/AdminOrderShippingController.java)는 배송 준비·출발·완료 처리를 제공한다.
- **영향:** 결제 후 주소 오입력을 발견해도 고객과 운영자가 서비스 안에서 바로잡을 수 있는 동선이 없다.
- **구현 결과:** 회원과 소유권을 확인한 비회원에게 배송 준비 시작 전 수정 기능을 제공한다. 배송 준비와 주소 수정이 동시에 실행되면 같은 주문을 잠가 허용 여부를 확정하고, 변경 전후 주소·처리자·시각을 기존 개인정보 보호 방식에 맞춰 보존한다. 승인 대기·이행 대기·제작 중·지연 동의 대기·지연 수락 상태에서 허용하고, 이행 정보 버전 충돌은 409로 거절한다. 변경 이력도 데이터 키 회전 대상에 포함한다.
- **확인할 동작:** 다른 고객의 주소 수정 거절, 배송 준비와 수정의 동시 요청, 기존 주문 금액·상품·수령 방식 보존을 확인한다.
- **추가 구현:** 회원 기본 배송지 한 개 저장·삭제와 주문서에서 불러오기를 제공한다. 기본 주소 변경은 과거 주문 주소에 영향을 주지 않는다.

## 4. 품절 전 재고 부족 안내

- **검토 당시:** [관리자 품절 목록](../../../frontend/src/features/admin-product/OutOfStockProductSection.tsx)은 판매 중 기성품 또는 활성 옵션 조합의 수량이 정확히 0일 때만 표시한다.
- **영향:** 1~2개 남은 상품을 미리 보충할 작업 목록이 없어 운영자가 재고 화면을 직접 확인해야 한다. 실제 품절 빈도는 운영 기록으로 확인해야 한다.
- **구현 결과:** 상품 또는 옵션 조합별 최소 보유 수량을 선택적으로 설정하고, 그 이하인 항목을 기존 오늘 할 일에서 재고 조정으로 연결한다. 기성품 수량과 주문제작 옵션 조합 수량을 각각 판단한다. 초기에는 외부 알림 채널을 추가하지 않고 운영 화면 표시부터 제공한다.
- **확인할 동작:** 기준 수량의 경계, 비활성 상품·조합 제외, 재고 보충 후 목록에서 빠지는지 확인한다. 스마트스토어 재고 차감·전송 순서는 변경하지 않는다.

## 5. 상품 옵션별 재입고 알림

- **검토 당시:** [상품 상세](../../../frontend/src/pages/ProductDetailPage.tsx)는 품절과 구매 가능 여부를 표시하지만 재입고 신청 흐름은 없다. 예약은 [빈자리 알림 서비스](../../../application/src/main/java/com/personal/happygallery/application/booking/DefaultBookingVacancyAlertService.java)와 영속 알림 처리가 이미 있다.
- **영향:** 품절 상품을 원하는 고객이 다시 방문해야 입고 여부를 알 수 있다. 구매 전환 효과는 신청·발송·후속 구매 수로 확인해야 한다.
- **구현 결과:** 우선 회원이 상품과 옵션 조합을 지정해 1회성 알림을 신청·해지한다. 해당 조합이 실제 판매 가능해졌을 때 기존 알림 Outbox를 통해 안내하고, 같은 신청에 중복 발송하지 않는다. 예약 빈자리 알림의 신청·중복 방지·해지 처리 방식을 참고하되 상품 재고 판단은 상품 영역에 둔다.
- **검증 범위:** 다른 옵션의 입고로 오발송하지 않는지, 비활성·삭제된 조합과 해지된 신청에 발송하지 않는지, 재입고 재처리 시 중복 알림이 없는지 확인한다. 알림은 구매 우선권이나 재고 예약을 보장하지 않는다고 표시한다.

## 6. 단체·기관 수업 문의 접수·처리 상태

- **검토 당시:** [단체 수업 화면](../../../frontend/src/pages/GroupClassesPage.tsx)은 네이버톡톡·전화·카카오톡 ID 안내로 연결한다. 별도의 [회원 1:1 문의 입력](../../../adapter-in-web/src/main/java/com/personal/happygallery/adapter/in/web/customer/dto/CreateInquiryRequest.java)은 제목·본문만 받고 단체 수업 조건이나 상담 진행 상태를 구조화하지 않는다.
- **영향:** 인원·장소·희망 일정과 견적·확정 여부를 이 서비스 밖에서 관리해야 한다. 문의 누락이 실제로 발생하는지는 상담 운영 기록으로 확인해야 한다.
- **구현 결과:** 기관명·담당 연락처·인원·희망 일정·장소·관심 수업을 접수하고 관리자에게 접수→상담 중→확정/종료 상태를 제공한다. 외부 채널로 받은 상담도 관리자가 등록할 수 있게 하면 기존 운영 방식을 이어갈 수 있다. 온라인 견적 결제나 일반 예약 자동 생성은 다음 범위로 둔다.
- **검증 범위:** 본인 조회, 연락처·메모 암호화와 키 교체, 상담 상태·버전 충돌, 탈퇴 삭제, 회원·비회원 접수와 관리자 외부 등록·상담 저장을 확인한다.

## 기존 범위와 문서 반영

- [범위 밖 문서](../../PRD/0003_범위_밖/scope.md)의 다중 공방 입점, POS 실시간 연동, 상품+예약 번들 결제, 추천·커뮤니티, 이메일·앱 푸시 채널은 이번 우선 제안에 포함하지 않는다.
- 1·2번 구현은 PRD-0001·PRD-0004, README, ADR-0031·ADR-0045에 반영했다. 회원 조회 API는 OpenAPI와 생성 TypeScript를 함께 갱신했다. 3~6번도 PRD·API 계약·관련 ADR과 생성 TypeScript에 반영했다.
- 후속 기능까지 포함해 전체 사용 사례 통합 테스트 432개, API 계약 295개, 보안 경계 웹 테스트 20개, 계층 규칙 9개가 통과했다. 변경 API의 REST Docs·OpenAPI·생성 TypeScript 일치, 보안 필터, 공통 알림·계층 규칙, 프론트 빌드·정적 검사와 브라우저의 검색·배송지 수정·재고 기준·재입고 신청/해지·단체 문의 접수/상담 흐름도 확인했다. 운영 데이터나 배포된 서비스의 성능을 측정한 결과는 아니다.

## 후속 검토에서 추가한 기능

- 상품·클래스 찜 저장·해제와 내 정보의 종류별 페이지 목록. 중지된 항목 표시·탈퇴 삭제.
- 단체 문의 다음 연락일 저장·해제와 관리자 오늘 할 일 조회. 종료 시 연락일 해제, 변경 이력 기록.
- 상품·옵션별 재입고 알림 대기 인원 조회. 해지·발송 완료·탈퇴 등 제외, 개인정보 없이 재입고 우선순위 판단에 활용.
- 2026-09-05 로컬 `127.0.0.1:8080` 상품 목록 API는 403을 반환해 실제 상품 JSON의 크기·개수·응답 시간을 측정하지 못했다. 전체 상세 조회가 필요한 주문서도 있으므로, 카드용 조회 분리는 실제 측정 후 결정한다.

후속 화면은 주문 검색, 기본 배송지 저장·주문서 불러오기·삭제, 찜 저장·종류별 조회·해제, 단체 문의 접수·상담 연락일, 재입고 알림·대기 인원 조회까지 브라우저에서 확인했다. 프론트 빌드·정적 검사·생성 API 일치 검사도 통과했다.

## 추가 사용 흐름 개선 결과

- 알림 전체 목록과 읽지 않은 알림 필터를 제공한다. 이전 페이지 조회, 개별·모두 읽음과 필터 URL 복원을 확인했다.
- 내 정보는 최근 내역과 관리 메뉴를 표시하고 찜·배송지·재입고 및 빈자리 알림·단체 문의를 개별 회원 화면으로 옮겼다. 이전 페이지 내부 링크도 새 화면으로 연결한다.
- 회원은 확정 전 본인 단체 문의의 일정·인원을 수정하거나 취소한다. 오래된 화면은 최신 문의를 다시 불러오도록 안내하며, 고객 변경 기록만 본인에게 공개한다. 로컬 관리자 메모도 비공개로 유지한다.
- 관리자는 접수 번호·경로·접수 기간을 함께 검색한다. 종료일 마지막 시각과 페이지 이동, 검색 초기화를 확인했다.
- 회원·비회원 주문 상세에서 현재 가격·옵션·재고와 기존 장바구니 수량을 확인해 다시 담는다. 변경 옵션과 과거 각인 문구는 재선택을 안내하고 같은 요청의 실패 재시도는 기존 멱등키를 유지한다.
