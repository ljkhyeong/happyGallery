# ADR-0047: 스마트스토어 주문·재고 양방향 동기화

**날짜**: 2026-08-29
**상태**: 승인됨

**갱신**: 2026-08-31

---

## 맥락

해피갤러리는 자사 주문뿐 아니라 오프라인 판매와 관리자 조정으로도 재고가 바뀐다. 로컬 최신 재고를 스마트스토어에
절대값으로 보내기만 하면 스마트스토어에서 판매된 수량이 내부 재고에 반영되지 않고, 다음 전송에서 판매 전 수량으로
되돌아갈 수 있다. 주문 수집을 재고 트랜잭션 안에서 실행하면 외부 지연 동안 DB 잠금을 오래 잡는 문제도 생긴다.

## 결정

### 1. 내부 재고를 운영 원장으로 유지하고 채널 주문을 먼저 반영한다

- 관리자는 공식 상품 목록 API에서 스마트스토어 상품을 선택해 `originProductNo`를 저장한다. 주문제작 상품은 원상품 상세 API의 옵션 조합명·가격·재고를 확인하고 내부 옵션 조합별 네이버 옵션 `id`를 선택한다.
- 기성품은 상품 단위 재고를 네이버 멀티 상품 변경 API의 `STOCK` 절대값으로 보낸다.
- 주문제작 상품은 상품 편집 응답에 표시되는 현재 조합에 네이버 옵션 `id`를 매핑한다. 현재 판매 중지 조합도 포함하고, 과거 주문 보존용 조합의 신규 매핑은 요구하지 않는다.
- 매핑 저장은 상품 정보 수정과 같은 상품 행 잠금 뒤 현재 조합을 확인한다. 옵션 구조 변경으로 사라진 연결과 같은 조합의 원격 옵션 번호를 바꾸기 전 연결은 `retired=true`로 보존해 재고 0개를 계속 전송한다. 매핑이 없던 과거 행은 전송 대상이 아니다.
- 현재 조합과 보존된 과거 매핑을 한 원상품의 옵션 재고 변경 요청으로 함께 전송한다. 과거 주문 환불로 내부 재고가 복구되어도 과거 원격 옵션에는 0개만 보내며, 현재 조합이 그 원격 옵션 번호를 재사용하면 과거 연결을 제거한다.
- 전체 연동 해제는 보존된 매핑도 삭제한다. 원상품 번호 변경은 기존처럼 이전 원상품 연결을 해제하며, 이전 원상품의 판매 상태는 스마트스토어에서 별도로 정리한다.
- 매핑 저장·조회 응답은 현재 연결만 반환한다. 과거 연결의 상품·SKU 참조는 유지하므로 이미 수집한 주문을 변경하지 않으며, 이전 원격 옵션의 주문도 보존된 연결로 처리한다. 자동 재고 전송과 가격·상태 미리보기는 과거 연결을 포함하되 현재 SKU 재고가 복구되어도 항상 0개로 처리한다.
- V166은 `retired`를 추가하고 과거 연결의 생성 키만 NULL로 바꾼다. 현재 SKU당 한 연결과 원격 옵션당 한 연결의 제약은 유지한다. 배포 전 기존 연결은 `retired=false`로 보존하며, 현재 옵션 구조에서 사라진 SKU는 기존 조회 규칙대로 0개를 전송한다. 매핑을 다시 저장하면 과거 연결로 명시한다.
- 과거 연결이 저장된 후 구버전은 같은 SKU의 이전 옵션에도 실제 재고를 보낼 수 있다. V166 배포는 구버전과 혼용하지 않으며, 구 이미지로만 롤백하지 않고 수정 버전으로 전진 배포한다. 이미 변경 전 코드가 삭제한 연결은 자동 복원할 수 없어 스마트스토어에서 남은 재고를 확인한다.
- 스마트스토어 변경 주문을 매분 50초에 수집해 내부 재고를 먼저 차감·복원하고, 매분 55초 재고 전송이 변경된 절대 수량을 다시 네이버에 맞춘다.
- 실행 시각 차이만으로 수집 완료를 가정하지 않는다. 자동 전송 대상이 있거나 관리자가 수동 상품 반영을 요청하면 주문 수집을 한 페이지 실행하고, 현재 조회 시점까지 마지막 페이지를 처리했는지 함께 반환한다. 비활성·실패·다른 실행의 선점·남은 페이지·24시간 구간 이후의 미수집 기간이 있으면 외부 재고 쓰기를 보류한다. 선점이 바뀌어 완료 결과를 저장하지 못한 실행도 전송을 허용하지 않는다.
- 수집 보류 시 자동 전송은 기존 `BatchResult`에 사유를 남기고 상품별 요청·실패 횟수를 유지한다. 수동 반영은 기존 `409 CONFLICT`를 반환한다. 수집 완료 이후 상품 스냅샷을 읽어 수집 전 수량을 재사용하지 않는다. 정기 수집의 cron과 배치 응답 형식, DB 스키마는 바꾸지 않는다.
- `MAPPING_REQUIRED`, `STOCK_SHORTAGE`, `STATUS_REVIEW` 주문이 있는 원상품은 전송 직전에 다시 확인해 해당 상품만 보류한다. 아직 내부 상품에 매핑되지 않은 주문도 원상품 번호로 찾는다. 자동 전송은 실패 횟수를 올리지 않고 다음 확인 시각을 1분 뒤로 옮겨 보류 상품이 대기 목록 앞을 계속 차지하지 않게 한다. 관리자 재처리로 실제 재고가 차감되면 기존 동기화 요청이 이 대기를 해제한다. `RETURN_REVIEW`는 반품 재고를 아직 복원하지 않았으므로 전송 보류 사유가 아니다.
- 이는 수집 실패·미완료와 이미 확인된 재고 미반영 주문을 차단하는 경계다. 조회 종료 시각 이후 네이버에서 새로 발생한 주문까지 두 판매 채널이 동시에 재고 예약하는 보장은 하지 않는다.
- 채널 주문은 자사 결제·승인 상태 머신에 넣지 않고 `smartstore_product_orders` 별도 원장에 저장한다.

### 2. 네이버 상품 주문 번호와 옵션 아이템 번호를 안정 식별자로 사용한다

- 네이버 `productOrderId`를 채널 주문 멱등 키로 사용한다.
- 기성품은 `originalProductId`와 옵션 없는 상품 매핑을 연결한다.
- 옵션 상품은 주문 상세의 `itemNo`를 등록된 네이버 옵션 `id`와 연결한다. 표시용 `productOption` 문자열은 매핑 키로 사용하지 않는다.
- 주문 상세의 `delivery`는 공식 응답과 동일한 단일 객체로 읽고, 배송 정보가 아직 없으면 택배사·운송장을 비워 둔다.
- 직접입력형 옵션은 SKU를 나누지 않으므로 선택 조합의 옵션 ID에 포함된 동일 재고를 사용한다.
- 매핑이 없거나 비활성화됐으면 상품명·옵션명으로 추측하지 않고 `MAPPING_REQUIRED`로 관리자에게 보여 준다.

### 3. 주문별 현재 차감 수량으로 부분취소와 재전송을 멱등 처리한다

- 상품 주문마다 `inventory_applied_quantity`를 저장한다.
- `PAYED`, 배송 중·완료, 구매 확정, 교환 완료, 반품 완료 상태의 목표 차감 수량은 `remainQuantity + completed_return_quantity - restored_return_quantity`이다. 검수 대기와 판매 불가 반품은 계속 차감 수량에 포함된다.
- 목표 수량이 기존 적용 수량보다 크면 차이만 차감하고, 부분·전체 취소로 작아지면 차이만 복원한다. 잔여 주문 수량 감소만으로 반품을 취소로 판단하지 않는다.
- `CANCELED`, `CANCELED_BY_NOPAYMENT`, `PAYMENT_WAITING`은 목표 계산에서 잔여 주문 수량을 0으로 두되, 아직 복원하지 않은 완료 반품 수량은 유지한다.
- 같은 변경을 다시 수집해 목표 수량과 적용 수량이 같으면 재고를 변경하지 않는다.
- 내부 재고 부족은 주문 수집 자체를 버리지 않고 `STOCK_SHORTAGE`로 저장하며 관리자가 재고를 조정한 뒤 다시 시도한다.
- 기성품·옵션 재고의 단일 SKU `tryDeduct`가 잠금 차감 중 발생한 부족 예외를 서비스 내부에서 `false`로 바꾼다. 부족 예외가 Spring 트랜잭션 경계를 넘어 전체 주문 기록을 롤백시키지 않으며, 성공한 차감과 주문 적용 수량은 여전히 같은 트랜잭션에 저장한다. 일반 주문의 다중 SKU 차감은 기존 예외·전체 롤백 규칙을 유지한다.

### 4. 반품은 판매 가능 여부를 확인한 뒤 복원한다

- `completedClaims`의 `RETURN`·`RETURN_DONE`과 `currentClaim.return`의 완료 반품을 `claimId`로 중복 제거해 누적 완료 수량을 집계한다. `DELIVERING` 등 일반 상태인 부분반품도 동일하게 처리한다. 현재 클레임이 이후 취소로 바뀌어도 완료 이력에서 이전 반품을 유지한다.
- 반품 번호·수량·완료일이 없거나 반품 완료 상태인데 완료 수량을 확인할 수 없으면 주문 상세 수집을 실패 처리한다. 변경 피드 커서를 유지하며, 잔여 수량 감소를 취소로 추측해 재고를 복원하지 않는다.
- `completed_return_quantity`는 누적 완료 반품 수량이며 뒤이은 수집으로 줄이지 않는다. 미검수 수량은 `completed_return_quantity - reviewed_return_quantity`이고, 재고 반영이 끝난 주문에 미검수 수량이 있으면 `RETURN_REVIEW`로 표시한다. 매핑 누락·재고 부족은 해당 확인 사유를 먼저 유지한다.
- 관리자는 실물 검수 뒤 미검수 수량을 재고에 복원하거나 판매 불가로 판단해 복원 없이 종료한다. 두 선택 모두 `reviewed_return_quantity`를 완료 반품 수량까지 올리고, 복원한 경우에만 `restored_return_quantity`를 늘린다. 검수 완료 기록과 재고 복원은 같은 주문 잠금·트랜잭션 안에서 반영한다. 재수집·재시도는 검수를 다시 열지 않으며 이후 취소나 추가 반품으로 판매 불가 반품을 함께 복원하지 않는다.
- 목록은 `pendingReturnQuantity`와 `returnReviewVersion`을 반환한다. 버전은 완료·검수 누적 수량으로 계산하고, 이관 전 행은 기존 차감·잔여·검수 기록을 사용한다. 추가 DB 컬럼은 필요하지 않다. 미검수 수량만 비교하면 이전 2개 검수 뒤 새로 들어온 2개를 구분하지 못하므로 누적 수량을 함께 비교한다.
- 확인창은 열 때의 상품 주문·미검수 수량·버전을 보존하며 목록 자동 갱신으로 바꾸지 않는다. 처리 요청의 필수 `reviewVersion`을 주문 잠금 안에서 비교해 달라졌으면 재고·검수 기록을 바꾸지 않고 409를 반환한다. 화면은 확인창을 닫고 최신 목록을 조회하되 자동으로 다시 처리하지 않는다.
- `reviewVersion` 없는 기존 v1 검수 요청은 400으로 거절한다. 누락 시 현재 버전을 대신 넣으면 검수하지 않은 추가 반품까지 복원할 수 있으므로 호환 기본값을 제공하지 않는다. 관리자 화면·서버·OpenAPI를 함께 배포하고 이전 화면은 새로고침한다. 이 안전 수정의 v1 예외는 ADR-0016에 명시한다.
- V168은 기존 행의 완료 반품 수량을 NULL로 두고, 검수·복원 수량을 0으로 추가한다. DB 이관은 기존 재고·차감 수량·확인 사유·주문 변경 시각을 바꾸지 않는다. V167의 검수 당시 잔여 수량은 전환 전 기록을 읽기 위해 남긴다.
- 기존 주문의 다음 변경 수집에서는 이전 수집 시각까지 완료된 반품 이력, 기존 차감·잔여 수량, 검수 대기 여부로 누적 수량을 초기화한다. 상세 응답이 변경 피드 시각보다 최신일 수 있으므로 잔여 수량이 같으면 현재 완료 이력을 이전 수집분으로 본다. 기존 검수 결과를 옮긴 뒤 V167 필드는 비우며, 이후 추가 반품은 새 수량만 검수한다. 아직 전환하지 않은 주문의 재시도·검수는 기존 기록을 사용한다.
- 과거 오류로 이미 자동 복원된 부분반품은 DB 이관에서 일괄 차감하지 않는다. 판매 가능 여부와 실제 보유 재고를 알 수 없으므로 관리자가 과거 부분반품과 실물 재고를 확인해 조정한다.
- 구버전은 누적 반품 수량을 읽지 않으므로 주문 수집·검수 처리 서버를 신버전으로 함께 전환한다. 구 이미지 단독 롤백은 반품을 취소로 계산하거나 완료 검수를 다시 열 수 있어 수정 버전으로 전진 배포한다.
- 교환 완료만으로는 별도 재고를 증감하지 않는다.
- 네이버가 새 주문 상태를 추가하면 임의로 재고를 바꾸지 않고 `STATUS_REVIEW`로 남긴다.

### 5. 변경 피드 커서와 외부 호출을 재고 잠금에서 분리한다

- `smartstore_order_sync_state`의 단일 행을 잠가 `lastChangedFrom`, `moreSequence`, 처리 시작 시각과 마지막으로 관측한 연동 활성 여부를 관리한다.
- 최대 24시간 구간과 300건 페이지를 네이버 변경 피드 계약대로 조회하고, 상품 주문 상세를 모두 받은 경우에만 커서를 전진시킨다.
- 중간 실패는 커서를 유지해 같은 구간을 다시 읽고, 이미 성공한 주문은 적용 수량 비교로 중복 변경을 막는다.
- 5분 이상 끝나지 않은 선점은 다음 실행이 다시 가져갈 수 있다.
- 주문·정산 수집의 선점 시각은 주입된 `Clock`에서 읽은 뒤 마이크로초로 절삭한다. `DATETIME(6)` 저장값과 반환한 선점 시각을 같게 유지해 완료·해제가 정상 실행된다. 재선점 이후 이전 실행이 완료하거나 해제하지 못하도록 시각 비교는 유지한다.
- 마이그레이션에서 커서를 배포 시각으로 초기화하고 연동이 꺼진 동안 현재 시각으로 이동해, 활성화 전에 수동 반영한 과거 주문을 소급 차감하지 않는다.
- 연동 중지 기간 처리도 기존 `claim`의 5분 만료 판정을 사용한다. 선점이 없거나 시작 후 5분 이상 지났으면 같은 트랜잭션에서 선점·완료해 조회 시작점을 현재 시각으로 옮기고 `moreSequence`와 처리 시작 시각을 비운다. 5분 미만인 실행은 건드리지 않으며, 만료된 이전 실행의 완료 요청은 커서를 되돌리지 못한다.
- 비활성 배치는 상태에 `integration_enabled=false`를 남긴다. 이후 활성 설정으로 시작한 애플리케이션은 생성 시각을 보존하고 첫 선점에서 `false → true` 전환을 확인해 조회 시작점을 그 생성 시각으로 옮긴다. 첫 배치 시각으로 옮기지 않으므로 활성화 이후 첫 배치 전 주문은 버리지 않는다. 이미 활성 상태인 재기동은 기존 커서를 유지한다.
- V169의 활성 여부는 기존 설치가 활성·비활성 중 어느 상태였는지 추측하지 않도록 NULL로 추가한다. 최초 관측이 활성이면 기존 커서를 유지한 채 활성로 기록하고, 비활성이면 중지 상태로 기록한다. 이후 전환부터 애플리케이션 시작 시각 경계를 적용한다.
- 외부 API 호출은 DB 트랜잭션 밖에서 수행하고, 각 상품 주문의 재고 변경만 짧은 트랜잭션과 기존 비관적 재고 잠금으로 처리한다.

#### 재고 전송의 삭제·재등록 구분

- 재고 동기화 행에는 요청 버전과 별개로 생성 시 UUID `generation`을 저장한다. 선점·완료·실패 처리에 함께 전달하며, 현재 행과 다르면 이전 응답을 새 요청의 성공·실패로 기록하지 않는다.
- 재등록 전 전송이 늦게 외부 수량을 덮을 수 있으므로 현재 행이 `PROCESSING` 또는 `SYNCED`이면 기존 `request(now)`로 최신 수량 보정 요청을 남긴다. 새 전송이 진행 중이어도 이미 외부에 적용됐을 수 있어 요청 버전을 올리며, 그 전송의 뒤늦은 완료는 보정 요청을 지우지 못한다. 외부 수량 반영 후 실패 응답도 같은 처리를 사용한다.
- 이미 `PENDING`이면 해당 요청이 최신 재고를 읽으므로 기존 대기 시각·실패 횟수를 유지한다. `FAILED`는 기존 관리자 재시도 정책을 유지한다. 비활성화·전체 해제 후 재등록하지 않아 행이 없으면 보정 요청을 새로 만들지 않는다. 원상품 번호를 바꾼 경우 이전 원상품을 별도로 정리하는 운영 규칙은 유지한다.
- V165는 기존 행에도 식별자를 채운다. 배포 시 구버전 재고 전송을 종료한 뒤 신버전으로 전환하며, 구버전과 혼용하면 이전 코드의 버전 단독 비교가 남으므로 이 보장을 할 수 없다.

### 6. 네이버 인증 정보와 토큰은 한 구성요소에서 관리한다

- OAuth2 Client Credentials 토큰은 `client_id + timestamp`를 네이버가 발급한 bcrypt salt 형식의 client secret으로 해시하고 Base64 URL 인코딩해 발급한다.
- 주문 조회와 재고 전송이 같은 메모리 토큰을 사용하고, 만료 60초 전에 갱신한다.
- `401`이면 한 번 강제 재발급 후 동일 요청을 다시 보낸다.
- client secret과 access token은 DB와 로그에 저장하지 않는다.

### 7. 가격과 판매 상태는 차이를 확인한 뒤 관리자가 반영한다

- 자동 재고 동기화는 계속 최신 절대 재고만 반영하며 상품 가격이나 판매 상태를 임의로 바꾸지 않는다.
- 관리자는 원상품 현재 값을 조회해 로컬 판매가·판매 상태·옵션가와 비교한 뒤 명시적으로 반영한다.
- 미리보기는 상품 버전·가격·판매 상태·원상품 번호·옵션 연결과 옵션가·사용 여부를 SHA-256으로 계산한 `previewVersion`을 반환한다. 연결 행 ID도 포함해 해제·재등록을 구분하고, 연결과 옵션은 고정된 순서로 계산한다. DB 버전 열이나 미리보기 저장소는 추가하지 않는다.
- 수동 반영은 같은 식별값을 요구한다. 수량 자체는 비교에서 제외해 주문 후에도 최신 수량을 쓰지만, 수량 변화로 판매 상태가 바뀌면 다시 비교한다. 기존 숫자 `productVersion` 계약은 제거하므로 서버와 화면을 함께 전환한다. 충돌 화면은 새 미리보기의 원상품 번호를 표시하고 자동 반영하지 않는다.
- 옵션가는 네이버 계약에 맞춰 상품 판매가와 전체 옵션 재고·옵션가·사용 여부를 한 번에 전송한다.
- 과거 보존 매핑은 수동 상품 반영에서도 재고 0개·추가금 0원·사용 불가로 처리한다. 자동 재고와 수동 상품 반영은 같은 현재 조합 조회와 매핑 조립 함수를 사용한다.
- 미리보기 행은 내부 SKU가 아니라 원격 `optionId`로 구분하고 원격 옵션 번호·이전 연결 여부를 표시한다. 매핑을 저장하면 비교 결과도 다시 조회한다.
- 기성품은 판매가와 현재 재고를 멀티 상품 변경 API로 함께 보내고, 재고를 고려한 판매 상태를 별도 상태 변경 API로 반영한다.
- 수동 외부 호출 종료 후 성공·실패와 관계없이 기존 `SmartStoreStockSyncQueuePort`로 최신 재고 재전송을 요청한다. 자동 전송이 먼저 완료돼도 늦은 수동 요청의 수량을 다음 배치에서 보정한다. DB 트랜잭션을 외부 호출 동안 유지하거나 별도 배치를 추가하지 않으며, 가격·판매 상태는 자동으로 재시도하지 않는다.

### 8. 채널상품 운영 정보는 네이버 원본을 실시간 사용한다

- 상품 목록에서 `originProductNo`와 `channelProductNo`를 함께 반환해 재고 매핑과 채널상품 대상 작업을 구분한다.
- 상품 검수 반려 목록은 로컬에 복제하지 않고 네이버 검수 API에서 실시간 조회한다. 관리자는 사유와 조치 방법을 확인하고 수정 뒤 복원 요청을 보내며, 복원 가능 상태를 로컬 규칙으로 다시 판정하지 않는다.
- 상품 공지사항은 네이버 목록·상세를 기준으로 등록·수정·삭제한다. 공지 적용은 선택한 `channelProductNo` 목록을 네이버에 전달하고 로컬 상품 상태를 변경하지 않는다.

## 결과

- 스마트스토어 판매가 내부 공유 재고에서 누락되지 않고, 다음 절대 재고 전송이 판매 수량을 되돌리지 않는다.
- 부분취소와 변경 피드 재전송이 주문별 적용 수량으로 한 번만 반영된다.
- 반품품의 판매 가능 여부는 자동 판단하지 않고 관리자 검수로 결정한다.
- 관리자는 주문 탭과 오늘 할 일에서 매핑 누락, 재고 부족, 반품 검수 주문을 확인하고 후속 처리할 수 있다.
- 활성화 이전 과거 스마트스토어 주문은 자동 소급하지 않는다.
- 가격과 상태는 자동 재고 배치에 섞이지 않아 관리자가 미리 확인한 범위만 채널에 반영된다.
- 숫자 식별자를 직접 옮겨 적지 않아 상품·옵션 매핑 오류 가능성이 줄어든다.
- 검수 반려와 상품 공지 상태가 로컬 복제 지연 없이 네이버 현재 상태와 일치한다.
