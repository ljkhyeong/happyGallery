# ADR-0016: API URI 버저닝 전략 도입

**날짜**: 2026-03-06  
**최종 갱신**: 2026-08-14
**상태**: Accepted

---

## 컨텍스트

API 버전 체계를 도입할 때는 기존 무버전 경로와 `/api/v1/**`를 한시적으로 병행했다.
현재 클라이언트와 문서가 `/api/v1/**`로 전환되어 무버전 호환 경로를 계속 유지할 이유가 없다.

또한 버저닝 규칙이 없는 상태에서 ad-hoc 경로(`v1_new` 등)가 생기면 운영/문서/테스트 일관성이 무너진다.

---

## 결정 사항

### 1. URI Versioning을 표준으로 채택한다

- 표준 API 경로: `/api/v1/**`
- 컨트롤러, 보안 필터, 클라이언트, 문서, 테스트는 `/api/v1/**`를 기준으로 작성한다.

### 2. 무버전 호환 경로는 제공하지 않는다

- 기존 무버전 경로(`/bookings`, `/passes`, `/products`, `/admin/**`)의 병행 제공을 종료한다.
- 컨트롤러 매핑과 보안 필터에는 버전 경로만 선언한다.
- 무버전 경로는 외부 API 계약으로 간주하지 않는다.

### 3. 브레이킹 변경은 `/api/v2/**`로 분리한다

- `v1` 계약을 깨는 변경은 `v2` 엔드포인트로 신규 제공한다.
- `v1`은 사전 공지된 deprecate 기간 후 제거한다.

배열 응답을 `{content,nextCursor,hasMore}` 객체로 바꾸는 것도 브레이킹 변경이다. 기존 목록의 무제한 조회를
제거할 때는 기존 경로를 명시적 최대 100건의 배열로 유지하고 같은 리소스의 `/page` 경로를 additive하게
추가한다. 현재 웹 클라이언트는 `/page`로 옮기되 기존 클라이언트의 JSON shape은 바꾸지 않는다.

---

## 결과 (트레이드오프)

| 항목 | 내용 |
|------|------|
| 장점 | 운영·보안·문서·테스트의 경로 기준이 `/api/v1/**` 하나로 통일된다 |
| 장점 | 별칭 누락으로 일부 경로가 다른 보안 체인에 매칭되는 위험을 없앤다 |
| 단점 | 무버전 경로를 사용하는 외부 클라이언트는 `/api/v1/**`로 전환해야 한다 |
| 대응 | 지원 경로를 API 계약 문서에 명시하고 이후 브레이킹 변경은 새 버전으로 분리한다 |

---

## 구현 반영

- 컨트롤러와 보안 필터는 `/api/v1/**`만 노출한다.
- 프런트엔드와 테스트도 `/api/v1/**`만 호출한다.
- 현재 HTTP 계약은 `docs/PRD/0004_API_계약/spec.md`를 기준으로 한다.
- 운영 공개 전 기준선에서 `/api/v1/me/cart/merge`의 `expectedCustomerId`를 필수로 추가한 변경은 배포된 외부 클라이언트가 없는 상태에서 서버·웹 클라이언트·OpenAPI를 같은 커밋으로 이동한 최초 공개 계약 보정이다. 운영 공개 뒤의 같은 필수값 추가는 본 ADR의 `/api/v2/**` 규칙을 따른다.
