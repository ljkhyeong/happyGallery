# ADR-0046: 주문제작 상품 옵션과 SKU 재고

**날짜**: 2026-08-27  
**상태**: 승인됨

**갱신**: 2026-08-31

---

## 맥락

주문제작 상품은 색상·크기처럼 정해진 값에서 고르는 옵션과 각인 문구처럼 고객이 직접 쓰는 제작 정보가 필요하다.
옵션 조합마다 제작 가능 수량과 가격이 다르므로 상품 단위 재고만으로는 품절과 주문 금액을 정확히 표현할 수 없다.
장바구니와 결제 이후에도 관리자가 옵션 이름·가격을 바꿀 수 있으므로 과거 주문은 당시 선택을 독립적으로 재현해야 한다.

## 결정

### 1. 옵션 그룹은 선택형과 직접입력형으로 구분한다

- `SELECT` 그룹은 관리자가 옵션값을 등록하며 필수 또는 선택으로 설정한다.
- `TEXT` 그룹은 안내 문구, 필수 여부, 최대 입력 길이와 추가 금액을 가진다.
- 상품 하나에 선택형은 최대 3개, 직접입력형은 최대 5개를 허용한다.
- 그룹명과 선택값은 25자 이하로 제한하고, API에서 사용하는 `groupKey`, `valueKey`는 표시명과 분리해 수정 뒤에도 식별자를 유지한다.

### 2. 선택형 옵션의 데카르트 곱을 SKU로 관리한다

필수 선택형 그룹은 모든 값, 선택 그룹은 미선택 값까지 포함해 가능한 조합을 만든다. 조합은 최대 500개이며,
각 `ProductVariant`가 SKU 코드, 추가 금액, 재고와 판매 여부를 소유한다. 선택형 그룹이 없는 주문제작 상품도
기본 조합 하나를 만들어 같은 재고 경로를 사용한다. 기성품은 기존 상품 단위 `Inventory`를 계속 사용한다.

관리자 상품 저장 시 서버가 요청한 그룹으로 가능한 조합을 다시 계산해 누락·중복·존재하지 않는 옵션값을 거절한다.
옵션 구조 변경으로 사라진 조합은 비활성화하고, 유지된 조합은 같은 선택 키 집합으로 식별해 기존 SKU 설정을 이어간다.
조합 키는 표시 순서가 아니라 옵션 키의 문자열 순서로 만든다. 선택 그룹의 미선택 값은 `groupKey=-`로 포함한다.

편집 조회도 저장과 같은 조합 키 생성 함수를 사용한다. 현재 그룹·값·필수 여부로 만들 수 없는 과거 조합은
편집 응답에서 제외하고, 현재 조합을 판매 중지한 행은 그대로 표시한다. 옵션 없는 상품에 선택형을 추가하거나
필수 여부를 바꾸고 그룹을 삭제해도 이전 기본·미선택 조합이 재저장 요청에 섞이지 않는다.

기존 SKU의 정보 수정 메서드는 가격·판매 여부만 받으며 수량을 받지 않는다. 재고 행 잠금은 유지하되 화면을
열었을 때의 과거 수량으로 덮어쓰지 않는다. 기본 조합도 같은 규칙을 따르고 수동 변경은 재고 조정 API의
이력·스마트스토어 동기화 경로를 사용한다. 신규 SKU만 최초 재고를 받으며, 기존 비활성 SKU를 재사용할 때도
남아 있는 재고를 보존한다. 관리자 상품 수정에서는 기존 조합 재고를 읽기 전용으로 표시한다.

### 2.1. V164 조합 키 전환

- V164는 저장된 조합 키의 각 `groupKey=valueKey`를 옵션 키 순으로 정렬한다. 임시 키를 거쳐 UNIQUE 충돌을 피하고 조합 번호·선택값·수량과 다른 테이블의 참조를 바꾸지 않는다.
- 표시 순서 차이로 같은 선택 조합이 여러 행에 있으면 활성 행을 우선하고, 같은 상태이면 최소 ID를 현재 조합으로 유지한다. 나머지는 `legacy-variant:{id}` 키와 비활성 상태로 보존하며 재고를 합치지 않는다.
- 과거 보존 행은 현재 상품 옵션 편집 목록에서 제외한다. 과거 주문의 재고 복구는 기존 번호를 계속 사용하며, 이미 비활성화된 장바구니 항목을 다른 번호로 자동 교체하지 않는다.
- 적용 중·적용 후 구 백엔드를 함께 실행하지 않는다. 구버전은 다시 순서 의존 키를 만들 수 있으므로 이전 이미지로만 되돌리지 않고 수정 버전으로 전진 배포한다. DB를 되돌려야 하면 배포 전 백업과 애플리케이션을 함께 복구한다.

### 3. 직접입력은 SKU가 아니라 제작 지시다

직접입력값은 SKU 재고를 나누지 않는다. 대신 서버가 필수 여부와 최대 길이를 검증하고, 장바구니 행은
`productId + variantId + 정규화된 직접입력값`으로 구분한다. 같은 SKU라도 각인 문구가 다르면 별도 행으로 담아
수량과 제작 지시가 섞이지 않게 한다.

### 4. 가격과 주문 조건은 서버가 확정한다

결제 prepare는 공개 요청의 금액을 신뢰하지 않고 현재 상품·옵션·SKU를 일괄 조회해
`상품 기본가 + 조합 추가금 + 직접입력 추가금`을 최종 단가로 계산한다. 같은 SKU의 여러 품목은 재고 요구량을
합산해 prepare에서 확인하고, confirm은 SKU 행을 정렬해 비관적 잠금한 뒤 차감한다.

prepare payload와 `order_items`에는 기본가, 조합 추가금, 직접입력 추가금, 최종 단가, variant ID와 SKU를 저장한다.
선택 그룹·값과 직접입력 문구는 `order_item_option_snapshots`에 표시 순서대로 복사한다. confirm은 현재 옵션 가격을
다시 읽지 않고 저장 스냅샷과 결제 시도 금액의 일치만 검증한다. 환불·거절·교환 재고 처리는 주문 항목에 저장한
variant ID로 동일 SKU를 복구하거나 다시 차감한다.

### 5. 기존 주문제작 상품을 기본 SKU로 이관한다

마이그레이션은 기존 주문제작 상품마다 `DEFAULT` variant를 만들고 기존 상품 재고를 그 SKU 재고로 옮긴다.
이후 주문제작 상품의 기존 `inventory.quantity`는 0으로 두어 상품 재고와 SKU 재고가 동시에 판매 가능 수량으로
계산되지 않게 한다. 기존 기성품과 과거 주문 항목은 변경하지 않는다.

## 결과

- 관리자는 네이버 스마트스토어와 유사하게 필수·선택 선택형 옵션, 직접입력 옵션과 조합별 가격·재고를 등록할 수 있다.
- 고객은 한 상품의 서로 다른 조합과 각인 문구를 여러 줄로 담고 주문할 수 있다.
- 옵션 이름과 가격이 변경되어도 주문 상세, 환불 금액과 복구할 SKU를 결제 당시 값으로 재현한다.
- 선택값이 늘면 조합 수가 곱으로 증가하므로 500개 상한 안에서 관리자가 조합별 재고와 판매 여부를 입력해야 한다.
