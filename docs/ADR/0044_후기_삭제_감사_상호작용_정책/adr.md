# ADR-0044: 후기 삭제·감사·상호작용 정책

**날짜**: 2026-08-09
**상태**: Accepted

## 배경

ADR-0043은 작성자가 후기 행을 삭제한 뒤 같은 완료 거래로 다시 작성할 수 있게 했다. 그러나 관리자가
부적절한 후기를 숨긴 뒤 작성자가 삭제하고 다시 작성하면 새 후기가 `PUBLISHED`로 생성되어 운영 조치를
우회할 수 있다. 운영 전에는 삭제 경험, 개인정보 최소화, 운영 증거 보존과 정상 재작성 허용을 함께
정의해야 한다.

또한 후기 요청 시점, 공식 답글, 별점 분포, 사진, 신고와 도움돼요 기능을 추가할 때 공개 캐시와 회원별
상태가 섞이지 않는 API 및 저장 경계가 필요하다.

## 결정

### 1. 작성자 삭제는 내용 비식별화와 원천 점유를 분리한다

- 작성자 삭제는 행을 제거하지 않고 `deleted_at`을 기록하며 본문·별점·공식 답글과 현재 행의 숨김 사유·
  처리 관리자·처리 시각을 지운다. 재작성 차단 표식과 별도 moderation·증거 이력만 보존한다.
- 한 번이라도 `HIDDEN`이 된 후기는 `recreation_blocked=true`를 단조 증가 값으로 유지한다. 재공개해도
  이 이력을 지우지 않는다.
- 한 번도 숨겨지지 않은 삭제 후기는 원천을 해제해 같은 주문 품목 또는 예약으로 다시 작성할 수 있다.
- 숨김 이력이 없고 신고·moderation·증거가 없는 삭제 tombstone은 `deleted_at`부터 30일이 지나면 기존
  개인정보 보존 배치가 100건 단위로 파기한다. 증거 정리를 먼저 실행한 뒤 tombstone을 정리한다.
- 숨김 이력이 있는 삭제 후기는 사용자 화면에서 삭제된 것으로 보이지만 원천을 계속 점유해 재작성을
  `409 REVIEW_RECREATION_BLOCKED`로 거절한다.
- 활성 후기와 재작성 차단 tombstone이 같은 원천을 동시에 점유하지 못하도록 DB 생성 열과 UNIQUE 제약을
  사용한다. 사전 조회는 오류 메시지를 위한 것이고 동시 요청의 최종 방어선은 DB 제약이다.
- 일반 목록, 집계와 상호작용은 `deleted_at IS NULL` 후기만 대상으로 한다.
- 신고·moderation·증거 테이블의 후기 FK는 `ON DELETE RESTRICT`로 두어, 애플리케이션 후보 조회가
  잘못되거나 정리 작업과 경합해도 보존 중인 자식 기록보다 부모 tombstone이 먼저 삭제되지 않게 한다.

### 2. 운영 상태 변경은 현재 상태와 별도 감사 이력으로 남긴다

- `PUBLISHED <-> HIDDEN` 실제 전이마다 이전 상태, 새 상태, 사유, 관리자와 시각을 append-only 감사 행으로
  기록한다.
- 현재 후기의 숨김 필드는 빠른 조회를 위한 현재 상태이고, 감사 행은 과거 판단을 복원하기 위한 이력이다.
- 신고 접수만으로 자동 숨김하지 않는다. 관리자가 신고를 `ACCEPTED` 또는 `REJECTED`로 결정하고 필요한
  숨김 전이는 별도 moderation action으로 남긴다.
- 신고 시 신고자, 사유, 선택 상세와 대상 후기를 고정해 중복 신고를 차단한다. 작성자는 자기 후기를
  신고하거나 도움돼요 표시할 수 없다.
- 후기 본문·평점·사진 묶음에는 별도 `content_revision`을 둔다. 생성 시 1이고 회원 본문·평점 수정과 사진
  추가·삭제에서만 증가한다. moderation, 답글, 도움돼요와 신고는 이 값을 바꾸지 않는다.
- 회원 수정도 화면이 읽은 `expectedContentRevision`을 제출한다. 현재 값과 다르면
  `409 REVIEW_CONTENT_CHANGED`로 거절해 다른 탭에서 먼저 바꾼 본문·평점을 덮어쓰지 않는다.
- 상태 전환 요청은 관리자가 읽은 `expectedContentRevision`을 포함한다. 잠근 후기의 현재 값과 다르면
  `409 REVIEW_CONTENT_CHANGED`로 거절해, 숨김 상태에서 회원이 바꾼 미검토 콘텐츠가 오래 열린 관리자
  화면에서 재공개되는 것을 막는다.
- JPA `@Version`은 후기 행의 모든 쓰기에서 증가하는 저장 동시성 토큰이다. 관리자 상태 변경은
  `expectedContentRevision`과 조회한 `expectedVersion`을 함께 비교하고, 공식 답글 작성·수정·삭제는
  `expectedVersion`을 비교해 다른 관리자의 상태 왕복 전환(ABA)과 답글 덮어쓰기·삭제를 `409 CONFLICT`로
  막는다. 콘텐츠 의미 변경만 추적하는 `content_revision`과 행 쓰기 충돌을 추적하는 `version`은 서로
  대체하지 않는다.
- 신고와 moderation은 Envers 대신 명시적인 `review_evidence_snapshots`를 사용한다. 별점·본문·수정 시각과
  정렬된 사진 URL을 하나의 불변 증거로 저장하고 사건 행은 이 증거 ID를 참조한다. 과거 신고 이관본은
  당시 사진을 복원할 수 없으므로 `LEGACY_REPORT`, `images_complete=false`로 표시하며, 과거 moderation에
  현재 내용을 연결해 과거 증거처럼 만들지 않는다.
- 미결 신고 증거는 결정 전까지 보존한다. 종결 신고·moderation과 그 증거는 개인정보 처리방침의 소비자
  불만·분쟁처리 기록 기준인 3년 동안 보존하고 개인정보 보존 배치에서 순차 삭제한다.

### 3. 공개 정보와 회원별 반응을 분리한다

- 공개 후기 응답은 검증된 거래 표식, 수정 표식, 공식 답글, 사진과 도움돼요 수처럼 모든 방문자에게 같은
  데이터만 포함한다.
- 현재 회원의 도움돼요·신고 여부는 `/api/v1/me/**` 일괄 조회에서만 제공한다. 공개 query cache에는 회원별
  상태를 넣지 않는다.
- 관리자 신고 목록은 신고 ID, 후기 ID, 사유, 신고 당시 공개 상태, 처리 상태와 접수 시각만 반환한다.
  신고자 ID·상세·판단 정보와 전체 evidence는 계정 기반 Bearer 단건 조회에서만 제공해 목록 조회의
  민감정보 노출과 payload를 줄인다.
- 회원 반응 응답은 `ownedByMe`, `canInteract`도 계산해 자기 후기의 도움돼요·신고 버튼을 요청 전에
  비활성화한다.
- 도움돼요 등록과 해제는 멱등하게 처리하고 `(review_id,user_id)` UNIQUE로 동시 중복을 막는다.
- 공개 별점 분포는 필터와 무관한 전체 `PUBLISHED` 후기를 기준으로 한다. 별점 필터 결과 수는 별도 값으로
  제공하며 최신순·별점 높은순·낮은순마다 정렬 키를 포함한 opaque cursor를 사용한다.

### 4. 공식 답글과 사진은 후기 생명주기에 종속한다

- 공식 답글은 후기당 하나이며 관리자만 작성·수정·삭제한다. 첫 작성에만 회원 알림을 요청한다.
- 후기 본문 수정 시각은 moderation·답글 갱신과 분리해 `edited_at`으로 저장한다.
- 사진은 먼저 텍스트 후기를 만든 뒤 해당 후기 소유자가 최대 5장까지 첨부한다. 회원 UGC는 JPEG/PNG만
  표준 디코더로 읽고 가로·세로 4,096px·총 1,600만 픽셀 상한을 확인한다. 실제 디코딩 형식을 권위로 삼되
  명시 MIME과 다르면 거절하고, EXIF 방향을 적용한 뒤 메타데이터 없는 파일로 재인코딩한다. 동시 디코딩은
  설정 상한만 허용하고 포화 시 `429`로 빠르게 거절한다.
- 관리자 자산 경계에서 허용하던 WebP는 검증 가능한 서버 디코더가 없으므로 회원 후기 업로드에서는
  제외한다.
- 저장 뒤 DB 첨부 실패와 사진 참조 해제는 커밋 이후 참조를 재확인해 즉시 보상 삭제한다. 삭제 실패에는
  기존 7일 고아 정리를 fallback으로 사용한다.
- `review_images`와 `review_evidence_snapshot_images`를 미디어 참조 조회에 포함해 현재 후기 또는 보존 중인
  증거에 연결된 이미지가 고아 파일로 삭제되지 않게 한다.
- 증거 전용 또는 숨김·삭제 후기에서만 참조되는 사진은 공개 미디어 경로에서 `404`로 숨긴다. 활성 숨김
  후기의 현재 사진은 소유 회원의 CustomerSession 경로 또는 계정 기반 Bearer 관리자 경로에서만 제공하고,
  증거 사진은 계정 기반 Bearer 관리자의 `/api/v1/admin/review-evidence/{evidenceId}/images/{sortOrder}`로만
  제공한다. 모든 보호 이미지 응답은 `Cache-Control: no-store`를 사용한다.
- 3년 보존 만료로 증거 참조를 삭제하면 커밋 뒤 사건을 받아 파일 참조를 다시 확인하고 즉시 물리 파일을
  지운다. 같은 파일이 공개 자산이나 다른 후기·증거에서 계속 쓰이면 삭제하지 않는다.

### 5. 후기 요청과 상태 알림은 기존 outbox를 재사용한다

- 주문은 배송 완료 또는 픽업 완료, 예약은 수강 완료가 처음 확정될 때 후기 작성 기회 알림을 aggregate당
  한 번 저장한다. 완료된 비회원 이력을 회원이 가져오면 현재 회원에게 같은 멱등 규칙으로 요청한다.
- 주문 알림은 미작성 가능한 품목이 하나 이상일 때 주문 단위, 예약 알림은 예약 단위로 발송한다.
- 숨김, 재공개, 최초 공식 답글은 후기 단위로 저장한다. 발송 준비 시 현재 상태와 수신자 소유권을 다시
  확인해 의미가 사라진 요청은 `OBSOLETE`로 끝낸다.

## 결과

### 장점

- 운영자가 숨긴 콘텐츠의 삭제·재작성 우회를 막으면서 정상 삭제 후 재작성 경험은 유지한다.
- 현재 조회 모델과 감사 모델을 분리해 공개 성능과 운영 추적성을 함께 확보한다.
- 공개 캐시가 로그인 사용자별 반응으로 오염되지 않는다.
- 알림, 이미지 저장, 본문 정책과 opaque cursor 등 이미 검증한 플랫폼 추상화를 재사용한다.

### 단점

- 재작성 차단 tombstone과 moderation 이력은 장기 보존되고, 일반 tombstone도 30일 동안 남으므로
  보존·파기 정책과 배치 실패를 함께 관리해야 한다.
- 정렬별 cursor, 도움돼요 counter, 이미지 참조가 추가되어 통합 테스트 범위가 넓어진다.
- 신고 결정과 후기 숨김은 정책상 별도 상태 전이지만, 관리자 화면은 신고에서 현재 후기 단건을 바로
  확인하고 숨김 조치로 이어갈 수 있게 한다.

## 대안

- 모든 삭제 후 재작성을 금지하면 모델은 단순하지만 정상적인 후기 정정 기회를 과도하게 제한한다.
- 삭제 tombstone 행을 재활성화하면 과거 도움돼요·신고 UNIQUE·evidence·알림 멱등 식별자가 새 후기
  생명주기와 섞이므로 채택하지 않았다. 일반 tombstone을 짧게 보존한 뒤 선별 파기한다.
- 숨김 당시 별도 차단 이력 없이 현재 상태만 확인하면 재공개 후 삭제하는 순서로 우회할 수 있어 채택하지
  않았다.
- 공개 후기 응답에 현재 회원 반응을 포함하면 요청은 줄지만 공용 CDN·React Query cache를 안전하게 공유할
  수 없어 채택하지 않았다.
