## 1. 목적과 범위

이 검수는 자동 테스트를 다시 사람이 따라 하는 절차가 아니다. 실제 고객과 공방 관리자가 각자의 화면에서 주문·예약·8회권·문의·후기를 이어서 처리했을 때 다음 세 가지를 확인한다.

1. 고객이 필요한 정보를 이해하고 스스로 흐름을 끝낼 수 있다.
2. 관리자가 같은 주문·예약·후기를 찾아 후속 업무를 끝낼 수 있다.
3. 금액, 재고, 정원, 쿠폰·적립금, 알림과 공개 상태가 양쪽 화면에서 모순되지 않는다.

리눅스 서버 종류, 배포 토폴로지, 백업 장비 선택은 이 검수에서 제외한다. 상품+예약 번들 결제, 오프라인 POS 실시간 연동, 이메일·앱 푸시, 개인화 추천·커뮤니티와 다중 공방 마켓플레이스도 [현재 범위 밖 항목](../../PRD/0003_범위_밖/scope.md)이라 합격 조건에 넣지 않는다.

## 2. 역할과 책임

| 역할 | 권장 인원 | 책임 |
| --- | ---: | --- |
| 검수 진행자 | 1명 | 환경·데이터를 준비하고 시나리오 ID와 업무 ID를 연결한다. 참가자를 대신해 화면을 조작하지 않는다. |
| 실사용자 참가자 | 2명 이상 | 비회원·회원 관점에서 설명 없이 흐름을 수행하고 이해하기 어려운 지점을 말한다. |
| 관리자 참가자 | 실제 운영자 1명 이상 | 고객이 만든 업무를 검색하고 상태 변경·답변·정산·콘텐츠 관리를 수행한다. |
| 관찰·기록 담당 | 1명 | 시작·종료 시각, 기대/실제 결과, 증거와 사용자 발언을 기록한다. |
| 판정 책임자 | 1명 | 결함 심각도와 GO 여부를 결정하고 조건부 승인 기한을 소유한다. |

한 사람이 여러 역할을 맡을 수 있지만, 고객과 관리자 화면은 서로 다른 브라우저 프로필 또는 기기에서 사용한다. 계정 전환·캐시·권한 경계를 실제와 가깝게 확인하기 위해서다.

## 3. 실행 전 준비

### 3.1 실행 정보

검수 시작 전에 결과 문서에 다음 값을 먼저 고정한다.

- 실행 ID: `UAT-<YYYYMMDD>-<release-id>`
- 실행 종류: `ISOLATED_UAT` 또는 `PRODUCTION_SMOKE`
- 대상 commit 또는 이미지 식별자
- 기준 URL과 결제·알림 연동 모드
- 시작·종료 예정 시각(KST, UTC offset 포함)
- 참가자 역할과 계정 별칭
- 기기, 운영체제, 브라우저와 화면 크기
- 이번 실행에서 수행할 P0·P1 시나리오 목록

### 3.2 실행 종류

전체 릴리스 판정은 `ISOLATED_UAT`에서 수행한다. `PRODUCTION_SMOKE`는 실제 배포 뒤 제한된 정상 경로만 확인하는 보조 실행이며, 이것만으로 GO를 판정하지 않는다.

| 실행 종류 | 허용 | 금지 |
| --- | --- | --- |
| `ISOLATED_UAT` | 이 문서의 P0·선택 P1 전체, 전용 테스트 결제·알림과 합성 데이터 | 실제 고객 데이터·결제 수단 사용, 저장소에 비밀값 기록 |
| `PRODUCTION_SMOKE` | 공개 조회, 로그인·로그아웃, 사전 승인한 소액 정상 결제 1건과 정상 관리자 처리 | 장애 주입, 마지막 재고·정원 경합, 필수 사업자 정보 제거, 쿠폰 비활성화, MFA 초기화, 후기 신고·숨김, 환불 실패 재현 |

운영 smoke에서 문제가 발견되면 추가 조작으로 원인을 확인하지 말고 실행을 중단해 격리 환경에서 재현한다. 운영에서 만든 후기 신고·숨김 증거는 장기 보존될 수 있으므로 테스트 목적으로 생성하지 않는다.

### 3.3 테스트 계정과 데이터

데이터 이름에는 `[<실행 ID>-<시나리오 ID>]` 접두사를 붙인다. 다음 데이터 세트를 권장한다.

| 데이터 | 최소 준비 |
| --- | --- |
| 비회원 | SMS를 받을 수 있는 전용 번호 1개 |
| 회원 | `member-uat-01`, `member-uat-02`; 서로 다른 번호·이메일 사용 |
| 관리자 | `admin-uat-01`; 관리자 경합 검수 시 `admin-uat-02` 추가 |
| 기성품 | 픽업용 1개, 배송용 1개, 각각 재고 3개 이상 |
| 주문제작 상품 | 고정 사양·관리 방법·예상 제작 기간이 입력된 상품 1개 |
| 클래스 | 일반 예약용 1개, 8회권 사용 가능 클래스 1개 |
| 슬롯 | 변경 전·후로 사용할 미래 슬롯 3개 이상 |
| 이벤트 | 현재 진행용 1개, 미게시 또는 종료 확인용 1개 |
| 쿠폰 | 주문 시나리오 전용 1개와 프로모션용 정액·정률 각 1개 |
| 적립금 | 주문에서 사용할 수 있는 잔액이 있는 회원 1명 |
| 이미지 | 사람·주소·영수증·차량번호가 없는 합성 관리자용 JPEG/PNG/WebP와 후기용 JPEG/PNG 각 1개 |

테스트 데이터의 상품명·이벤트명·문의 제목에는 시나리오 ID를 포함한다. 주문·예약이 생성되면 화면에 표시되는 `ORD-*`, 예약 번호, 8회권 번호, 후기·신고 ID를 즉시 결과 문서에 기록해 다음 역할에 전달한다.

### 3.4 결제·알림·개인정보 안전 수칙

- 전체 UAT는 테스트 결제·알림 환경에서 수행하는 것을 기본으로 한다.
- 실제 결제가 불가피하면 결제 수단 소유자의 서면 동의와 승인 금액 상한을 결과 문서에 남기고, 상한 이하의 최소 금액만 사용한다.
- 카드·계좌 정보는 수집하거나 기록하지 않는다. 당일 취소 요청으로 끝내지 않고 결제사의 최종 환불 완료까지 확인할 담당자를 지정한다.
- 결제 결과가 불명확하면 같은 결제를 다시 시도하지 말고 결제 상태 화면과 관리자 `오늘 할 일`에서 먼저 확인한다.
- 운영 환경 smoke에서는 고의 환불 실패, 승인 만료, 마지막 재고·정원 경합처럼 고객 영향이 큰 시나리오를 실행하지 않는다.
- 비밀번호, SMS·이메일 인증 코드, 관리자 복구 코드, 비회원 조회 코드 전체, 세션·접근 토큰, 결제 키는 기록하거나 캡처하지 않는다.
- 전화번호·이메일·주소·운송장·신고 증거는 마스킹한다. 마스킹할 수 없는 원본은 저장소 밖 접근 통제 위치에 둔다.

### 3.5 진입 조건

다음 조건을 모두 충족해야 실행을 시작한다.

- [ ] 대상 릴리스와 기준 URL이 확정됐다.
- [ ] 고객·관리자 계정과 MFA 수단이 준비됐다.
- [ ] 테스트 상품·클래스·슬롯·쿠폰·적립금이 준비됐다.
- [ ] 결제와 알림의 테스트 방식, 장애 시 중단 담당자가 합의됐다.
- [ ] 비동기 결제·환불·알림을 기다릴 상한과 확인 담당자가 합의됐다.
- [ ] 결과 문서를 만들고 시나리오별 기록 담당자를 정했다.
- [ ] 테스트 종료 후 주문·예약·환불·알림 backlog를 정리할 담당자를 정했다.

### 3.6 권장 실행 순서와 데이터 의존성

| 묶음 | 대상 | 권장 진행 |
| --- | --- | --- |
| 준비 | 진행자·관리자 | 계정, 상품·클래스·슬롯, 쿠폰·적립금과 결과 문서를 준비한다. |
| 1차 | 실사용자 중심 | 공개 콘텐츠, 가입·로그인, 주문·예약·8회권 결제까지 고객이 먼저 수행한다. |
| 2차 | 관리자 중심 | 같은 업무 ID로 승인·완료·답변·정산·운영 조치를 수행한다. |
| 3차 | 실사용자 재확인 | 고객이 상세·알림·혜택·공개 상태를 다시 확인한다. |
| 4차 | 판정·정리 | 결함을 분류하고 결제·환불·재고·정원·임시 권한을 정리한다. |

결제사(PG) 주문 ID와 내부 주문·예약 번호는 다른 값이다. 결과 문서에는 둘을 구분해 기록하고, 참가자에게는 화면에 보이는 주문·예약 번호를 우선 사용하게 한다.

- `UAT-ADM-READINESS-001`에서 공방 정보를 원복한 뒤 나머지 결제를 시작한다.
- 주문·클레임·프로모션 시나리오는 서로 다른 상품·쿠폰·주문을 사용한다. 프로모션의 쿠폰 비활성화가 주문 시나리오를 막지 않게 한다.
- 예약 완료용 슬롯은 검수 시간 안에 종료되도록 별도로 준비하고, 후기 시나리오는 그 완료 예약 또는 완료 주문을 이어 쓴다.
- 환불·교환·대사 시나리오는 각각 전용 업무를 사용한다. 이미 끝난 업무에 다른 실패 경로를 겹쳐 만들지 않는다.
- 참가자 개인 브라우저 전체 데이터를 지우지 않는다. 조회 정보 상실은 전용 프로필에서 해당 사이트 데이터만 지우거나 새 전용 프로필로 전환해 재현한다.

## 4. 실행 방법

### 4.1 기본 순서

1. 고객 참가자는 안내 문구만 보고 시나리오를 수행한다.
2. 진행자는 막히기 전까지 정답이나 클릭 위치를 알려주지 않는다.
3. 고객이 만든 업무 번호를 기록 담당자가 관리자에게 전달한다.
4. 관리자는 검색 또는 `오늘 할 일`에서 같은 업무를 찾아 후속 처리한다.
5. 고객은 새로고침 또는 상세 재진입으로 결과를 확인한다.
6. 기대 결과와 실제 결과를 비교하고 PASS·FAIL·BLOCKED를 기록한다.
7. 결함 수정 후에는 같은 원천 데이터로 가능한 범위까지 재검수하고, 새 데이터가 필요하면 기존 ID와 새 ID를 함께 남긴다.

### 4.2 관찰 원칙

- 데이터베이스나 API를 직접 보는 결과보다 고객·관리자 화면에서 관찰한 결과를 우선한다.
- 예상한 문구가 아니라 실제 보인 문구와 상태를 기록한다.
- 성공 여부뿐 아니라 참가자가 망설인 지점, 잘못 이해한 용어, 뒤로 가기·재시도 행동도 기록한다.
- 오류 화면의 `requestId`가 보이면 함께 기록하되, 같은 오류를 불필요하게 반복 재현하지 않는다.
- 개인정보 노출, 타인 데이터 접근, 중복 결제·중복 환불, 금액·재고·정원 불일치는 한 번만 관찰돼도 즉시 해당 시나리오를 중단한다.

### 4.3 실행 상태

| 상태 | 의미 |
| --- | --- |
| `NOT_RUN` | 아직 실행하지 않음 |
| `PASS` | 기대 결과를 모두 만족함 |
| `FAIL` | 실행은 끝났지만 기대 결과와 다름 |
| `BLOCKED` | 환경·선행 데이터·외부 연동 문제로 판정할 수 없음 |
| `RETEST_PASS` | 결함 수정 뒤 같은 기대 결과를 다시 확인함 |

### 4.4 비동기 결과 대기

- 진행자는 실행 전에 결제·환불과 알림의 대기 상한을 결과 문서에 기록한다. 사전 합의값이 없으면 격리 환경 권장값으로 결제·환불 2분, 알림 5분을 사용하되 제품 정책으로 간주하지 않는다.
- 대기 상한까지는 화면이 제공하는 상태 다시 확인만 사용한다. 결제, 환불, 적립, 쿠폰 사용 같은 쓰기 동작을 반복하지 않는다.
- 상한 뒤에도 처리 중이면 현재 화면 상태와 시각을 기록하고, 외부 연동이나 준비 데이터 문제면 `BLOCKED`, 기대 상태와 명백히 다르면 `FAIL`로 판정한다.
- `BLOCKED`는 무한 대기 사유가 아니다. 확인 담당자와 다음 확인 시각을 정하고 실행을 계속한다.

## 5. 시나리오 요약

P0는 운영 승인 전에 모두 실행한다. P1은 해당 기능을 이번 릴리스에서 사용한다면 실행하고, 미실행 사유를 결과 문서에 남긴다.

| ID | 우선순위 | 역할 | 업무 연결 키 | 시나리오 |
| --- | --- | --- | --- | --- |
| `UAT-PUB-CONTENT-001` | P0 | 공개 방문자·관리자 | 상품·클래스·이벤트명 | 공개 콘텐츠·사업자 정보·이미지 경계 |
| `UAT-ADM-READINESS-001` | P0 | 공개 방문자·회원·관리자 | 공방 프로필 version | 운영 결제 준비와 필수 사업자 정보 |
| `UAT-ADM-CATALOG-001` | P0 | 공개 방문자·관리자 | 상품·클래스·슬롯 ID | 상품 재고·판매 상태와 클래스 슬롯 운영 |
| `UAT-MEM-IDENTITY-001` | P0 | 비회원·회원 | 계정 별칭 | 가입·로그인·세션·장바구니 경계 |
| `UAT-PAIR-ORDER-001` | P0 | 회원·관리자 | `ORD-*` | 쿠폰·적립금 주문과 픽업·배송 완료 |
| `UAT-PAIR-GUEST-001` | P0 | 비회원·회원·관리자 | `ORD-*` | 비회원 주문 조회 복구와 회원 이력 가져오기 |

## 6. P0 필수 시나리오

### UAT-PUB-CONTENT-001 — 공개 콘텐츠·사업자 정보·이미지 경계

**사전조건**: 관리자가 공개/비공개 상품·클래스, 진행/종료 이벤트, 공지와 공방 정보를 준비한다.

**정책 근거**: [기준 스펙 §3.1](../../PRD/0001_기준_스펙/spec.md), [API 계약 §2.2·§2.19·§2.20](../../PRD/0004_API_계약/spec.md)

**절차**

1. 관리자가 상품·클래스·이벤트 대표 이미지를 업로드하고 비공개 상태에서 미리보기를 확인한다.
2. 공개 방문자가 홈, 작품, 클래스, 단체수업, 이벤트, 공지 상세를 모바일과 데스크톱에서 확인한다.
3. 진행 중 이벤트의 관련 상품으로 이동하고, 미게시·종료 이벤트와 비활성 상품·클래스가 공개 목록에 없는지 확인한다.
4. 페이지 맨 아래, 이용약관, 개인정보처리방침, 사업자 정보에서 현재 공방 정보와 링크를 확인한다.
5. 관리자가 대상을 비공개로 바꾼 뒤 기존 공개 화면을 다시 연다.

**기대 결과**

- 공개 가능한 콘텐츠와 이미지만 보이고, 비공개·종료·숨김 자료의 기존 이미지 주소는 열리지 않는다.
- 관리자 화면에서는 업로드 직후와 비공개 자산도 인증된 미리보기로 확인할 수 있다.
- 공방 연락처·주소·사업자·정책 정보가 서로 모순되지 않고 모바일에서 잘리지 않는다.

**필수 증거**: 콘텐츠명, 공개/비공개 전후 화면, 페이지 맨 아래·사업자 정보, 기기·브라우저.

### UAT-ADM-READINESS-001 — 운영 결제 준비와 필수 사업자 정보

**사전조건**: 운영 결제 준비 가드가 활성화된 검수 환경과 원복할 공방 프로필 값을 준비한다. 실제 운영 프로필에서는 필수 정보를 지우지 않는다.

**정책 근거**: [기준 스펙 §3.1](../../PRD/0001_기준_스펙/spec.md), [API 계약 §2.19.1](../../PRD/0004_API_계약/spec.md)

**절차**

1. 검수 환경에서 연락처·주소·사업자등록번호·대표자명·전자우편·통신판매업 신고번호 중 하나가 빠진 프로필을 준비한다.
2. 회원이 결제 준비를 시도하고, 결제창을 열기 전에 운영 준비 안내를 받는지 확인한다.
3. 관리자가 공방 공개 정보에서 누락 값을 보완한다.
4. 공개 페이지 맨 아래와 사업자 정보에서 보완 값이 보이는지 확인한다.
5. 같은 회원이 다시 결제 준비를 수행한다.

**기대 결과**

- 필수 공개 정보가 빠진 동안에는 결제 시도를 만들지 않는다.
- 관리자가 값을 보완하면 공개 정보와 결제 가능 상태가 함께 정상화된다.
- 이전 공개 프로필을 보고 있던 화면도 새 값으로 갱신된다.

**필수 증거**: 프로필 version, 결제 차단 안내, 보완 전후 공개 사업자 정보, 재시도 결과.

### UAT-ADM-CATALOG-001 — 상품 재고·판매 상태와 클래스 슬롯 운영

**사전조건**: 관리자, 비활성 기성품·클래스, 슬롯 일괄 생성 기간을 준비한다.

**정책 근거**: [기준 스펙 §3.1·§4.1](../../PRD/0001_기준_스펙/spec.md), [API 계약 §2.1·§2.3](../../PRD/0004_API_계약/spec.md)

**절차**

1. 관리자가 기성품을 등록하고 입고·오프라인 판매 사유로 재고를 증가·감소시킨다.
2. 현재 재고보다 큰 감소가 거절되고 조정 전후 수량·사유가 이력에 남는지 확인한다.
3. 상품을 판매 중으로 전환한 뒤 공개 화면에서 확인하고, 다시 중지해 공개 목록에서 사라지는지 본다.
4. 관리자가 클래스를 만들고 반복 슬롯을 미리보기한 뒤 일괄 생성한다.
5. 같은 조건을 다시 시도해 이미 생성된 슬롯이 중복되지 않는지 확인한다.

**기대 결과**

- 재고가 음수가 되지 않고 조정 이력과 공개 판매 상태가 실제 수량에 맞는다.
- 슬롯 미리보기와 생성 결과가 일치하고 날짜·요일·시각·정원이 중복되지 않는다.
- 이후 주문 거절·취소·클레임에서 복구한 재고는 `UAT-PAIR-ORDER-001`과 `UAT-PAIR-CLAIM-001`에서 같은 상품으로 이어서 확인할 수 있다.

**필수 증거**: 상품·클래스·슬롯 ID, 재고 전후와 조정 이력, 판매 상태, 슬롯 미리보기·생성 결과.

### UAT-MEM-IDENTITY-001 — 가입·로그인·세션·장바구니 경계

**사전조건**: 사용하지 않은 테스트 이메일·휴대폰, 회원 A·B, 브라우저 탭 2개를 준비한다.

**정책 근거**: [기준 스펙 §8](../../PRD/0001_기준_스펙/spec.md), [API 계약 §1.3·§2.12](../../PRD/0004_API_계약/spec.md)

**절차**

1. 비회원으로 상품을 장바구니에 담는다.
2. 현재 약관·개인정보처리방침에 동의하고 휴대폰 인증을 마쳐 이메일 회원으로 가입한다.
3. 로그인 뒤 비회원 장바구니가 한 번만 병합되는지 확인한다.
4. 한 탭에서 수량을 바꾸고 오래된 탭에서 결제를 시작해 최신 장바구니 확인 안내를 본다.
5. 다른 탭에서 회원 A를 로그아웃하고 회원 B로 로그인한다.
6. A의 주문·예약·배송지·비밀 Q&A·입력 중 폼이 B에게 보이지 않는지 확인한다.
7. 로그아웃 후 `/my`와 회원 전용 화면이 다시 인증을 요구하는지 확인한다.

**기대 결과**

- 동의·휴대폰 확인 전 가입이 완료되지 않는다.
- 병합은 중복되지 않고 오래된 장바구니로 자동 결제하지 않는다.
- 계정이 바뀌면 이전 회원의 화면·캐시·초안·민감 정보가 남지 않는다.

**필수 증거**: 계정 별칭, 병합 전후 품목, 장바구니 충돌 안내, 계정 전환 전후 화면.

### UAT-PAIR-ORDER-001 — 쿠폰·적립금 주문과 픽업·배송 완료

**사전조건**: 재고가 있는 기성품, 전용 공개 쿠폰, 적립금 잔액이 있는 회원을 준비한다. 픽업 완료용, 배송 완료용, 관리자 거절용 주문을 각각 만든다.

**정책 근거**: [기준 스펙 §3.1·§3.1.1](../../PRD/0001_기준_스펙/spec.md), [API 계약 §2.6·§2.7·§2.20](../../PRD/0004_API_계약/spec.md)

**절차**

1. 회원이 주문 시나리오 전용 쿠폰을 발급받고 내 혜택에서 사용 가능 상태를 확인한다.
2. 픽업·배송 완료용 주문을 만들고, 그중 하나에는 적립금만 사용한다.
3. 관리자 거절용 주문에는 전용 쿠폰과 적립금을 함께 적용한다. 세 주문 모두 상품액·배송비·쿠폰 할인·적립금·최종 결제 금액을 확인한다.
4. 주문번호를 관리자에게 전달한다.
5. 관리자가 주문을 검색해 승인한다. 배송 건은 배송 준비→택배사·운송장 입력 후 배송 출발→배송 완료, 픽업 건은 픽업 준비→픽업 완료까지 처리한다.
6. 회원이 주문 상세와 내 혜택을 다시 확인한다.
7. 거절용 주문은 관리자가 판매 불가로 거절하고, 회원이 환불 상태를 확인한다.
8. 거절 전후의 상품 재고, 쿠폰 상태와 적립금 이용 내역을 비교한다.

**기대 결과**

- 고객과 관리자 화면의 상품·수량·금액·상태가 일치한다.
- 결제 완료 시 재고가 한 번만 차감되고, 쿠폰·적립금이 이중 사용되지 않는다.
- 완료 뒤 지급되는 적립금이 기준 스펙에 맞게 한 번만 적립금 이용 내역에 나타난다.
- 관리자 거절 주문은 전액 환불되고 재고·쿠폰·적립금이 기준 스펙에 맞게 한 번만 복구된다.

**필수 증거**: `ORD-*` 3건, 결제 전후 금액 구성, 관리자 처리 단계, 재고 전후, 쿠폰 상태, 적립금 이용 내역.

### UAT-PAIR-GUEST-001 — 비회원 주문 조회 복구와 회원 이력 가져오기

**사전조건**: 전용 휴대폰과 활성 상품을 준비하고, 전용 브라우저 프로필의 해당 사이트 데이터만 지우기 전 조회 화면을 캡처한다.

**정책 근거**: [기준 스펙 §3.1·§8](../../PRD/0001_기준_스펙/spec.md), [API 계약 §2.12·§2.18](../../PRD/0004_API_계약/spec.md)

**절차**

1. 비회원이 휴대폰 인증과 정책 동의를 거쳐 주문·결제를 완료한다.
2. 비회원 주문 상세에서 주문번호와 상태를 확인한다.
3. 조회 정보를 잃은 상황을 만들고 `/guest`에서 SMS 기반 조회 정보 복구를 수행한다.
4. 관리자가 같은 주문을 완료한다.
5. 같은 번호로 회원가입 또는 로그인하고 `/my`에서 비회원 이력 가져오기를 수행한다.
6. 회원 내 주문에서 같은 주문이 보이고 비회원 토큰 없이 상세를 열 수 있는지 확인한다.

**기대 결과**

- 복구 전후 주문은 하나이며, 조회 정보가 없다고 새 결제를 유도하지 않는다.
- 이력 가져오기는 같은 소유자의 주문만 회원에게 귀속하고 중복 실행해도 한 번만 반영한다.

**필수 증거**: `ORD-*`, 마스킹한 복구 화면, 이력 가져오기 전후 주문 목록.

### UAT-PAIR-MADE-001 — 주문제작·지연 제안 수락/거절

**사전조건**: 주문제작 상품과 수락용·거절용 주문 2건을 준비한다.

**정책 근거**: [기준 스펙 §3.2](../../PRD/0001_기준_스펙/spec.md), [API 계약 §2.7](../../PRD/0004_API_계약/spec.md)

**절차**

1. 회원이 각 주문에서 고정 사양, 관리 방법, 예상 제작 기간과 주문제작 동의를 확인하고 결제한다.
2. 관리자가 두 주문을 승인해 제작 중 상태로 전환한다.
3. 배송 주문이면 관리자가 예상 출고일을 별도로 설정한 뒤 지연 제안을 보낸다. 픽업 주문은 출고일 입력 없이 지연 제안만 보낸다.
4. 회원이 첫 주문의 지연을 수락하고, 관리자가 처리를 재개해 제작·배송 또는 픽업을 이어간다.
5. 회원이 두 번째 주문의 지연을 거절한다.
6. 양쪽 화면에서 취소·환불과 상태 이력을 확인한다.

**기대 결과**

- 결제 당시 제작 조건과 관리 방법이 이후 상품 수정과 무관하게 주문 상세에 남는다.
- 지연 수락 전 관리자는 임의로 재개할 수 없고, 수락·거절 결과가 양쪽에 동일하게 표시된다.
- 거절 주문은 재고·PG·적립금·쿠폰 정책에 맞게 환불로 수렴한다.

**필수 증거**: 주문번호 2개, 결제 당시 조건, 지연 제안, 수락/거절 후 상태·금액.

### UAT-PAIR-CLAIM-001 — 주문 취소·환불·교환

**사전조건**: 승인 대기 주문 1건, 배송 또는 픽업 완료 주문 2건을 준비한다.

**정책 근거**: [기준 스펙 §3.1](../../PRD/0001_기준_스펙/spec.md), [API 계약 §2.6·§2.7](../../PRD/0004_API_계약/spec.md)

**절차**

1. 고객이 승인 대기 주문을 직접 취소하고 환불 진행 상태를 확인한다.
2. 완료 주문 A에서 품목·수량·사유를 선택해 환불 클레임을 접수한다.
3. 완료 주문 B에서 교환 클레임을 접수한다.
4. 관리자가 주문 탭의 클레임 목록에서 상태 필터와 페이지 이동으로 주문 A를 찾아 환불을 승인하고 반품 재고 복구 여부를 선택한다.
5. 주문 B의 교환을 승인하고 택배사·운송장을 입력해 교환을 완료한다.
6. 고객이 두 클레임 상세와 주문 금액 구성을 다시 확인한다.
7. 쿠폰·적립금을 사용한 환불 건은 내 혜택의 쿠폰 상태와 적립금 이용 내역을 확인하고, 이미 완료된 환불 화면을 다시 열어 중복 처리 버튼이 없는지 확인한다.

**기대 결과**

- 접수 가능 수량을 넘기거나 같은 수량을 중복 접수할 수 없다.
- 환불액은 PG 환불과 적립금 복원으로 구분되고, 쿠폰·적립금·지급 적립금과 재고가 한 번만 조정된다.
- 교환은 별도 교환품 재고를 사용하고 출고 정보가 고객에게 보인다.
- 이미 끝난 환불·복구는 다시 실행할 수 없고 쿠폰·적립금·환불이 중복 반영되지 않는다.

**필수 증거**: 주문·클레임 번호, 접수 수량, 관리자 판단, 고객 반환액, 재고 전후.

### UAT-PAIR-BOOKING-001 — 예약 결제·변경·취소·완료

**사전조건**: 활성 클래스, 변경 가능한 미래 슬롯 2개, 검수 시간 안에 정상 종료되는 완료용 슬롯 1개와 비회원용 휴대폰을 준비한다. 완료용 슬롯이 당일 끝나지 않으면 다음 회차 담당자와 확인 시각을 미리 정한다.

**정책 근거**: [기준 스펙 §4.1~§4.3](../../PRD/0001_기준_스펙/spec.md), [API 계약 §2.4·§2.9](../../PRD/0004_API_계약/spec.md)

**절차**

1. 비회원이 클래스·인원·날짜·시간을 선택하고 휴대폰 인증 뒤 예약금을 결제한다.
2. 비회원 조회 코드로 예약 상세를 열어 같은 클래스의 다른 가능한 슬롯으로 변경한다.
3. 별도 비회원 예약을 취소 마감 전에 취소하고 예약금 환불 상태를 확인한다.
4. 완료용 예약은 관리자가 현장 잔금 수납 또는 미수 상태를 기록한다.
5. 클래스 종료 뒤 관리자가 예약을 완료 처리한다.
6. 비회원과 관리자가 슬롯 정원, 예약 상태, 결제·환불 금액을 비교한다.

**기대 결과**

- 변경 전 슬롯 정원은 복구되고 변경 후 슬롯은 인원만큼 차감된다.
- 취소 마감과 환불 안내가 서울 시각 기준으로 이해 가능하게 표시된다.
- 잔금 상태와 완료 여부가 고객·관리자 화면에서 일치한다.

**필수 증거**: 예약 번호, 변경 전후 슬롯, 정원 전후, 취소 환불, 잔금·완료 상태.

### UAT-ADM-BOOKING-001 — 전화·메신저·방문 수기 예약과 운영자 취소

**사전조건**: 일반 예약 가능한 클래스·슬롯, 테스트 고객 정보, 수기 예약금·잔금 값을 준비한다.

**정책 근거**: [기준 스펙 §4.1~§4.3](../../PRD/0001_기준_스펙/spec.md), [API 계약 §2.9](../../PRD/0004_API_계약/spec.md)

**절차**

1. 관리자가 예약·8회권 화면에서 클래스와 슬롯을 선택한다.
2. 전화·메신저·방문 중 접수 경로, 고객·인원과 예약금 입금 여부를 입력해 예약을 만든다.
3. 예약 목록에서 같은 예약을 찾고 현장 잔금을 결제 완료 또는 미수 상태로 별도 처리한다.
4. 예약 목록과 검색에서 슬롯 정원과 최종 수납 상태를 확인한다.
5. 별도 수기 예약을 운영자 사유로 취소한다.
6. 환불, 크레딧 복구 또는 수동 보상 후속 작업이 생기면 금액·사유를 확인하고 완료 처리한다.

**기대 결과**

- 수기 예약도 일반 예약과 같은 슬롯 정원을 사용하고 접수 경로·수납 상태가 보존된다.
- 운영자 취소는 고객 취소 마감과 무관하게 가능하지만, 필요한 금전·크레딧 후속 작업을 생략하지 않는다.
- 완료한 후속 작업은 `오늘 할 일`에서 사라지고 같은 예약에 중복 적용되지 않는다.

**필수 증거**: 예약·후속 작업 ID, 접수 경로, 인원·정원, 예약금·잔금, 취소 전후 상태.

### UAT-PAIR-PASS-001 — 8회권 구매·사용·취소·정산 환불

**사전조건**: 회원, 8회권 사용 가능 클래스와 미래 슬롯을 준비한다.

**정책 근거**: [기준 스펙 §5.1~§5.3](../../PRD/0001_기준_스펙/spec.md), [API 계약 §2.5](../../PRD/0004_API_계약/spec.md)

**절차**

1. 회원이 8회권을 결제하고 `/my/passes`에서 총 8회와 유효기간을 확인한다.
2. 호환 클래스에서 8회권을 선택해 1명 예약을 만들고 잔여 횟수 `8→7`을 확인한다.
3. 취소 마감 전에 예약을 취소해 `7→8` 복구를 확인한다.
4. 별도 미래 예약을 만든 뒤 회원이 잔여 횟수 정산 환불을 요청한다.
5. 관리자가 8회권 번호로 예상 환불액, 미래 예약 취소와 환불 상태를 확인한다.
6. 환불 실패 또는 상태 확인 필요 건으로 준비된 경우에만 `오늘 할 일`에서 기존 환불을 재처리하고 최종 상태를 확인한다.

**기대 결과**

- 비호환 클래스나 2명 이상 예약에는 8회권을 사용할 수 없다.
- 취소 정책에 따라 크레딧 복구 여부가 한국어로 분명히 보인다.
- 정산 환불은 미래 예약·잔여 횟수·환불 금액을 모순 없이 처리한다.

**필수 증거**: 8회권·예약 번호, 잔여 횟수 변화, 유효기간, 환불 전후 상태.

### UAT-PAIR-SUPPORT-001 — 공개/비밀 Q&A·1:1 문의·알림

**사전조건**: 회원, 공개 상품, 관리자 계정을 준비한다.

**정책 근거**: [기준 스펙 §3.4·§7](../../PRD/0001_기준_스펙/spec.md), [API 계약 §2.12~§2.14](../../PRD/0004_API_계약/spec.md)

**절차**

1. 회원이 상품 공개 질문과 비밀 질문을 각각 작성한다.
2. 로그아웃한 공개 방문자가 공개 질문 상세를 보고 비밀 질문 본문은 볼 수 없는지 확인한다.
3. 회원이 1:1 문의를 작성한다.
4. 관리자가 고객 응대 화면에서 질문·문의를 찾아 답변한다.
5. 회원이 Q&A·문의 상세와 알림함에서 답변을 확인한다.
6. 관리자가 답변 완료 건을 다시 열어 기존 답변만 보이고 답변 입력·저장 동작이 사라졌는지 확인한다.

**기대 결과**

- 공개·비밀·회원 전용 경계가 섞이지 않는다.
- 답변은 한 번 저장되고 회원 알림도 한 번만 생성된다.
- 이미 답변한 건은 화면에서 다시 답변할 수 없고 기존 답변과 알림 한 건이 유지된다.

**필수 증거**: 질문·문의 ID, 공개/비밀 비교 화면, 관리자 답변, 회원 알림.

### UAT-PAIR-REVIEW-001 — 후기·사진·도움돼요·신고·운영 조치

**사전조건**: 완료 주문 또는 완료 예약을 가진 회원 A, 다른 회원 B, 관리자, JPEG/PNG 사진을 준비한다.

**정책 근거**: [기준 스펙 §3.5](../../PRD/0001_기준_스펙/spec.md), [API 계약 §2.14.3](../../PRD/0004_API_계약/spec.md)

**절차**

1. A가 `/my/reviews` 또는 완료 거래 상세에서 별점·본문 후기를 먼저 저장한다.
2. 생성된 내 후기 카드에서 JPEG/PNG 사진을 별도로 추가한다.
3. 공개 상품·클래스 상세에서 마스킹 작성자, 거래 확인, 별점 분포와 사진을 확인한다.
4. A가 본문·별점·사진을 수정하고 수정 표식을 확인한다.
5. B가 도움돼요를 등록하고 신고 사유·상세를 제출한다.
6. 관리자가 후기 화면에서 신고 상세·당시 증거를 열고 공식 답글을 작성한다.
7. 관리자가 신고를 판단하고 후기를 사유와 함께 숨긴다.
8. A와 B가 각각 내 후기·알림·공개 목록을 다시 확인한다.

**기대 결과**

- 작성 가능 거래만 후기 폼을 제공하고 같은 거래에 활성 후기를 중복 작성할 수 없다.
- 자기 후기에는 도움돼요·신고가 비활성화되고 다른 회원의 반응은 한 번만 반영된다.
- 숨김 뒤 공개 목록·별점 통계에서 제외되며, 작성자에게는 사유와 보호된 사진이 보인다.
- 신고 판단·공식 답글·숨김은 관리자 화면에서 같은 후기와 연결되고 알림이 중복되지 않는다.

**필수 증거**: 거래·후기·신고 ID, 공개 전후 통계, 사진, 도움돼요 수, 답글·판단·숨김 이력.

### UAT-PAIR-PROMO-001 — 이벤트 게시·쿠폰 발급·주문 적용

**사전조건**: 관련 상품, 진행 중 추천 이벤트, 정액·정률 공개 발급 쿠폰과 회원을 준비한다.

**정책 근거**: [기준 스펙 §3.1.1](../../PRD/0001_기준_스펙/spec.md), [API 계약 §2.20](../../PRD/0004_API_계약/spec.md)

**절차**

1. 관리자가 이벤트 기간, 대표 이미지, 홈 추천, 관련 상품을 설정해 게시한다.
2. 회원이 홈·이벤트 목록·상세를 거쳐 관련 상품으로 이동한다.
3. 관리자가 정액·정률 쿠폰을 공개 발급 가능하게 만들고 회원이 각 쿠폰을 한 번씩 발급받는다.
4. 최소 주문금액보다 작은 장바구니에서 적용을 시도한 뒤, 조건을 충족하는 두 주문에 쿠폰을 하나씩 적용한다.
5. 정률 쿠폰은 최대 할인액을 넘는 주문에서도 상한까지만 적용되는지 확인한다.
6. 관리자가 쿠폰을 비활성화하고 미사용 회원 화면과 새 결제 가능 여부를 확인한다.

**기대 결과**

- 진행·예정 정책에 맞는 이벤트만 노출되고 미게시·종료 이벤트는 공개되지 않는다.
- 회원당 같은 쿠폰은 한 장만 발급되며 최소 주문금액, 정액·정률과 최대 할인액이 기준 스펙대로 계산된다.
- 비활성화 뒤 신규 사용은 막히고 과거 발급 내역과 결제 당시 주문 내용은 유지된다.

**필수 증거**: 이벤트·쿠폰 ID, 홈/목록/상세, 발급 전후, 주문 할인, 비활성화 전후.

### UAT-ADM-AUTH-001 — MFA·세션 만료·로그아웃·보호 자료 접근

**사전조건**: 관리자 계정, 인증 앱, 복구 코드 보관 절차와 일반 사용자 브라우저를 준비한다.

**정책 근거**: [ADR-0023](../../ADR/0023_관리자_회원_인증_세션_기준선/adr.md), [API 계약 §1.2](../../PRD/0004_API_계약/spec.md)

**절차**

1. 관리자가 비밀번호와 MFA로 로그인한다.
2. MFA 미등록 계정이면 다른 운영 메뉴보다 등록과 복구 코드 확인만 가능한지 본다.
3. 로그아웃 후 브라우저 뒤로 가기와 새로고침으로 관리자 자료가 다시 보이지 않는지 확인한다.
4. 진행자가 짧은 테스트 세션 만료 시간을 사용하거나 관리자 비밀번호를 변경해 기존 세션을 폐기한 뒤, 진행 중 화면에서 재로그인 안내를 확인한다.
5. 숨김 후기·신고 증거·비공개 이미지가 일반 사용자나 인증 없는 새 창에서는 열리지 않는지 확인한다.
6. 별도 테스트 계정에서 복구 코드 로그인과 MFA 재등록 절차를 수행한다.

**기대 결과**

- 관리자 상태 변경과 보호 자료는 계정 기반 관리자 세션에서만 가능하다.
- 만료·로그아웃 뒤 캐시된 관리자 데이터와 보호 이미지가 남지 않는다.
- 복구 코드는 일회성이며 재등록 전 허용 화면이 제한된다.

**필수 증거**: 관리자 계정 별칭, MFA 단계, 로그아웃·만료 화면, 보호 자료 내용이 노출되지 않고 인증 또는 비공개 안내가 보이는 화면. 복구 코드 자체는 기록하지 않는다.

### UAT-PAIR-PAYMENT-001 — 결제 새로고침·중복 방지·결과 복구

**사전조건**: `ISOLATED_UAT` 테스트 결제 환경과 주문·예약·8회권 결제 대상, 재시도 가능 환불·예약 취소 후속 작업을 준비한다. 결제 대사 필요 건은 재현 가능한 전용 준비 수단이 제공된 회차에서만 추가한다.

**정책 근거**: [기준 스펙 §8.1](../../PRD/0001_기준_스펙/spec.md), [API 계약 §2.11·§2.15](../../PRD/0004_API_계약/spec.md)

**절차**

1. 각 결제에서 결제 성공 화면의 자동 확정 중 새로고침 또는 뒤로 가기를 수행하고, 화면에 `결제 결과 다시 확인`이 보이면 한 번 사용한다.
2. 고객 화면에서 최종 상태 또는 `확인 중` 안내를 확인한다.
3. 비회원 결제는 조회 정보 복구 화면에서도 같은 결제 결과를 확인한다.
4. 관리자는 고객이 전달한 주문·예약·8회권 번호로 각각 조회해 같은 결제에서 같은 종류의 업무가 중복 생성되지 않았는지 확인한다.
5. 재현 가능한 전용 준비 수단으로 결제 대사 필요 건이 제공된 회차라면 관리자가 결제사 조회로 확인한다. 준비되지 않았다면 이 단계만 `N/A`로 기록한다.
6. 관리자가 재시도 가능 환불에 화면의 재처리 동작을 한 번 사용한다.
7. 예약 취소 후속 작업의 금액·사유를 확인하고 완료 처리한다.
8. 고객 화면에서 최종 결제·환불·예약 상태와 금액을 다시 확인한다.

**기대 결과**

- 한 결제가 같은 종류의 업무를 두 건 만들지 않는다.
- 결과를 모르는 상태에서 새 결제를 유도하지 않고 상태 조회·대사·환불 중 하나로 수렴한다.
- 결제·환불은 성공 안내만으로 끝내지 않고 최종 성공 상태와 금액을 확인하며, 같은 복구를 반복해도 중복 환불되지 않는다.
- 고객과 관리자 화면의 결제·환불·예약 후속 작업 상태가 최종적으로 일치한다.

**필수 증거**: 마스킹한 결제사 주문 ID, 내부 업무 ID 수, 새로고침 전후, 관리자 확인·복구 결과.

## 7. P1 확장 시나리오

선택한 P1도 결과 문서에 사전조건·단계·증거를 기록한다. 아래 단계는 참가자가 독립적으로 실행할 수 있는 최소 절차다.

### UAT-MEM-IDENTITY-002 — 소셜 로그인과 계정 연결

- **준비·역할**: Google·Naver 테스트 계정, 기존 이메일 회원, 회원 참가자.
- **단계**: 각 제공자로 신규 로그인→기존 회원에서 최근 본인 확인→소셜 계정 연결→연결 해제와 마지막 로그인 수단 해제 시도.
- **기대**: 이메일 일치만으로 계정이 자동 병합되지 않고, 현재 회원 소유권을 확인하며 마지막 로그인 수단을 제거할 수 없다.
- **증거**: 계정 별칭, 제공자별 가입·연결·해제 전후 화면. [API 계약 §2.12](../../PRD/0004_API_계약/spec.md)

### UAT-MEM-ACCOUNT-001 — 회원 보안 정보와 탈퇴

- **준비·역할**: 비밀번호 회원, 휴대폰·이메일 인증 수단, 처리 중 거래가 있는 계정과 없는 계정.

- **기대**: 최근 본인 확인과 기존 세션 종료가 일관되고, 처리 중 거래가 있으면 탈퇴를 막는다.
- **증거**: 계정 별칭, 각 인증 완료·세션 종료·탈퇴 안내. [API 계약 §2.12](../../PRD/0004_API_계약/spec.md)

### UAT-MEM-BOOKING-002 — 회원 일반 예약금 결제

- **준비·역할**: 휴대폰 확인 회원, 일반 클래스와 미래 슬롯.
- **단계**: 로그인 회원이 일반 예약금을 결제→`/my/bookings`에서 조회→변경 또는 취소→관리자가 같은 예약 확인.
- **기대**: 비회원 조회 코드 없이 회원 세션으로만 소유권을 확인하고 예약금·정원·환불 결과가 양쪽에 일치한다.
- **증거**: 계정 별칭, 예약 번호, 변경·취소 전후. [기준 스펙 §4](../../PRD/0001_기준_스펙/spec.md)

### UAT-CONCURRENCY-001 — 마지막 재고·슬롯 경합

- **준비·역할**: `ISOLATED_UAT` 전용 마지막 재고 1개와 잔여 정원 1명, 고객 2명.
- **단계**: 두 기기에서 같은 상품 또는 슬롯 결제를 최대한 동시에 확정→양쪽 결과와 관리자 재고·정원 확인.
- **기대**: 한 건만 성공하고 다른 고객은 중복 청구 없이 이해 가능한 실패 안내를 받는다.
- **증거**: 두 고객 시각, 결제 결과, 최종 재고·정원. [기준 스펙 §3.1·§4.1](../../PRD/0001_기준_스펙/spec.md)

### UAT-TIME-BOUNDARY-001 — 취소·변경·픽업 시간 경계

- **준비·역할**: 격리 환경에서 경계 직전·직후 예약, 8회권 예약과 픽업 주문을 진행자가 준비한다.

### UAT-ADM-CONFLICT-001 — 오래된 관리자 화면 충돌

## 8. 참가자 인터뷰

각 시나리오 직후 참가자에게 아래 네 문항만 묻는다. 기능 결함과 사용성 의견을 분리해 기록한다.

1. 방금 작업이 끝났다고 확신했습니까? 1점(전혀 아님)~5점(매우 확실함)
2. 가장 오래 멈추거나 다시 읽은 화면은 어디였습니까?
3. 실제 공방 업무 또는 구매 상황이라면 다음 행동을 스스로 알 수 있었습니까?
4. 상태명·버튼·안내 중 평소 쓰는 말과 다른 표현이 있었습니까?

관리자에게는 다음도 묻는다.

- 고객이 문의하기 전에 지금 처리해야 할 업무를 찾을 수 있었습니까?
- 상태를 바꿀 때 금액·재고·정원에 미치는 영향을 충분히 이해할 수 있었습니까?
- 실수했을 때 되돌리거나 복구할 경로가 분명했습니까?

## 9. 결함 심각도와 중단 기준

| 심각도 | 기준 | 예시 |
| --- | --- | --- |
| `Blocker` | 필수 여정 자체를 시작하거나 계속할 수 없음 | 전체 로그인·결제·관리자 진입 불가 |
| `Critical` | 금전·소유권·개인정보·중복·재고·정원 무결성 위반 | 타인 주문 노출, 중복 결제/환불, 비공개 사진 노출 |
| `Major` | 핵심 흐름이 잘못되거나 일반 사용자가 복구하기 어려움 | 주문 상태 불일치, 답변·알림 누락, 모바일 주요 버튼 조작 불가 |
| `Minor` | 우회 가능한 문구·정렬·시각·표현 문제 | 오탈자, 간격, 비핵심 안내 개선 |

다음 상황은 즉시 중단하고 판정 책임자에게 알린다.

- 타인의 주문·예약·후기 증거·연락처가 보임
- 같은 결제·환불·적립·쿠폰 사용이 두 번 반영됨
- 재고 또는 슬롯 정원이 음수이거나 양쪽 화면에서 모순됨
- 실제 결제 결과가 불명확한데 화면이 재결제를 유도함
- 관리자 권한 없이 비공개·숨김 자료에 접근할 수 있음

## 10. 종료 조건과 릴리스 판정

### GO

- 모든 P0가 `PASS` 또는 `RETEST_PASS`다.
- 미해결 `Blocker`·`Critical`이 없다.
- 금액·쿠폰·적립금·재고·정원과 테스트 결제 환불 대사가 끝났다.
- 실사용자 2명 이상과 관리자 1명 이상이 핵심 업무를 독립적으로 완주했다.

### CONDITIONAL_GO

- P0는 모두 통과했고 `Major`만 남았다.
- 각 잔여 결함에 담당자, 수정 기한, 임시 운영 절차와 영향 범위가 기록됐다.
- 판정 책임자와 실제 운영 관리자가 위험을 승인했다.

### NO_GO

- P0가 `FAIL`, `BLOCKED`, `NOT_RUN` 중 하나다.
- `Blocker` 또는 `Critical`이 미해결이다.
- 결제·환불·혜택·재고·정원 대사가 끝나지 않았다.
- 고객 또는 관리자가 핵심 흐름을 도움 없이 끝내지 못했다.

### PRODUCTION_SMOKE 판정

- 허용된 정상 경로가 모두 통과하면 `SMOKE_PASS`, 하나라도 실패하면 `SMOKE_FAIL`이다.
- 운영 smoke는 격리 UAT의 `GO`를 대체하지 않고, 금지 시나리오를 운영에서 추가 실행해 판정을 바꾸지 않는다.

## 11. 종료 후 정리

`ISOLATED_UAT`에서는 아래 정리 항목을 모두 수행한다. `PRODUCTION_SMOKE`에서는 기존 운영 데이터를 수정·삭제하지 않으며, 공개 콘텐츠·미디어 정리 항목은 `N/A`로 기록하고 관찰한 최종 상태와 승인된 후속 작업만 남긴다.

- [ ] 테스트 주문·예약·8회권·클레임·후기의 최종 상태를 기록했다.
- [ ] 실제 결제·환불과 쿠폰·적립금 이용 내역을 숫자로 대사했다.
- [ ] 관리자 `오늘 할 일`에 남은 테스트 업무를 정리하거나 인계했다.
- [ ] 테스트 알림 수신자와 임시 계정·권한을 정리했다.
- [ ] (`ISOLATED_UAT` 전용) 테스트 상품·클래스·슬롯·공지·이벤트·쿠폰을 비공개·비활성화하거나 삭제했다.
- [ ] (`ISOLATED_UAT` 전용) 업로드 미디어의 현재 참조를 확인하고 불필요한 파일을 정리했다.
- [ ] 후기 신고·숨김처럼 정책상 남는 테스트 증거는 삭제하지 않고 보존 책임자와 만료일을 기록했다.
- [ ] 스크린샷·영상에서 개인정보와 비밀값을 제거했다.
- [ ] 결과 문서의 결함 링크와 재검수 상태를 갱신했다.
- [ ] 최종 GO 판정자와 시각을 기록했다.

## 12. 유지보수 규칙

- 사용자 여정이 바뀌면 먼저 PRD와 구현을 갱신하고 이 문서의 해당 시나리오만 수정한다.
- 화면의 버튼 위치나 일시적인 문구보다 업무 상태와 관찰 가능한 결과를 기준으로 쓴다.
- 자동화된 Playwright 시나리오가 있어도 실제 사용자 이해·운영자 판단·양쪽 업무 연결 검수를 삭제하지 않는다.
- 반대로 자동 테스트가 소유하는 정밀한 시간·동시성·API 오류 코드 조합을 UAT 참가자에게 반복 수행시키지 않는다.
- 실제 실행 결과는 [결과 양식](result-template.md)을 복사해 `runs/`에 보존한다.
