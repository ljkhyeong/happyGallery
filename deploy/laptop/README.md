# happy-gallery.com 노트북 설치 준비

2026-09-05에 확인한 보유 노트북으로 Linux 설치와 서비스 검증을 먼저 진행한다. 운영자는 Windows 삭제와 Linux 설치를 허용했다. 실제 OS 설치·접속·공개 배포는 아직 실행하지 않았다. 현재 실행 계획은 루트 `plan.md`, 서비스 배포·백업·복원 명령은 [k3s 운영 절차](../k3s/README.md)를 따른다.

## 확인한 사양과 판단

| 항목 | 확인 내용 | 판단 |
| --- | --- | --- |
| CPU | Intel Core i5-8250U, x64 | 4코어·8스레드. `linux/amd64` 이미지 사용 |
| 메모리 | 16GB | 기존 전체 구성을 먼저 실행해 사용량을 측정할 여유가 있음 |
| 저장장치 | Windows 표시 총 477GB, 사용 79GB | SSD/HDD 종류와 상태는 사진만으로 알 수 없음 |
| OS | Windows 11 Pro | 삭제 후 서버 전용 Linux 설치 가능 |
| 회선·전원 | 24시간 가동 가능. 유선 연결·공유기 관리 가능 여부는 확인 필요 | 외부 공개 방식과 무인 복구를 확정하기 전 확인 |

CPU 코어 수는 [Intel 공식 사양](https://www.intel.com/content/www/us/en/products/sku/124967/intel-core-i58250u-processor-6m-cache-up-to-3-40-ghz/specifications.html)을 확인했다. 기존 app·MySQL·Redis·frontend·모니터링 컨테이너의 메모리 한도 합계는 약 4.75GiB이며 OS·k3s 사용량과 이미지 빌드 메모리는 별도다. 이 합계는 실측 사용량이나 처리 가능한 이용자 수가 아니다.

노트북은 서버 임대료가 없지만 전기료·외부 백업·문자와 결제 비용은 남는다. 소비전력과 백업 용량을 측정하기 전에는 월 총비용을 확정하지 않는다. 예를 들어 콘센트에서 평균 20W가 측정되면 30일 상시 가동은 14.4kWh다. 이는 실측값이나 CPU TDP를 전체 소비전력으로 환산한 값이 아니다. 클라우드 VM 구매는 보류하고 [서울 리전 비교](../cloud/README.md)는 이전 후보로 보관한다.

## 1. 설치 USB 준비 — 해당 Windows 노트북에서 진행

설치 기준은 **Ubuntu Server 24.04 LTS amd64**다. 이번에 확인한 설치 이미지는 `ubuntu-24.04.4-live-server-amd64.iso`다. GUI가 없는 서버용이며, Intel CPU도 `amd64`를 선택한다. 24.04는 [일반 보안 유지보수가 2029년 5월까지 제공되는 LTS](https://ubuntu.com/about/release-cycle)다. 이 노트북에서의 드라이버·서비스 호환성 검증은 설치 후 수행한다.

1. 필요한 Windows 파일을 다른 장치에 복사하고, 지워도 되는 8GB 이상 USB를 준비한다. USB 작성은 USB 내용을, OS 설치의 전체 디스크 선택은 대상 노트북 디스크의 Windows와 파일을 지운다.
2. [Ubuntu 공식 24.04 다운로드](https://releases.ubuntu.com/24.04/)에서 **64-bit PC (AMD64) server install image**를 받는다. 같은 페이지의 `SHA256SUMS`와 다운로드 파일의 해시를 대조한다.
3. [Rufus 공식 사이트](https://rufus.ie/)에서 프로그램을 받아 실행한다. 장치 목록에서 설치 USB를 용량·모델로 확인하고 내려받은 ISO를 선택한다. UEFI 설치에는 GPT와 UEFI를 선택한다. 추가 다운로드나 기록 방식 선택은 [Ubuntu의 Rufus 안내](https://ubuntu.com/tutorials/create-a-usb-stick-on-windows)를 따른다.
4. USB 작성 후 노트북을 재부팅하고 제조사 부팅 메뉴에서 해당 **UEFI USB**를 선택한다. 사진의 모델군 표시만으로 부팅 단축키를 단정하지 않는다.

## 2. Ubuntu 설치 화면에서 선택할 값

설치 화면 설명은 [Ubuntu Server 설치 안내](https://ubuntu.com/server/docs/tutorial/basic-installation/)를 참고한다.

| 화면 | 선택할 값 |
| --- | --- |
| 설치 종류 | Ubuntu Server |
| 네트워크 | 가능하면 유선 연결, 최초에는 공유기 DHCP 사용 |
| Proxy·Mirror | 별도 사내 설정이 없다면 기본값 |
| 저장장치 | 약 477GB인 내부 디스크의 모델·용량을 확인한 뒤 전체 디스크 사용. 연결된 백업 디스크는 분리 |
| 파일시스템 | 최종 화면에서 `/`에 배정된 용량 확인. LVM 기본값이 일부 공간만 배정했다면 필요한 OS 부팅 영역을 제외한 공간을 `/`에 배정 |
| 서버 이름 | 예: `happygallery-01` |
| 운영 계정 | 예: `hgadmin`, 운영자가 직접 비밀번호 지정 |
| SSH | `Install OpenSSH server` 선택 |
| 추가 서버 소프트웨어 | 선택하지 않음. k3s와 필요한 도구는 OS 확인 후 설치 |

디스크 암호화를 선택하면 재부팅 때 암호 입력이 필요할 수 있다. 자동 전원 복구와 별개이므로 잠금 해제 방법까지 확인한 뒤 무인 복구 여부를 판단한다. 운영 계정 비밀번호·개인키·복구키는 채팅이나 저장소에 적지 않는다.

설치가 끝나면 안내에 따라 USB를 제거하고 재부팅한다. **여기까지는 공인 DNS 변경이나 공유기 포트 개방이 필요하지 않다.**

## 3. 첫 로그인 후 확인

아래 조회는 새로 설치한 **노트북의 Ubuntu 터미널**에서 실행한다. 개발용 Mac에서는 실행하지 않는다.

```bash
lsblk -d -o NAME,MODEL,SIZE,ROTA,TRAN
free -h
df -h /
hostname -I
```

- 내부 디스크의 `ROTA=0`은 비회전식 장치, `ROTA=1`은 회전식 장치로 보고된다는 뜻이다. 모델 정보로 SSD 여부를 함께 확인한다. 필요하면 장치별 SMART 상태와 온도도 조회한다.
- `/`에 실제 배정된 용량을 확인한다. 이미지 빌드 캐시·k3s 이미지·MySQL·미디어·모니터링이 이 공간을 사용한다.
- 같은 내부망의 관리 PC에서 계정과 사설 IP로 SSH 접속한다. 첫 연결의 호스트 키 지문은 노트북에서 대조한다. 관리 PC가 다른 망에 있다면 이 사설 IP만으로 접속할 수 없다.
- 공개키 로그인이 확인되면 SSH 비밀번호 로그인과 root 직접 로그인을 제한한다. SSH를 인터넷에 포트 전달하지 않는다. 외부 관리가 필요하면 접근 방식을 별도로 정한다.
- 보안 업데이트·시간 동기화와 `Asia/Seoul`을 설정한다. 덮개 닫기·유휴 절전·최대절전 동작을 조정한 뒤 실제로 SSH가 유지되는지 확인한다. 초기 확인 중에는 덮개를 열어 둔다.
- 전원 연결 상태, 냉각·배터리 상태와 BIOS의 전원 복구 기능을 확인한다. 재부팅 후 서비스 자동 기동과 완전 방전 후 전원 복구는 별개로 확인한다.

이 단계가 끝나면 [k3s 운영 절차의 외부 전제](../k3s/README.md#1-외부-전제)로 이어간다. 현재 빌드·이미지 반입 스크립트는 같은 호스트에서 실행하므로 첫 배포는 서비스 공개 전에 진행한다. Apple Silicon Mac에서 만든 ARM 이미지를 그대로 반입하지 않는다. 운영 갱신 전에는 별도 빌드·이미지 전달 절차를 마련한다.

## 4. 인터넷 연결과 외부 백업

노트북 설치와 별개로 아래 조건을 확인한 뒤 공개 접속 방식을 정한다.

- 공유기에서 노트북의 내부 IP를 DHCP 예약으로 고정한다. 인터넷 회선의 서버 운영·인바운드 포트 제한도 확인한다.
- 공유기 WAN 주소와 외부에서 보이는 주소를 비교하고 이중 공유기·통신사 공유 주소 사용 여부를 확인한다. 서로 다르거나 WAN 주소가 사설 주소이면 포트 전달만으로 해결된다고 가정하지 않는다.
- 직접 공개가 가능하면 TCP 80/443만 노트북으로 전달한다. 현재 기본 경로는 Cloudflare **DNS only → 공유기 → Traefik TLS**다. A 레코드는 실제 회선 공인 IPv4를 사용하고, 유동 IP라면 주소 갱신 방법을 마련한다. IPv6는 별도 검증 전 공개하지 않는다.
- 22·6443·3306·6379·8080·8081·9090·9093·3000 및 UDP 8472는 인터넷에 전달하지 않는다. 호스트 방화벽은 k3s 내부 통신을 유지하면서 외부 접근을 제한한다.
- 직접 공개가 불가능하면 터널 방식이나 AWS 서울을 다시 비교한다. 터널은 아직 구현·검증된 경로가 아니며, 도입 시 실제 이용자 IP·HTTPS 전달·인증서 갱신·쿠키·처리율 제한을 함께 검증한다.
- 운영 백업은 노트북·집 전원·회선과 분리된 원격 저장소를 사용한다. 저장 국가·업체·용량·월 비용은 미확정이다. 기존 백업 스크립트가 요구하는 원격 mount와 완료 marker 동작을 검증한다. 노트북 내부 복사본이나 같은 집의 디스크만으로 운영 복구 조건을 충족하지 않는다.

백업은 기존처럼 6시간 간격·30일 보존으로 검증한다. **현재 백업은 app을 중지하므로 하루 4회 주문·예약·로그인 API가 중단될 수 있다.** 실제 백업·재기동 시간과 별도 환경에서의 복원 결과를 확인하고, 중단 시간이 운영에 맞지 않으면 공개 전에 개선한다. DB·미디어·배포 이미지 복구 묶음과 암호화 키를 분리해서 보관하는 조건은 [k3s 운영 절차](../k3s/README.md)를 유지한다.

## 운영 개시 판단

사양 확인만으로 운영 개시를 확정하지 않는다. 실제 HTTPS·외부 비공개 포트·핵심 주문과 결제 흐름·동시 처리·배치·백업·복원·재부팅 후 기동을 검증한다. 정전이나 인터넷 단절은 서비스 전체 중단으로 이어지므로 외부 uptime 감시를 둔다. 상시 가동이나 외부 연결 조건을 충족하지 못하면 노트북을 검증용으로 유지하고 AWS 서울 후보를 다시 검토한다.
